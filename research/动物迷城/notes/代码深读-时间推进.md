# 代码深读：时间推进、观察事件与存读档边界

核查日期：2026-10-10。关联机制卡：**K01 行动推进时间、K03 白天准备改变夜间**，兼及 K08 资源耦合、K11 失败恢复。本轮只补充研究，没有改变《来自月亮的 Z》的已定规则、采用状态或代码。

研究对象是社区项目 [LittleCAT8449/BackToTheDawn-ModLoader](https://github.com/LittleCAT8449/BackToTheDawn-ModLoader)，固定 commit **`c766a431fe1d959e4418b07fe1980b60397b6b33`**。只读缓存：`/tmp/bttd-research-20261010/modloader`。本轮对缓存执行文本检索和分段阅读，没有构建、启动、注入或执行社区程序，没有读取游戏安装目录或用户存档。

## 1. 最重要的结论

**这份代码提供了“观察游戏时钟”的实现，没有提供原游戏“为什么、何时、按什么规则推进时钟”的完整实现。**已经追通读取、Hook、去重、通知和载入基线；不能据此声称已取得原作时间系统源码。

| 能提高确定性的结论 | 本轮依据 | 仍不能推出的结论 |
|---|---|---|
| 插件按需读取 `TimeManage.nowTime`，复制成普通时间快照 | T01—T02 | 原作的主时钟是否逐帧更新、哪些行动免费、具体行动耗时 |
| 两个 `GameProcess.PassMinutes` 重载返回后，插件检查快照是否改变 | T03—T04 | 所有时间变化都经过这两个入口；一次玩家行动只调用一次；所有日程回调均已执行完 |
| 插件事件是同步通知，不是推进游戏时间的命令 | T05 | 订阅者不会产生其他副作用，或通知等于一笔已完全提交的世界事务 |
| 约 0.2 秒轮询用于识别任务日志变化 | T07 | 原作每 0.2 秒推进时间或检查全部任务；这个频率属于插件 |
| 载入入口返回与可操作状态分开；可操作时重新建立事件基线 | T06 | 不会出现载入过程通知；所有恢复状态都必定通过事件逐项重放 |
| 地图变化通知与时间变化通知来自不同 Hook | T03—T04 | 换地图一定耗时、一定不耗时，或两种事件有全局固定先后顺序 |

**旧版“普通移动/待机不推进时间”的依据仍是当年的攻略与游玩预览，而不是这次社区代码。**正式版当前构建的逐动作规则与例外仍待实机确认。官方“专注/饱腹随时间变化”“医生 17:30 下班”等说明证明时间与世界状态有关联，但未给出完整时钟算法。[T12—T13]

## 2. 真实读取链：读取一次，而非走一步时间

```text
Mod 请求 GameContext.Time
  → GameContext.Current
  → SnapshotProvider.Invoke()
  → GameContextAdapter.Capture()
  → CaptureTime()
  → 读取 TimeManage.nowTime 的 day / wakeDay / hour / minute
  → 调用 GetTotalMinutes()，构造 GameTimeSnapshot
```

`Plugin.Load` 把 `SnapshotProvider` 绑定到 `GameContextAdapter.Capture`。因此 `GameContext.Time` 是每次访问时取快照，不是一个由插件计时器自行累加的字段。`CaptureTime` 的可见代码只读四个字段并调用总分钟 getter；此处没有加时、减时或写回 `nowTime`。[T01—T02、T08]

快照有五项：`Day`、`WakeDay`、`Hour`、`Minute`、`TotalMinutes`。**应保留原字段名而不自行补全语义**：文档将 `WakeDay` 描述为醒来日，但当前源码不包含原游戏字段的维护规则，也没有 `GetTotalMinutes` 方法体。不能自行假定 `Day` 从 0 或 1 开始、`WakeDay` 等于自然日、总分钟必定为 `day × 1440 + hour × 60 + minute`。[T01—T02]

还有两个读取边界：

- `Current` 捕获 Provider 异常并返回 `null`；`Capture` 在 `GameProcess.singleton` 为空时也返回 `null`。因此“读不到时间”与“游戏时间为零”是两种状态。
- `Capture` 没有要求 `IsGameplayReady == true` 才生成快照；其结果含一个独立的 readiness 标志。**时间非空不等于玩家已可操作。**一次取 `Current` 再读取其中时间、地图和角色，能避免多次 getter 分别捕获；但可见代码没有锁或事务版本，不能把文档的“一致快照”扩大为原游戏全局原子快照保证。[T01—T02]

## 3. 时间变化通知：Postfix + 五字段比较

```text
原游戏某调用者调用 PassMinutes(int, bool) 或 PassMinutes(TimePass)
  → 原方法返回
  → 社区 Postfix 调 PublishTimeIfChanged()
  → 读取 current，与插件保存的 previous 比较
  → 保存 current 作为下一次基线
  → previous 非空且值不同，才 RaiseTimeChanged(previous, current)
  → 同步逐个调用订阅者
```

两个补丁都只有 Postfix，既没有在 Prefix 替换参数，也没有在 Postfix 写入游戏时钟。当前链属于**变化观察器**。全缓存检索 `TimeManage`、`PassMinutes`、`GetTotalMinutes`，没有找到原游戏这几个类型/方法的实现；工程通过外部 interop DLL 引用它们。仅凭方法名无法重建原作的时间推进顺序。[T03、T09]

`GameTimeSnapshot` 为 record，`previous != current` 比较的是记录值，不只比较总分钟。由此可直接读出：[T01、T04]

1. 首次没有 previous 时，仅建立基线，不发时间变化事件。
2. 如果两个重载嵌套调用但最终快照相同，后一次比较可消除相同状态的重复通知；**不能保证每次玩家行动只有一条事件**，中间状态不同仍可能多次通知。
3. 即使总分钟相同，只要其他字段变化，仍可能触发事件。`WakeDay` 等字段是否会单独变化需实测。
4. 事件载荷只有 previous/current，没有 action ID、原调用参数、原因、成本或成功/失败结果。**无法从事件独立判断“这次工作耗时 30 分钟”或“失败额外扣时”**，必须关联玩家动作与其他状态。
5. 如果有原游戏路径直接改时间但没有经过所 Hook 的重载，插件就可能漏掉即时通知；下次 Hook 才看到较大的差值，或在重建基线时被吸收。是否存在这样的原生路径，本轮未知。

API 文档把事件描述成时间推进及回调完成后的通知；当前源码只能直接核到 **PassMinutes 方法返回后的 Postfix**。因为没有其原方法体，无法排除方法内部排队协程、UI 回调或后续帧任务。“所有世界后果已经稳定”应留给实机验证。[T03、T11]

## 4. 线程、轮询与其他时钟不要混为一谈

`GameEvents.Raise` 直接遍历委托并调用，没有看到时间事件专用的队列、后台线程或主线程转发器；每个订阅者有 try/catch，单个订阅者抛异常后继续其他订阅者。因此就这段代码而言，它运行在 **触发 Postfix 的调用线程**。原生调用实际在哪个线程发生，需要运行证据；不能只凭事件名称保证线程安全。[T05]

`TaskEventMonitorRunner.Update` 调用 `TaskRuntime.Tick` 和 `TaskEventMonitor.Tick`。后者用 `UnityEngine.Time.unscaledTime` 限制为约每 0.2 秒读取一次任务日志，比较完成、失败、放弃、超时、目标等快照。**这是采样频率，不是游戏内分钟，也不是每个任务自带 0.2 秒期限。**短于采样间隔的多次变化可能被合并成一次前后对比；任务事件和时间事件的日志顺序不能直接还原原生结算顺序。[T07]

`TaskRuntime.Tick` 还会处理社区任务的待应用注册、待接取队列。这说明“每帧做一些插件工作”不等于“每帧让原作时间流逝”。插件的场景诊断探针延迟 120 帧扫描，也只是诊断调度。[T07—T08]

作为可复用的简单设计例子，社区 JSON 电话条件支持按 Day 和当天分钟判断时间窗口。`timeBetween` 两端均含等号，起点晚于终点时按跨午夜窗口处理；示例为 20:00—06:00。这是**社区 Mod 的条件解释器规则**，不证明原作全部设施也使用同样的闭区间或窗口算法。动态通话在开始时拿到一个时间快照；本轮不推断整段对话中的时间是否冻结。[T10]

## 5. 存读档与地图边界：三件事必须分开

可见生命周期为：[T06]

| 信号 | 代码具体做什么 | 应如何理解 |
|---|---|---|
| `ReadArchiveDataAndStartGame` Prefix | 重置运行时克隆房间；ready=false；重置任务监测；发 ArchiveLoadStarted | 开始进入一次载入，不是时间已恢复完成 |
| 同一方法 Postfix | 发 ArchiveLoadInvocationReturned | 入口调用已返回，不等于地图/UI/角色可操作 |
| `ShowCurrentMapAndCanControl` Postfix | ready=true；处理社区任务配置；重建时间/地图/玩家基线；建立任务基线；发 GameplayReady | 插件选定的可操作边界；该时刻恢复状态作为基线 |
| `Map.FocusMap` Postfix | 读取地图 ID；与旧 ID 不同才发 MapChanged/RoomChanged | 地图观察信号，不提供切图时间成本 |
| `Plugin.Unload` | 取消补丁/订阅并执行 Adapter.Reset | 真正清空时间/地图基线及 Provider 的位置之一 |

`ShowCurrentMapAndCanControl` 每次被调用时都会重建基线；原生在什么场景调用它、是否只用于初次读档，当前仓库未提供调用者。不能擅自把这个补丁等同于“每局仅执行一次”。[T04、T06]

**发现一个需要特别验证的静态边界：**读档 Prefix 和主菜单 Prefix 虽把 ready 设为 false，却没有清空 `_lastPublishedTime` / `_lastPublishedMapId`；`PublishTimeIfChanged` 与 `PublishMapIfChanged` 本身也没有 ready 门槛。因此若载入期间触发这些原生入口，代码允许新存档时间/地图与旧基线比较，产生看起来像跳时或切图的通知。随后 GameplayReady 又会用恢复后的状态重建基线。[T04、T06、T08]

这不是已复现的原作缺陷；它是社区观察器的**潜在跨会话误归因**。在研究记录中，载入过程事件不能自动记为玩家支付的时间成本。初始化 baselines 则不发 `TimeChanged`，因此也不能只订阅该事件就期待收到完整读档时间；需在 readiness 边界主动读取一次快照。

地图观察器只比较 ID：同 ID 的地图重新显示或内部状态改变，不会因此得到 MapChanged。任务基线也会把首次恢复的任务视为已有记录，而不是全部重新接取。地图事件的“没发生”不证明环境状态没变化，任务事件的“没发生”也不证明存档没有恢复任务。[T04、T07]

本轮检索未找到存档序列化或写存档的实现，因此不能给出时钟如何写入存档、午夜恢复顺序、回溯后资源如何重算的结论。上面的判断限定在**读取和观察层**。

## 6. 与官方和历史玩法证据怎样接起来

- **官方直接支持的规则：**专注可随时间恢复；饱腹随时间下降，饥饿继续影响健康/心态；医生 17:30 下班；祝福持续 24 小时。可以确认时间连接资源和可用机会，但官方这些段落没有说现实秒数与游戏分钟如何映射。[T12]
- **EA 历史玩法证据：**2023-11-08 攻略记载移动/送礼不耗时，具体行动耗时；当时的游玩预览也说明走动和待机不推进时间。应继续以“旧版游玩规则”记录，而不是被当前社区 Hook 间接升级为所有正式版模式结论。[T13]
- **本轮代码增加的证据：**至少有社区作者围绕原生分钟推进入口构建了五字段快照及变化通知；已经能区分读取时钟、时间变化观察、任务轮询、载入恢复四件事。它未补齐行动消耗表、日程触发器、跨窗口处理或真实潜行计时。[T01—T09]

## 7. 对《来自月亮的 Z》的建议：保留代价，主动设计结算边界

**版本对齐：本节以当前 v2 设计为准。**《游戏设计总案 v2》及专项规格已给出 21 天、分钟与精力预算、危险区动作步、双视角共享世界时间和异步读档边界；旧 v1 的七天、粗时段及关键潜行实时建议只作历史材料。v2 的细则和具体数值仍是待原型验证的规则草案，不代表已实现或已平衡，也不退回为本研究重新决定的开放问题。以下是基于社区代码发现提出的实现与验收重点，不是原作事实或新增批准。[T14]

1. **K01：按 v2 分开读状态与提交行动。**普通安全区域移动、查看记录、输入和等待 AI 不推进时间；正式劳动、深入调查等由行动卡预告并结算游戏分钟与精力。保存行动 ID、前后时间、资源和机会变化，防止 UI 重绘、模型延迟或重复回复被误作一次新行动。
2. **K01/K03：实现 v2 已定义的完整窗口与区间推演。**不可分活动超出窗口不能开始；可分段活动必须明确各段成本和进度。活动内部跨过 NPC 或消息事件时按游戏时间顺序推演，再原子提交事实、成本、时间和结果；原子提交用于防重复，不把全部中间变化压到结束时刻，也不允许晚到消息回写早先决定。
3. **K03/K11：把读档恢复与异步结果隔离。**按 v2 保存世界快照、pending 行动、唯一事务 ID 和已结算结果；AI 请求绑定快照版本，载入另一档后丢弃旧请求。恢复网络请求或重播动画只补表达，不重新扣分钟、发工资、生成承诺。结合本轮观察器的旧基线风险，建议恢复完成后再公开可操作状态，并用独立载入标识防止跨存档通知混入当前行动。
4. **危险区沿用动作步，不恢复实时潜行。**v2 中相邻战术点移动、开门、操作或主动等待按标注推进步数与游戏分钟，统一结算巡查和摄像头；观察、悬停、输入、模型等待不推进步数，切图不重置风险状态。默认一步 1 分钟是当前未平衡草案值。应验证分钟预算与局部步数不会重复扣除，也不把社区任务的 0.2 秒采样变成玩法计时器。
5. **双视角共享同一区间，保留因果先后。**按 v2 的起点、资源、消息交接点和汇合上限执行：前置同时成立且无资源冲突的独立行动，以较晚完成时刻汇合；依赖新消息的行动收到消息后串行开始。验证切换不重复扣世界时间、不扣错行动者费用、不复制物品，也不把玩家看过 Z 镜头当作玩家角色已获得情报。
6. **对用户显示 v2 的行动语义。**玩家需要看到起止时刻、分钟/精力成本、会错过的窗口和下一动作步的可见风险；无需看到 `TimeChanged`、Provider 或采样间隔。优先验证“能够安心阅读，同时无法免费取得所有机会”，再调整具体耗时和每日内容密度。
