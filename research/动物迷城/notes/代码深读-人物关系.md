# 代码深读：人物关系、数值读取与变化观察

日期：2026-10-10。对象：社区项目 `LittleCAT8449/BackToTheDawn-ModLoader`，固定 commit **`c766a431fe1d959e4418b07fe1980b60397b6b33`**。本轮仅静态阅读只读源码缓存和公开网页，没有构建、运行插件、启动游戏、读取存档或修改原作数据。

已读根 `AGENTS.md`、研究入口、开发参考导航、研究第 9 节、K04「关系成为能力入口」、K09「阵营选择有明确代价」。起初参考 v1 的认知/合作边界，交付前已复核工作区新增 v2 的关系与 AI 规格；以下以 v2 为当前设计依据。本文只增加研究证据，不修改本项目规则或采用状态。

## 1. 先明确能证明什么

| 层次 | 本次结论 | 不能扩大成什么 |
|---|---|---|
| 原作公开机制 | 官方区分囚犯好感、帮派信任、女性角色的“热情”；关系影响交易与援助。[R01] | 官方没有在该说明公布 `Friend` 与 `Affection` 的数值公式、边界处理或全套触发条件 |
| 社区读取实现 | 关系 API 经 Provider 现采 `CharacterAttribute`；`Friend`、`Affection`、上下限各自读取，模式调用 `IsFriendToAffection()`。[R02–R05] | 这些是插件观察字段，不是游戏完整关系模型或原作方法实现 |
| 社区写入能力 | **没有发现公开的关系写 API。**已核 `RelationshipApi` 只有查询，Provider 也只有读取委托；`ChangeFriend` 在本仓库出现的是 Harmony 观察补丁，不是供 Mod 使用的 setter。[R02–R06] | 不能说原作没有写入口，也不能说其他低层 Mod 绝不可能间接改变关系 |
| 社区变化事件 | 存在 `TradeDetected/TradeCompleted` 的 `RelationshipDelta`；部分数值来自方法参数，部分来自邮购成本补值。[R06–R09] | **不能无条件把事件值当成原作已生效的净变化，也不能当所有 NPC 的完整关系日志** |

最重要的纠正：仓库注释建议把交易事件作为权威变化量，但实际代码并未普遍用关系的前后快照相减。因此“当前值”与“交易观察值”需要分别记录，不能仅凭注释提高证据等级。

## 2. 原作机制证据与社区术语

云豹娱乐 2026-02-12 的官方社交介绍确认：交談/赠礼可以提升囚犯好感，改善可交易内容，进一步获得随身装备与人物过去；帮派信任由帮派任务提高，加入要求及排他性另有规则；与有好感的女性聊天或送情书培养“热情”，可用来寻求援助，单方面索取会使对方失望。[R01]

社区文档把 `Friend` 称为通用关系值，把 `Affection` 解释为亲情/恋爱模式下的当前值；这属于社区命名说明。[R12] 原作官方页面使用“热情”，**不能因为词语近似就断言这几种中文术语逐项对应同一存储字段**。本轮桥接确认的是成员访问，不是本地化语义映射。

也不能把帮派信任塞进 `Friend`：官方已区分两者；社区 `CharacterRelationshipSnapshot` 根本没有帮派信任、贡献、声望字段。[R01–R02] `GAME_SYSTEMS.md` 中的 `ChangeGangFriend` 等是社区的成员目录，不是这份关系 API 已实现的读写功能。[R14]

## 3. 查询链：从公开 API 追到实际字段

```text
ModApi.Relationships
  → RelationshipApi.All / Interactive / Protagonist
  → GameContext 对应属性
  → Plugin.Load 安装的三个 Provider
  → GameContextAdapter.CaptureRelationships 等
  → CharacterManage / CharacterAttribute
  → 新的 CharacterRelationshipSnapshot
```

### 3.1 各字段实际来自哪里

| 快照字段 | 桥接读取 | 已确认与限制 |
|---|---|---|
| `CharacterId` | `attribute.id` | 角色 ID；不是关系记录 ID，也不是双方 ID 组成的关系边 |
| `CharacterName` | 先 `GetFullName()`；结果空白才尝试 `GetName()` | 名称可空；若前一调用直接抛错，catch 吞掉，不继续保证后备名称成功 |
| `Friend` | `attribute.friend` | 原样拷贝整数；插件此处不归一化、不换算、不夹断 |
| `Affection` | `attribute.affection` | 原样读取；社区注释称其为衍生值，但衍生算法不在已读代码内 |
| `FriendLowerLimit` / `FriendUpperLimit` | 同名 lower/upper 成员 | 原样拷贝；没有写死默认范围，也没有用上下限计算百分比 |
| `IsAffectionMode` | `attribute.IsFriendToAffection()` | 调用游戏侧方法得到 bool；判定条件与模式切换副作用未公开在本仓库 |
| `IsProtagonist` / `IsInteractive` | 与当前主角/交互角色的 ID 比较 | 是采样时的角色标记；后续交互目标改变不会自动更新旧快照 |

依据为 `GameContextAdapter.cs` 1419–1453 行。[R05] 这里没有证明 `Affection = Friend - 某阈值`、`Friend` 固定为 0–100、模式在某值自动开启等说法。即使其他旧攻略给过数字，也不能据此补出当前正式版公式。

### 3.2 `All` 不等于全世界所有人物

`CaptureRelationships()` 遍历当前 `CharacterManage.characterAttributeDict.Values`，跳过 null；然后按 `CharacterId` 去重补入主角和当前交互对象。[R05] 因此只能称“可读取的已加载角色集合，加上主角/交互对象兜底”，不能当完整角色配置表或任意两 NPC 的关系网络。

`TryGet(id)` 线性扫描一次 `All`；没有命中就返回 false。`TryGetAffection` 命中时直接返回 `Affection`，**不会先检查 `IsAffectionMode`**；未命中时输出参数置 0，同时返回 false。[R02] 调用方若只读取输出数字而丢掉 bool，会把“未知/未加载”误当“好感为零”。

`InteractiveAffection` 只是 `Interactive?.Affection`，没有交互对象返回 null；它适合显示当前上下文，不适合跨对话保存某个人的身份。[R02] `Protagonist` 同样是主角对象上关系成员的快照，不能擅自解释成“所有 NPC 对玩家的平均好感”。

### 3.3 没有关系写接口，也没有公式修正层

已全文读取 74 行 `Relationship.cs`、160 行 `GameContext` 类，并全仓检索 `Set/Change/AddFriend`、`Set/Change/AddAffection`、`friend =`、`affection =`。公开关系类只有 `All`、`Interactive`、`Protagonist`、`InteractiveAffection`、`TryGetAffection`、`TryGet`；没有返回操作结果的关系变更方法。[R02–R03]

读取所得 record 是数据快照；修改本地副本不会因此回写原作。`TradeDetectedEvent` 也明确是不可取消的只读观察。[R09] `GAME_SYSTEMS.md` 列出原生 `ChangeFriend` 的名字，只能证明社区辨认过这个成员；本仓库没有其原作方法体。[R14]

## 4. 刷新、缺省与失效边界

| 情况 | 代码实际行为 | 使用时的含义 |
|---|---|---|
| 再次读取 `All` / `Interactive` | 每次调用 Provider 并重新采样；关系 API 没有自己的定时缓存 | 新请求可得到新值；保存下来的旧 record 不会自行刷新 |
| Provider 未安装或为空 | `All` 返回空数组；单对象返回 null | 空结果不是“所有关系都为零” |
| Provider 抛异常 | `GameContext` catch 后同样返回空数组/null | API 没有错误原因或“未知”状态码，外部难以区分没有数据和读取失败 |
| 字典遍历中途某项失败 | Adapter 捕获整段遍历异常，保留先前已追加记录，再补主角/交互对象 | `All` 可能是部分集合；不是每个坏对象独立跳过后保证遍历完毕 |
| 补主角/交互对象阶段失败 | 补充操作在 Adapter 的字典 try 之外；异常可再被外层 `GameContext` 吞掉 | 原本已有的局部结果也可能变为空数组 |
| 主菜单/读档阶段 | 生命周期把 `IsGameplayReady` 设 false；但三个关系捕获函数没有检查它 | 调用方应先检查就绪状态；未就绪时能否暂读旧原生对象需实机核验 |
| 插件卸载 | 清订阅、Adapter.Reset → GameContext.Reset 清三个 Provider；TradeSignals.Reset 清观察状态 | 新查询失效；此前持有的快照仍是旧数据，不带失效通知 |

以上来自 R03–R07、R11。当前关系 record 没有采样时间、存档 ID、会话版本或是否完整字段；在读档/角色切换时直接复用旧记录存在误关联风险。这是由接口结构推导出的集成风险，尚未执行故障复现。

还应注意：`Plugin` 的 `EnableLifecycleHooks` 开关控制 assembly 级 Harmony 安装；关闭时另装的是电话补丁，不能默认关系变化观察仍照常存在。[R04] “有 Provider”与“有事件 Hook”是两件事。

## 5. 变化链：有观察事件，但覆盖范围和准确度有限

### 5.1 普通变化的入口

`GameLifecyclePatches` 对 `ThingPackage.ChangeFriend` 安装 **Postfix**，把 `__instance.cId`、参数 `count` 与 `reason.ToString()` 传给 `TradeSignals.PublishRelationship`。[R06] 本补丁未采集调用前后的 `Friend`，也未读取原生函数返回的实际变更量。

因此目前只能确认“原生方法返回后，插件报告了传入的 count”。如果原作在上限处夹断、根据模式换算，或接受参数但因业务条件没有更改，这个 count 是否等于最终净变化必须另验。**Postfix 的位置不自动使参数变成结算事实。**

### 5.2 `PublishRelationship` 的三条分支

1. **语义交易处理中**：把 delta 加到栈顶 `state.RelationshipDelta`，暂不独立发事件。此处没有按入参 `characterId` 单独分账。[R07]
2. **匹配延迟商店原因**：把一次变化存入单个 `_pendingSettlement`。后续订单仅在角色为当前主角、间隔不超过两秒、原因匹配时取走它。原因匹配采用 `GirlFriendShop/GirlFriendMail/Maggie/Maji` 等文本片段；这是社区兼容策略，不是原作原子交易规则。[R07]
3. **其他情况**：发 Currency 类型、Relationship 货币、RelationshipAction 阶段的观察，负值判为 PlayerGives，非负值判为 PlayerReceives；未知原因允许归入 Unknown。[R07]

最终 `Publish` 会过滤：游戏须已就绪、角色 ID 非零、并且等于当前主角 ID。[R07] 所以这不是“每个 NPC 的关系变化都会通知”的通用事件。若游戏对不同对象的 `ChangeFriend` 使用不同 cId，哪些会被保留要实机查证，不能从字段名推定。

`GameEvents` 没有单独的 `RelationshipChanged`，而是 `TradeDetected` 等通道。[R11] 事件中也没有独立的 `FriendDelta`/`AffectionDelta` 或必填的关系目标 ID；`CharacterId` 与可空的 `CounterpartyId` 不足以自动保证某条双向关系的身份。[R09]

### 5.3 邮购的“成本补值”尤其不能冒充实测

玛姬邮购补丁读取商品价格，失败或非正数时尝试 `ActionGirlFriend.GetNeedAffection()`；随后开始 `GirlfriendShopPurchase`，阶段为 `OrderPlaced`，记录期望关系成本。另一入口 `UI_MailItem.SubmitMailItem` 从参数 `costValue` 观察同类成本。[R08]

`ObserveSemanticRelationshipCost` 将正成本保存为 `-Math.Abs(cost)`。`EndNpcTrade` 先合计已观察 delta 与外部延迟 delta；**合计为 0 且期望值非 0 时，直接使用期望值**。其状态记录含金钱等资源的 Before 基线，却没有 BeforeFriend/BeforeAffection；订单阶段还允许库存完全没变化时继续发布。[R07]

这合理表达了插件作者试图覆盖“先支付、后送货”的意图，但只证明该观察器会这样补充数据。它没有在这些行中核验邮购历史、对应关系前后差、或业务成功返回值。需要将如下三件事分开：

- 代码进入下单方法并正常返回；
- 插件发出了 `Completed + OrderPlaced` 观察；
- 原作实际扣除关系资源，且订单之后成功交付。

不得用前两项替代第三项。若方法正常返回但业务拒绝、或真实净变化为 0，期望值仍可能进入观察结果；这是应重点验证的风险，**本轮没有运行证据证明它已发生**。

### 5.4 关系条件被用于社区电话内容，但未扩展成通用关系模型

`JsonPhoneMod` 支持 `friendAtLeast` 与 `affectionAtLeast`：按角色 ID 找快照，再比较相应值和阈值；找不到返回 false。`characterId` 不允许负数，阈值可为任意 int；亲密条件也没有检查模式旗标。[R10]

这是社区内容的门槛判断，不能反向证明原作所有对话都这样判断。若未进入 Affection 模式的角色恰好返回 0，且配置门槛为 0，单凭当前比较式并不会因模式不符而拒绝。是否需要“模式存在 + 数值满足”的双条件是调用方设计问题。

## 6. 对 Z 的候选启发：保留因果，不压成一个好感值

以下是研究建议，未进入已批准规则；依据 K04/K09 和现有 Z 文档的认知/合作边界。

| 原作/社区启发 | Z 候选适配 | 必须保持的区别 |
|---|---|---|
| 当前状态与事件原因分别读 | 一边记录当前判断/约定，一边保存何事促成变化 | “答应过”不是“已执行”，话语不替代世界状态 |
| 人物关系能打开资源与行动 | 兑现约定后获得一次核验、接触或共同分工机会 | 收到帮助应有具体因果，不是泛化送礼累计满条 |
| 同一角色可能存在不同关系模式 | 明确友情/亲密表达的语境 | 友情与恋爱都可完成核心合作，不能把 Affection 门槛当统一通关钥匙 |
| 条件不满足时行动不可用 | 对具体请求校验理解、意愿、能力、许可和窗口 | **Z 理解事实、信任玩家、同意某计划、出口可用、迁移完成分别成立** |

可用的最小模型不是五条待刷满的数值条，而是可追溯的事实与承诺：Z 亲自核验了哪些事实；对玩家的哪些可靠性已有依据；哪项计划已同意及其条件；哪些世界权限真实存在；何事已经完成。玩家夸赞增加情感回应，不应自动形成事实理解或迁移授权。Z 明白真相仍可以拒绝离开；双方愿意合作仍可能缺少可执行出口。

这些边界由当前 [AI 与状态规格 v2 第 2、6 节](../../../docs/AI与状态规格-v2.md)和[核心系统 v2 第 4 节](../../../docs/核心系统与数值草案-v2.md)继续维护，并分开识别、兴趣、信任、关系类型和具体约定。本研究补充观察方法，不能据社区的两个整数删掉自主判断设计；旧 v1 不作为当前规模或时间规则的依据。
