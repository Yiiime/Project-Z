# 直播记忆接入方案（已确认）

目标是让同一存档里的 Z 在白天和直播间记得双方经历，并依照 moon-z-life 的设定逐步讲出自己的故事。弹幕打字和连麦走同一套记忆规则。玩家通过聊天触发，无需打开新面板。

## 玩家会遇到什么

| 记忆层 | 何时取用 | 直播表现 |
| --- | --- | --- |
| 当下 | 本场刚说过的话、正在点的歌、尚未回答的问题 | 玩家说「刚刚说的那首」，沿用现有会话上下文接话。 |
| 日常 | 近几天的真实互动与当前话题有关 | 玩家问「昨天点的哪首」，Z 能区分点过、播完、播放中断。 |
| 锚点 | 作者已写的成长经历与话题有关，当前章节允许讲述 | 提起家人或童年可带出一个细节，玩家追问才进一步展开。 |
| 共同 | 有双方参与的证据，关系和公开场合允许提及 | 白天约好晚上点歌，玩家进直播间提起约定，Z 能接上。私下约定默认只在私下续谈。 |
| 裂缝 | 命中设定里的剧情线索，章节、情绪、关系满足该条目条件 | 只露出该阶段允许的一处迟疑或矛盾。反复刷同一句弹幕不会跳过剧情。 |

相关且允许公开的日常经历可以由 Z 自然提起。深层条目遵循各自的揭示条件。没有可确认的历史时，Z 可以请玩家给一个线索。事实不清时保留不确定性，例如同一晚点过两首歌时先问指哪首。

## 数据从哪里来、到哪里去

1. **以当前游戏存档为准。** Unity 用已有的 worldId、当前加载的时间线 runId、游戏日和 checkpoint 打开 MemoryLab。直播 sessionId 标识本场。重连恢复同场，读旧档从该档的快照恢复并丢弃旧时间线迟到的回执。老存档没有直播经历时从空历史开始。
2. **记录真实事件。** 复用 Unity 存档的 outbox 和连续序号。真人发送消息、上麦后的最终转写、Z 实际说出的话、歌曲播放完成等事件使用稳定 ID，保留说话者、参与者、时间、公开范围和来源。玩家说喜欢某首歌可形成偏好，单次点歌只证明点过。歌曲准备成功、开始播放、播完分别记；重复回执只算一次。模拟观众的说法保留来源，不能据此推断玩家的偏好或 Z 的经历。长期记录只留必要文本和事实，不保存声音登记样本或通话音频。
3. **按话题取用。** 在 MemoryLab 增加面向直播的只读查询，从本存档中取出 Z 已知且可在当前场合披露的内容。优先考虑玩家明确追问、当前所指对象和最近相关互动，每轮初始上限三条。每条附证据 ID、说话者、日期、公开范围和可说的细节。主 Agent 与发言审阅器读取同一份依据；模拟观众只读已公开的直播事件。跨场召回本身不触发再次点歌、付费生成或播放。
4. **给深层记忆限定内容。** 依据 moon-z-life 的人物、剧情及异常设定维护有稳定 ID 的条目，标出适用章节、话题、场景、关系、情绪、公开范围，以及每阶段允许透露的细节。由当前存档提供条件，替换直播固定的 opening 阶段。缺少章节或关系依据时只发放能确认的内容；模型不能自行解锁。白天和夜间用同一个条目 ID 与讲述进度。
5. **说出口才推进。** 主 Agent 接收 Skill 的 z_internal.memories，可在生成发言时提出 z_state_update.memories，引用条目和本轮发言 ID。服务校验条件、可披露内容与状态顺序。首个细节实际说出后记 hinted，追问后说出获准的新细节记 unfolding，主要内容实际讲完记 unfolded。中断时只承认已经完整播出的细节；草稿、被审阅退回的句子或未播出的后半段均不推进。玩家提到一条往事本身也不推进 Z 的讲述进度。
6. **保证收播和保存兼容。** 直播中及时把已确认事件交给 Unity 写入存档待同步队列，按事件 ID 确认接收。收播时先保存末批事件及换天结果，再确认结束；同场重复通知只能换天一次。记忆服务离线时继续本场对话、告别和换天，未确认的持久事件留队重试，恢复后去重。下次开播前优先同步；证据未恢复时不猜测。

## 代码范围与交付顺序

沿用横版工程的 K03「白天准备改变夜间」和 K04「关系成为能力入口」。关系和实际经历决定可交流的内容，反复发弹幕不刷新任或消耗时段。

| 改动位置（均相对 unity-sideview） | 工作 |
| --- | --- |
| Tools/MemoryLab | 复用已有角色记忆、事件同步与快照，补直播事件、可披露内容查询、深层条目进度，以及白天 Z 对话读写同一进度。 |
| Assets/Seabreeze/UI/ZLive 与 Tools/live-service | 开播绑定存档和时间线，转交事件和播放回执；扩展主播请求校验、主持和审阅上下文、记忆条目与回归用例。 |
| 本地 Mac 试玩包 | 启动并检查配套的 MemoryLab 和直播服务，使用独立试玩存档。实测离线恢复和退出换天。 |

同一任务分支先提交跨场事实读写，再提交五层记忆与讲述进度，最后打一个包含两者的 Mac 包，更新草稿 PR。优先复用 MemoryGameController.Append、MemorySaveState 和现有读档入口。若必须改动「工程设置」以外的 Unity 主游戏脚本或设计文档，先列出具体文件和原因，另行确认。

## 试玩验收

- 第一天用连麦点歌并实际播完，收播、存档、重启。第二天改用文字问「昨天唱了哪首」，Z 能说对歌名和结果。同一用例改为只点未唱、播放中断，回答要随结果变化。
- 同一存档双向核对：白天谈起可公开的约定，晚上能接续；夜里确实发生的事情，第二天白天 Z 也能提起。白天的私人信息不进入模拟观众上下文，也不由 Z 在直播中公开。
- 用一个有资料依据的锚点连续追问，验证三步进度随实际播出保存，隔天能从已讲内容接续。中途打断、闭麦或退出时，以实际播出回执为准。
- 用同一条裂缝在剧情条件未满足和已满足的存档分别验证，检查角色说出的细节、审阅器获得的依据和观众可见内容。验证用的后期存档独立于玩家试玩档。
- 换新档、读回点歌前的旧档、断网重连及服务重启后，没有串档、重复写入或重复换天。旧版存档能直接启动，原有五秒声音登记和退出流程仍可玩。
