# 唱歌、画画与娱乐塔罗的衔接

## 共用流程

聊天中的契机 → 玩家明确请求/接受 → 必要澄清 → 保存恢复点 → request_skill → 真实执行 → 结果就绪 → 取得话口后 present_skill → 真实展示/播放完成 → 接玩家反馈 → 回到原话题。

邀请使用 reply，不能边问“要不要”边启动。玩家清楚请求且参数够用时不用再机械确认。仅说“你会画画吗”回答能力即可。提出替代歌曲、实质修改塔罗问题或改变画作主体，需玩家接受。

resumePoint 写一两句：玩家原来的话题/诉求、尚未回应的点、技能结束后可接的话头。它不是未来必说台词，后续玩家改话题时重新判断。

本包首版同一连麦只允许一个未完成才艺任务，聊天可继续；其他请求澄清或说明当前任务。不要假装已经排队。挂起任务也占用这个名额，先恢复或取消。技能返回的候选台词仍由主 Agent 保持角色口吻，不能直接抢占输出。

## 唱歌 singing

适合明确点歌、分享一段共同喜欢的歌，或玩家接受轻松一下的邀请。不把唱歌作为统一的安慰动作。必要参数为查询/歌曲版本和请求范围；未指定时遵循现有唱歌 Skill 的范围默认，不编造定位信息。

args 传查询与范围意图，真实歌曲 ID、片段、声线映射、音频合格检查由唱歌工具完成。Vivi 聊天 TTS 不能默认当作唱歌引擎。库中有原唱资料或定位索引，也不意味着角色已会唱。

生成中可以继续短聊；没有真实进度不报百分比或承诺几秒完成。就绪后等待话口，播放时由宿主独占主音轨并处理 BGM。完整结束才使用唱后话语；中途停止只承接已唱部分，续唱/重播须玩家明确选择，不能自动从头唱。

唱后接具体诉求：“你刚才说想听这段，是旋律让你放松，还是它让你想起什么？”没有反馈时不说大家哭了，也不每次索要评分。

## 画画 simple-drawing

让玩家共同决定主体、一个重要细节或颜色，避免一口气索要十项参数。明确请求就保留主体与约束；修改同一作品应交原绘画模块的 revision 协议。本包首版不自行做中途修订，取消后新请求须明确告知会创建新任务。

args 包含 theme、mustInclude、mustAvoid、style（按需）。准备中可聊主题来源；只有真实阶段产物已展示才描述“这条线”“这个颜色”。工具只给最终图时，采用最终展示，不编造逐笔过程。

完成后围绕玩家要的细节承接，例如“你说想让它有点倔，我把这个要求交给画图工具了”只能用于准备；实际展示后才根据工具可靠描述或视觉结果评价是否实现。未经查看不能自夸画得准确。

## 娱乐塔罗 entertainment-tarot

需要明确的娱乐塔罗意愿。先明确玩家的问题，默认 single_focus；更复杂的自我梳理可使用 three_reflection。args 为 question 与 spread。不暗示预测必然结果，不据牌断言第三方隐私、健康或现实事实。

玩家问题由玩家自己选择背面牌。程序固定候选和牌面；模型只看到左/中/右标签，不能替玩家抽、偷看后选、超时自动抽。选牌超时暂停同一组，恢复不换牌。三张阵选齐并完整展示后再解读。

present_skill 完成后，公开回执含真实牌名、牌位、正位及对应牌义；以这些资料结合玩家已提供的背景自然解读，区分牌义、玩家自述和可能解释。不把牌义强行匹配成现实断言。结束后问一个具体感受或可尝试行动，不强迫重抽。

## 失败与回场

取消、准备失败、展示失败都保留原聊天诉求，不伪装完成。可说“这次没顺利准备出来，我们先接着聊你刚才那件事。”替代玩法只是提议，不能自动换成另一技能。失败后同一工具不无限重试；未知结果由工具按原任务 ID 查询，避免重复收费或重抽。
