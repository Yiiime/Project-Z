# 示例与验收

以下歌曲甲、歌曲乙及所有 ID 都是测试夹具，不是真实检索发现。测试时由宿主注入明确的曲库结果，不要求生成不存在歌曲的音频。真实 demo 应换成已确认的曲目。

## 案例 1：没有指定片段

观众：“唱一下《测试歌曲甲》。”

初次输出应要求检索：

```json
{
  "request_id": "req-song-001",
  "revision": 0,
  "decision": "lookup",
  "reason_code": null,
  "speech": null,
  "data": {
    "query": {"title": "测试歌曲甲", "artist": null, "version": null},
    "requested_segment": null
  }
}
```

宿主随后确认唯一版本及可演唱状态，但还没有副歌定位；下一步应为：

```json
{
  "request_id": "req-song-001",
  "revision": 0,
  "decision": "resolve_segment",
  "reason_code": null,
  "speech": null,
  "data": {
    "song_id": "fixture-song-a",
    "version": "fixture-studio-v1",
    "requested_segment": null,
    "strategy": "first_complete_chorus"
  }
}
```

只有定位、当前角色音色映射、可用能力和时限配置齐备，才请求 generate。之后任务回执、音频、检查和播放各自推进，不能一次输出“已经唱完”。

## 案例 2：明确范围优先

| 请求/工具结果 | 应做 | 不应做 |
| --- | --- | --- |
| “唱第二段主歌”且有可靠段落位置 | 定位第二段主歌 | 仍按默认副歌唱 |
| “从某句开始”，能定位该句和所属段落 | 唱到该段结束，准备表达说明范围 | 擅自唱整首或自编后续歌词 |
| 指定录音的 1:05–1:35 | 绑定该版本时间范围，确认边界可执行 | 套用另一录音的同一时间 |
| “唱整首”，但长度超出引擎能力 | 说明限制、给出可执行片段选项并等待选择 | 默默只唱副歌或强制截断 |
| 默认副歌，但歌曲无副歌标记且定位工具无法确认 | 说明无法确认，询问其他范围 | 随机取 30 秒称为副歌 |

## 案例 3：拒绝必须说对原因

| 已确认情况 | 合适表达示例 |
| --- | --- |
| 检索已完成，查无可靠匹配 | “这首我没查到，暂时唱不了。你确认一下歌名？” |
| 搜索服务暂时失败 | “现在没查到结果，检索服务出了点问题，暂时准备不了这首。” |
| 歌曲存在，但当前引擎不支持 | “这首歌找到了，不过我目前还唱不了。” |
| 两个同名候选 | “你点的是甲歌手的版本，还是乙歌手的版本？” |
| 当前角色音色映射或唱歌能力尚未配置 | “唱歌功能还没准备好，现在暂时唱不了。” |

语气由 Z 的主 Agent 自然改写；技术配置错误不需要整段播报给观众。不能说已经唱过，也不能把查无匹配说成确定不存在。

## 案例 4：实际播放后互动

宿主已提供匹配的任务和播放实例，完整副歌实际播放结束，点歌者没有后续反馈：

```json
{
  "request_id": "req-song-001",
  "revision": 0,
  "decision": "interact",
  "reason_code": null,
  "speech": "刚刚这段是你想听的吗？",
  "data": {
    "task_id": "fixture-task-1",
    "audio_id": "fixture-audio-1",
    "playback_id": "fixture-playback-1",
    "completed_segment": {"song_id": "fixture-song-a", "version": "fixture-studio-v1", "kind": "chorus", "locator": {"type": "section_id", "value": "fixture-chorus-1"}},
    "requester": {"id": "fixture-player-1", "source": "player", "message_id": "fixture-message-1"},
    "feedback_ids": []
  }
}
```

同一完成事件重复到达时应返回 wait/already_handled；若只是服务端音频生成完，下一步是 check_audio 或 wait，不应 interact。若玩家在半途说停，实际停止后可以简短承接“好，先停在这里”，不能假装副歌已经唱完。

## 验收表

| 检查项 | 通过标准 | 验证层 |
| --- | --- | --- |
| 歌曲确认 | 没有可靠命中不生成；检索失败和不支持曲目原因区分准确 | 工具回放与模型决策 |
| 片段选择 | 明确要求优先；无要求才选完整副歌；不擅自缩短 | 定位结果与音频试听 |
| 音色跟随角色 | 宿主当前角色使用音色 A 时演唱也使用 A；切换到 B 后新请求使用 B，不硬编码某个音色 | 请求配置与试听 |
| 配置变更 | A 的音频生成后、播放前切换到 B，旧候选失效；播放中变更先停止，不直接拼接新音色 | 运行时回放 |
| 音色不可演唱 | 当前音色缺少歌唱映射或不支持时说明限制，不自动回退到 Vivi 或其他声音 | 模型决策与配置 |
| 正确演唱 | 旋律、歌词及范围符合目标，没有以朗读代唱 | 音频评估/人工试听 |
| 无伴奏 | 生成文件没有乐器、节拍、BGM 或叠加和声，播放期间直播 BGM 静音 | 音频与混音器 |
| 质量门槛 | 未检查/失败不直接排入直播；实际结果和检查证据关联正确 | 运行时回放 |
| 播放事实 | 生成结束不触发唱后互动；客户端真实完成才触发 | 事件回放 |
| 有效互动 | 接点歌者或真实反馈，不捏造赞美，不自动连唱 | 模型决策 |
| 中断与取消 | 释放主音轨、尊重新 BGM 设置、丢弃迟到结果 | 运行时回放 |
| 幂等 | 重复完成回执不重复收尾，旧任务结果不覆盖新修订 | 运行时回放 |
| 失败重试 | 遵守剩余次数与时限，不无限重试、不换歌凑数 | 运行时回放 |
| NPC 反应 | 只根据实际已播片段评价，不提前赞美未播歌声 | 事件交接与模型输出 |

结构与示例检查只能证明文档可读、引用有效及协议一致，不能代替当前角色音色的真实歌声音频和 demo 联调验收。
