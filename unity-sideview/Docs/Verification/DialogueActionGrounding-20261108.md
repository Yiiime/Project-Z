# 对话虚构递菜单：本地排查与验证

用户截图中，李庭先说“喏，菜单”，玩家表示没看到后又说“菜单都递到你手边了”。当前本地角色行动目录没有展示菜单或交付物品的动作，Unity 的 MemoryActionExecutor 只消费待执行的移动命令。台词通过 JSON Schema 并不证明物理行为发生。

后台已有原话与事实区分：上述话语保存为 claim/hearsay，不会直接生成物品或任务完成。但模型仍可能把自己的原话当成完成依据。另一个容易混淆的点是 `previous_action_result.status=succeeded` 也用于 wait、消息送达和任务状态提交，不能只看 succeeded 就认定物理工作已完成。

## 本地改动

- `Engine.context` 增加 `character_state.execution_evidence`：从本人、当前时间线的真实行动回执生成最近六项只读视图，包含动作类型、目标、成功/失败和结果；不从台词提炼“已执行动作”。新回执保存实际游戏时间，未来、旧时间线、其他人的回执不进入视图。
- `previous_action_result` 增加 `action_type/effect_scope`，区分等待未改变世界、消息送达、任务状态提交、等待物理执行及执行结果。保留既有 status 值以兼容客户端。
- 共用行为、记忆、接口说明与岛上模型提示补充事实边界：职业知识不等于本轮已制作/递物，自己的原话不能自证；玩家指出未看到时应纠正，而不是坚持或虚构新位置。没有执行能力时只提供当前能兑现的口头帮助。
- 更新单文件 `docs/Project-Z-NPC全链路.schema.json`，保留三部分输出格式，不新增菜单或道具玩法，也不改变前端样式。

## 验证结果与限制

`npm test`：59 项通过，其中新增回归覆盖虚构菜单原话不生成执行证据、wait成功不等于交付、真实移动成功及读档、角色隔离、失败和未来/畸形回执。首次沙箱运行的 11 个 HTTP 用例因本机 listen EPERM 失败，在允许本机临时端口的环境重新运行后全部通过。

单文件 Schema：156 个定义可编译，85 正例、15 反例通过。此处证明结构与状态链路，不证明模型不会说错。

使用项目已配置的真实模型，在独立内存世界进行了三轮、每轮四个菜单/制作场景测试，没有操作玩家真实存档。最后一轮单次约 0.9—2.3 秒。模型能在被指出问题后承认“说早了、菜单没递”，但仍会生成“没印菜单”及未有执行动作的制作承诺。这些仍属未有依据的表述，不能把本轮结果报告为语义问题已彻底修复。补提示词与执行证据是防护措施；JSON Schema 不能独立校验自然语言事实。

仅查看了正在运行的 Unity 游戏窗口，未更换其后端、重启进程、移动玩家或进行该修订的 Unity 对话试玩。当前游戏是否使用本地新提示未经验证。未新增真正可看的菜单，也未实现递物；因此不存在“现在应能看见菜单”的交付结论。

要实现真正看菜单，需要内容来源、后台可选的展示/交付动作、客户端用现有样式实际显示，以及呈现/交付回执共同接通；在这些能力不存在时，NPC 不应声称完成。自然语言与动作的一致性还需要进一步校验，不应以统一 JSON 字段已经通过为完成标准。

研究参考：K04“关系成为能力入口”保留帮助要有可用结果，K06“能力来源嵌入世界”区分会做、可执行与效果；本次不新增研究资料中的其它玩法。
