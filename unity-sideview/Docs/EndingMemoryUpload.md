# 第七晚：上传记忆与自动更新结局

## 使用

双击 `试玩第七晚结局.command`，进入完整游戏，点击左下角「第七晚结局」。原生结局页顶部现在有：

- **上传 / 更换记忆文件**：打开属于当前存档的本机上传页。
- **以本局经历重新演出**：按当前文件和实际经历重新生成。
- **看上次结局**：回看上一份结局，再返回当前结局。

上传页支持选择文件或拖入文件。TXT、Markdown 会通过当前游戏配置的在线模型整理日期、段落标题和 Z 的知情范围，原文保留。JSON 支持本页下载的记忆格式。预览确认后点「使用这份记忆，更新结局」，服务立即开始生成；游戏中的结局页约每两秒检查一次更新，显示生成进度和新结果。

TXT / Markdown 上限 200KB、60,000字、40个原文块；JSON 上限 500KB、200条经历。上传失败、格式错误或解析不完整不会替换原文件。

## 记忆与结果

每次重新上传替换的是这份存档的预置经历。本局之后真正说出、看见或收到，且允许向玩家回望的经历仍由原有游戏事件系统补充。其他 NPC 私聊不会进入结局；作者侧未告知 Z 的内容保留在上传原文中，但不进入 Z 的回望。

上传文件、原文和版本保存在当前世界的 `endingMemorySource`，随 checkpoint 和游戏存档恢复。文件不会变成已完成任务、已交付物品或真实登船成功。离开意愿和实际离岛结果仍分别结算。

确认文件会自动发起同一模型连接下的结局生成，先形成 Z 的选择，再分批回望全部知情经历。原生界面通过 `/api/game/ending-source` 读取进度和结果。文件版本或实际经历更新后，旧的未完成生成不能写回；当前页会按最新经历重新生成。

旧结果仍保存在本局 checkpoint 的结局快照中，原生页提供上一份结果的回看。上限沿用原有的最近5份结局。下载按钮导出上传的预置记忆，不把实时游戏事件再次写成预置记忆，避免备份重传时重复添加本局经历。

## 接口与生命周期

- 原生游戏调用 `POST /api/game/ending-upload/open` 创建只属于当前 `worldId/runId/epoch` 的上传窗口。
- 窗口凭据只在地址 fragment 中，30分钟有效；切换存档、读档或重开后的旧窗口失效。
- `POST /api/ending-upload/import` 在线整理文件，返回待确认的原文预览。
- `POST /api/ending-upload/use` 校验预览和文件版本，保存当前存档的来源并自动生成。
- `GET /api/ending-upload/status` 显示进度和可读结局；`GET /api/ending-upload/export` 下载已上传记忆。
- `POST /api/game/ending-source` 向原生游戏提供当前来源、进度、结局和上次结局，并同步 checkpoint。

多人窗口的确认使用来源版本校验，不能静默覆盖其他窗口已更新的文件。网页不返回 Action/Info、其他人物的私有状态或供应商密钥。

启动器会检查服务是否包含上传功能。如果旧试玩服务占用了默认端口，会选择空闲的本机端口启动新版服务，不终止旧进程。模型连接仍沿用原有配置。

## 研究依据

- K04：角色关系与判断来自具体经历，上传材料与实际经历一起影响选择。
- K11：重试和重新上传保留旧结果，切换/恢复存档后旧请求不能覆盖新状态。
- K12：选择、准备、任务完成与真正逃离分别记录，文件不能制造执行成功。

## 验证范围

MemoryLab 91项回归及原文件/结局14项回归通过。新增测试覆盖原文、知情隔离、世界隔离、重传、冲突、历史快照、checkpoint恢复、新事件、旧生成失效，以及超过原40条限制的完整JSON分批回望。

Unity 6000.3.27f1构建成功。隔离的原生整局验收通过：真实HUD入口、上传按钮创建窗口、文件解析/确认接口、游戏自动呈现新结局、上次结局回看、返回探索、手机回看及读档恢复。

验收使用模型替身与临时存档，没有读取真实玩家记忆或调用付费供应商。浏览器扩展限制了自动化文件选择，文件提交使用真实游戏按钮创建的上传会话调用与网页相同的接口。普通用户在浏览器中选文件不依赖此自动化权限。

## 上传后仍显示旧结局的修复（2026-11-13）

实际排查发现两项问题：直接打开应用时没有 `-memoryService` 参数，应用使用4330默认地址，可能连到另一个旧协议服务，而上传页属于启动器的新版服务；旧存档中的结局快照没有 `contextRevision`，界面首次检查来源时错误地将新文件版本作为旧快照的基准，未刷新。

启动器现在记录验证过的端点到本机 `~/.project-z/ending-demo/game-service.json`，仅独立结局Demo应用在缺少命令行参数时读取，仍限制为本机HTTP。显式参数优先。启动器要求健康检查 `endingSourceRefresh >= 4`，旧实例占用端口时启动兼容的新服务。新版使用独立的 `ending-runtime-v4.sqlite`，从游戏checkpoint恢复，不与仍运行的旧端口共写同一个数据库。

旧快照首次读取来源时视为需要核对的历史结果，按当前上传文件重新生成；手动重新演出使用新请求ID。每次生成固定开始时的知情记忆快照，期间岛民新增事件不打断这次生成，完成后提示“本局有新变化，可重新演出”。重新上传、更换存档或时间线才取消旧请求，防止持续发生的岛民事件使结局永远无法生成。旧文件失效时网页显示原因，保留已上传文件。

修复验收：92项MemoryLab测试、14项文件测试，Unity6000.3.27f1构建及隔离原生旧快照自动刷新、全量回望、返回、手机回看、存档读取闭环通过。经典原生结局界面仍为默认；早期电影化布局仅通过显式 `-endingCinematicPreview` 试作参数启用，完整终章方案仍待制作。
