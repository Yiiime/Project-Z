# 每个 NPC 的独立运行记录

日期：2026-11-12。当前实现面向 `unity-sideview/` 的八位角色，使用同一个 SQLite 服务，按世界、存档时间线和角色隔离运行状态与记录。

## 行为

每个 NPC 拥有自己的环境快照、上报序号、确认进度和追加式运行日志。环境包括实际场景、地点、坐标、移动状态、动作与会话。日志串起收到的事件、决策输入、提案、实际提交、任务处理状态和行动结果；生成提案不等于行动已经执行。

Unity 的 `NpcRuntimeReporter` 在角色初始化、移动开始、实际到达、受阻、中断、等待、地点变化、动作状态变化、会话打开/关闭和场景卸载时采集位置。坐标每帧变化不产生逐帧日志；每次决策请求仍会附带当时的最新坐标。地点沿用已有导航锚点，未绑定节点的场景使用 `scene:<场景ID>` 和实际场景名称，不能被当作主街或已完成某条路线。地点区域的精确门内/门外判定没有在本次实现。

运行上报使用每角色独立的持久队列和序号，不占用原有对白/剧情事件序号。NPC A 的运行队列不会阻塞 NPC B 生成回复。原有对白/剧情事件队列继续有序投递；与某 NPC 有关的实际发言回执优先于该角色后续的位置变化，防止窗口关闭的快照抢先使已展示的台词无法提交。

运行快照更新环境，不写入长期记忆、不唤醒所有角色、不推进游戏时间。事件仍按实际接收者进入个人日志，NPC 的模型上下文不读取其他角色的运行日志。共享日志查看页面是本机开发观察入口。

同一地点的坐标小变化不作废回复。地点、移动状态、动作或会话变化会增加该角色的环境版本；生成完成与提案提交均检查版本，旧环境的结果不能落到新状态。已承诺行动保留原有路线状态，实际位置另存在环境里，只有合法执行回执能推进或完成动作。

## 存档与恢复

运行日志与上报回执随当前世界存档一起保存，压缩到 `npcRuntimeArchive`（deflate-raw/base64），避免把重复环境/决策数据直接膨胀到 HTTP 快照中。服务端保留完整可分页查询的记录；存档恢复会重新绑定时间线、恢复本人序号、移除存档之后的日志与回执。解压上限为 64 MiB。

旧版 V2 存档没有此归档时，保留原有角色/记忆/任务状态，从恢复时开始建立运行日志，不补造过去的决策。普通断线重试沿用稳定事件 ID；同一记录相同内容只确认一次，序号跳跃、同 ID 内容冲突和旧运行请求会被拒绝。

## 本地查看

重启使用本分支源码的 MemoryLab 服务后，打开 `http://127.0.0.1:<端口>/runtimes`。选择世界和角色，可查看当前环境、待处理任务和逐条时间线，展开条目看来源与详情。切换角色不会混入其他角色的记录。现有 `/memories` 继续查看个人记忆。

接口沿用本机 Host/Origin 与请求身份校验：

| 接口 | 用途 |
|---|---|
| `POST /api/game/runtime/sync` | 带 worldId/runId 的单个 NPC 有序环境上报 |
| `POST /api/game/runtime` | 带 actorId、after、limit 的本人运行记录；limit 为 1–200 |
| `GET /api/debug/runtimes` | 本机观察页面使用；需要 X-Test-Token 或 X-Z-Memory |

日志的 `runtime_seq` 是各 NPC 的运行时间线序号；上报的 `seq` 和角色的 `runtime_input_seq` 是宿主投递序号，两者分开。分页游标仅用于当前时间线，读档后应刷新页面重新查询。
