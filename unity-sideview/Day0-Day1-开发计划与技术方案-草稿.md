# Day0 至 Day1 开发计划与技术方案草稿

更新：2026-11-13。状态：已实现的开发草稿，正在进行本地验收。任务分支 `task/daiziqing2-sys/engineering-story-events-1113-0052`，草稿 PR #62。

本版以用户最新四项要求替代上一版的固定对白、预设迎新任务和定时直播方案：人物按照各自人设 Skill 自然说话；AI 根据现场实时生成任务；主 Agent 自己决定并调用两场直播所需的工具；修改保留在草稿分支，用户本地验收明确确认后才能进入 main。

## 1. 本轮体验边界

完成以下连续体验：已有首页 → 玩家输入名字 → 世界观视频接入口 → 第1000场直播与七天登岛邀请 → 码头见 Z → 自主跟随 Z 去市民广场 → 下午在榕树下认识所有到场角色 → 烟花视频占位 → 任选一位居民接受一项 AI 实时生成的迎新小任务 → 完成后由主 Agent 安排首夜直播 → 当日回顾、自然互动及主播自主安排的歌曲。

用户已确定的边界：

- 世界观视频1暂不制作，未配置时不阻塞流程。
- 烟花视频2保留空资源接入口，先完成前后场景承接；不把占位记成真实视频播放完成。
- 广场到场名单为晴野、留洋、正义、李庭、阿星、周伯伯、Z，以及玩家。认识目标为七位角色各完成一轮互动，梨园不在其中。
- 认识任务期间玩家不能离开区域，完成后解除。码头单聊不替代广场与 Z 的一轮交流。
- 烟花后只需完成一项迎新小任务，目标体验约2至3分钟；可以拒绝、换人，不需要清空全员任务。
- 开场直播只有虚拟观众；首夜由 Z 主持，其余六位到场居民可以参与直播互动，梨园不参与。
- 首夜开播有手机弹出、直播按钮高亮与1秒震动，然后进入直播界面。
- 开场约30秒是内容节奏目标；玩家考虑时间、网络等待不作为失败或自动确认条件。
- 本轮不追加后期逃离、公司真相、全游戏片尾或完整七天内容。

## 2. 自主决定与游戏事实的分工

| 负责方 | 职责 | 不代替谁决定 |
| --- | --- | --- |
| 主 Agent | 理解当前体验目标，选择何时开播、抽奖、邀请、转场、介绍新朋友、回顾和调用唱歌；根据执行结果继续安排 | 不直接改存档、发奖、伪造动作完成或替玩家接受邀请 |
| 角色 Agent 与人设 Skill | 结合人物关系、本人已知事实、当前位置和玩家原话生成对白；决定走近谁、聊什么、是否协作；生成符合现场条件的任务提案 | 不预读别人的私聊，不创造不存在的道具、地点或能力 |
| 游戏执行器 | 提供当前可用能力；验证工具调用；执行移动、抽奖展示、视频、任务动作和直播界面；保存实际结果 | 不编写角色台词，不把预设任务换几个名字冒充实时生成 |
| 玩家 | 选择名字、是否登岛、如何回应、是否接受任务、怎样移动和完成行动 | Agent 不代点确认，不把沉默当同意 |

用户确定的路线、七天邀请、指定角色名单和真实完成条件是本轮世界规则。任务标题、描述、交流方式、具体小任务与主持表达由 AI 现场生成；这些世界规则不意味着预写对白或预写七个任务。

## 4. 对话与直播全部使用自然生成

### 4.1 提供情境，不提供待朗读脚本

角色请求包含：本人的人设与交流规则、可知事实、当前互动对象、玩家显示名、正在发生的事情、当前可用工具、最近实际对话和本轮体验目标。不提供固定开场段落、固定介绍句或按秒排列的发言清单。

开场直播的情境说明表达以下事实和意图：这是第1000场直播；有一个七天登岛体验名额；希望新观众迅速感到被关注；抽奖结果由游戏工具产生；玩家接受后与其约定岛上见面。主 Agent 自己组织介绍、接弹幕、决定开奖和发邀请。

码头交流的情境说明是：Z 来接刚接受邀请的玩家；两人首次线下见面；Z 想自然介绍自己在岛上的生活，并邀请玩家去榕树下认识朋友。玩家可以实际输入回应，不自动替玩家说预写的一句。

广场介绍围绕本人职业、此刻在做的事和对新朋友的反应展开。Z 先实际向在场者介绍玩家姓名，各角色再依据获知事件称呼玩家。

### 4.2 主动开口、完整交流和语音

- 进入码头时主动请求 Z 的第一轮回应；靠近居民并交互时，由该居民先自然开口。
- “已聊过”需要 NPC 首轮实际展示、玩家实际回应、NPC 实际承接；打开窗口或生成出未展示的文本不计入。
- 接受任务或邀请必须有玩家点击或经当前语境确认的明确意图，不靠单个关键词判断。
- 台词沿用现有 TTS、字幕与口型链路；模型生成和语音播放各自有状态与取消归属。
- 已实际说出的内容保存为本局历史，重进不会变成另一段经历。缓存本局已生成内容用于恢复，不是全玩家共用固定台词。
- 服务异常使用界面状态、重试和可恢复退出；不塞一套角色固定对白冒充 AI。字幕可承接已生成但语音失败的真实内容。

## 5. AI 实时生成迎新任务

### 5.1 能力目录与任务生成

AI 读取当前场景的实际能力目录，包括可交互人物、可到达位置、真实存在且可使用的物件、玩家持有物、拍照及展示能力、当前人物占用和时段。能力目录由执行器提供。

AI 生成新的任务名称、提出理由、描述、步骤及目标对象，不从“晴野送花、李庭送饮料”等预写任务表中抽取。不同玩家、不同交谈、不同现场可以得到不同任务。

任务只能组合现有可执行动作。例如走到真实位置、和实际在场的人交流、拍照并展示、在已支持的物件之间交付。未接入对应执行能力时，不向 AI 声明可以搬箱子、维修、凭空取物或生成新人物。

生成结果是一份结构化提案，包含发起人、任务文案、步骤、实际目标ID、依赖关系和完成所需证据。任务稳定ID由宿主生成。步骤量保持在首晚可完成的小规模，预计2至3分钟；预计时间不是隐藏倒计时。

### 5.2 先检查能否完成，再向玩家提出

检查包括：

1. 发起人存在，且确实与玩家处于当前对话中。
2. 所用动作已由客户端声明支持，所有目标可定位、可到达、可交互。
3. 前置与步骤没有循环依赖，没有要求先离开尚未解锁的区域。
4. 涉及他人协作时，需要对方实际同意；不能将模型替别人答应当成任务前提已满足。
5. 与当前已接任务不冲突，不把后期秘密、逃离权限或无限奖励附赠给迎新任务。
6. 同一时刻最多有一项有效迎新任务。拒绝后允许根据新交谈重新生成，不能立刻反复塞回原任务。

无效提案将具体缺口反馈给生成方重新考虑；多次失败时保持聊天与换人机会，界面如实说明任务暂未准备好，不发布无法完成的卡片。

### 5.3 扩展现有任务系统

动态任务定义按 world/save 隔离保存，不能放进进程级全局定义表导致别的玩家看到同一任务。任务定义、接受状态、步骤进度和回执一起进入 checkpoint 与恢复流程。

现有 `TaskEngine` 保留静态任务兼容，增加本局动态定义。Unity 的任务卡和手机任务页需要能读取 checkpoint 中的动态定义，不能因为任务不在静态 JSON 内就直接丢弃。

完成由真实动作回执确认，AI 可以解释结果和提出下一步，不能直接把任务标成完成。重复回执不得重复完成；读档恢复同一任务；旧会话或旧NPC的迟到响应不得在新对话发布任务。

本轮首夜只要求完成一项动态迎新任务。现有长线任务保留，按首日阶段控制可见性，不自动成为开播前置。

## 6. 主 Agent 自己调用两场直播

### 6.1 以事件唤醒主 Agent

页面或阶段完成后，游戏提交“玩家姓名已确认”“欢迎任务已实际完成”等事实，唤醒主 Agent，并提供此时允许调用的工具。主 Agent 根据当前目标和现场决定下一步。

不再由计时器到12秒弹邀请，也不在完成任务的一瞬间直接无条件开直播。主 Agent 可以先接完玩家的话、处理当前占用，再调用开播工具。硬性前置不满足时，宿主返回原因供其重新安排。

拟增加的能力包括打开当前允许的直播、发起剧情抽奖、展示登岛邀请、请求合法转场、提出一起前往某处、发布已验证的动态任务。名称以现有工具注册规范确定。这些是可用能力，不是必须逐项照念的节目单。

每次工具调用携带请求ID、世界ID、运行ID、当前阶段版本和前置事实。工具调用是提案；宿主实际执行后的回执才推进状态。自然语言说“开播了”本身不能打开页面或结算日期。

### 6.2 开场直播

- 主 Agent 知道本场目的和约30秒的节奏目标，自行选择开场措辞、接话长度与开奖时机。
- 抽奖是本次故事设定中的中奖事件，游戏工具返回当前玩家获邀的真实结果；Z 在拿到结果后再自然公布，不凭生成台词提前制造中奖事实。
- 观众为虚拟直播观众，岛民不在开场参与列表，也不会因界面隐藏而继续在后台收到直播记忆。
- 玩家接受邀请后，主 Agent 完成自然的见面约定；以实际发言完成和转场回执衔接码头，不强制某一句字面台词。
- 玩家等待、提出问题或暂不接受时，主 Agent 根据语境回应；不让“约30秒”变成强行替玩家确认。

### 6.3 首夜直播

- 动态迎新任务完成是开播资格事件；主 Agent 决定合适时机并调用开播。
- 工具执行后出现手机、高亮及1秒震动，再打开直播页。1秒指视觉反馈，不承诺网络和语音生成都在1秒内完成。
- 向主 Agent 提供玩家姓名、已认识角色、实际经历与已完成任务的可公开摘要，由它自己回顾和介绍新朋友。
- 唱歌使用现有才艺工具，由主 Agent 根据当天情绪和交流自行选歌、准备、安排播放。《晚安》是用户给出的方向示例，不作为固定歌曲或开播后必播步骤。
- 六位居民可以参与，但每个人不必按顺序发一句。人设、已知事实和互动意愿决定是否说话。
- 开场与首夜使用不同直播用途标记、会话和回执归属。开场退出不切天，首夜实际收播才按既有机制结算一次。

## 7. 人物、名字与场景状态

### 7.1 玩家名字

姓名弹窗沿用已有首页风格。稳定 playerId 与 displayName 分离，姓名按存档保存，支持中文与输入法；统一处理长度、空白和富文本控制内容。

姓名作为事实进入 Agent 上下文和直播展示，不拼接为系统指令。传播顺序为：玩家确认 → Z 在开场获知 → 码头识别 → Z 在广场实际介绍 → 在场居民获知 → 首夜公开介绍。知道名字不等于知道玩家的私聊。

### 7.2 Z 带路

Z 的自然邀请被玩家接受后，形成去广场的行动目标。使用现有移动组件走码头、公共街、广场；玩家自主移动。Z 可在合适位置等待落后的玩家，不接管玩家角色。

场景切换保存 Z 的实际路线阶段和位置。目标场景在遮罩期间恢复角色，不重复生成、不在玩家眼前瞬移。读档和玩家绕路都有可恢复的集合位置。

### 7.3 榕树聚会

到场名单使用本轮七人配置，不修改全局八人名册。角色在区域内自由活动；给当前人设与关系系统提供区域内可达点和交流对象。

晴野与留洋的亲近来自已有关系与共同兴趣，不能写成永远绑定的站位。普通玩家单聊只占用目标人物，其他人仍可活动。转场、视频等场面操作才使用必要的全场锁。

区域限制统一落在移动入口，覆盖边界出口、地图跳转和建筑入口，不能只禁用一个按钮。七人介绍完成后解除限制，并在当前对话安全结束后承接烟花占位。

## 8. 存档、异常与恢复

扩展既有 FirstDayState，保存剧情版本、阶段、生成内容归属、认识名单、邀请状态、动态任务引用、行动回执与两场直播会话标记。Day0 是序章标记，保留现有 day >= 1 的协议约束。

旧阶段枚举不能随意插入重排。为旧首日中途档、已完成档及没有首日字段的历史档提供明确迁移；不让老档突然重新抽奖，也不删除已经完成的真实任务。

所有异步结果绑定存档、运行、人物、对话和阶段版本。暂停、换场景、换人、重开或读档后，旧结果失效；已经展示的对白和已经执行的动作按稳定事件恢复。

语音失败可以展示已生成的字幕；模型不可用时保留当前现场和进度，提供重试。没有模型生成时不使用角色固定台词兜底，未接通服务也不声称 AI 验收通过。

视频占位、跳过和真实播放完成分别保存。恢复不能把缺失视频当作解码成功，也不能让空视频留下永久黑屏或输入锁。

## 9. 实施顺序与验收

| 阶段 | 开发内容 | 验收标准 |
| --- | --- | --- |
| A | Agent职责、能力注册、动态任务与状态协议 | 不含固定角色对白与七人预设任务表；错误工具调用有明确拒绝结果 |
| B | 姓名、首日状态与旧档兼容 | 新局姓名贯通；旧档可继续；重开与换档不串名字、任务或生成请求 |
| C | 主 Agent 开场调度与码头欢迎 | 自然生成千场活动、抽奖结果后的邀请及欢迎；虚拟观众正确；玩家明确接受才登岛 |
| D | Z带路、区域活动与七人介绍 | 真正移动、人物可交互、关系驱动；各种离开入口均遵守区域限制；取消不误计数 |
| E | 动态迎新任务 | 不依赖角色固定任务表；生成目标均可执行；真实动作完成；拒绝换人、重复回执和读档正常 |
| F | 主 Agent 首夜直播与歌曲 | 任务结果唤醒后自主调用开播；介绍名字和真实今日经历；正确名单；主 Agent 调用现有唱歌工具 |
| G | 本地全流程试玩与草稿交付 | 从首页贯通首夜收播；无卡死、虚构完成、重复切天或私聊串档；等待用户本地确认 |

验证分为：

1. `tools/team/z check` 与对应 MemoryLab、live-service 自动化测试。新增测试重点是动态定义的存档隔离、目标可执行性、回执去重和主 Agent 工具权限，不只检查几句固定文本。
2. Unity 实际编译、移动、交互、对话、任务卡、转场、手机和直播表现。使用独立测试存档，不写用户真实进度。
3. 真实模型、TTS和唱歌的完整体验。更换名字、介绍顺序、交谈内容与任务对象，观察现场生成是否有差异且仍符合人设；不要求任何固定措辞才能通过。
4. 对抗与异常情境：请求不存在的物品、未解锁地点、让AI代做任务、连点接受、生成期间读档、旧直播回调、服务断线、静音及中断歌声。报告实际运行命令、结果和未覆盖范围。
