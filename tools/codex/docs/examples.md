# 三个团队使用示例

以下是安装 `$godot-team-collab` 后可复制到 Codex 的任务提示，**不是已经执行的任务或验收结果**。目录、分支名、资源名和接口均为示例；使用前替换成真实项目内容，以项目及子目录的 `AGENTS.md`、架构和资产规范为准。若项目没有这些约定，Agent 应先查清现状并说明缺口，不能假定示例结构已经存在。

每项任务使用独立分支和一个写入者。原目录即使有未提交或已暂存的工作也必须保留；新 Worktree 从已提交的主分支内容开始，不会自动包含原目录里的修改。下面提示明确授权完成本任务的 Commit、Push 和 PR；合并、分支集成和清理仍须确认具体方案。

## 示例 1：程序成员开发一个功能

**目标：** 为已有玩家系统增加冲刺能力，复用现有输入和移动逻辑。

**复制给 Codex：**

> 使用 `$godot-team-collab`，在这个 Godot 项目中实现玩家冲刺：短按冲刺键后加速一段时间，冷却结束后才能再次触发。先读 README、适用的 AGENTS、架构和现有玩家代码，确认能复用什么，并提出与现有玩法一致的参数和验收方式。
>
> 我正在原目录调试关卡，里面有未提交修改和可能已暂存的内容，请全部保留。确认可信远端后，成功获取最新 main，从明确的基准提交新建 `feat/player-dash` 和独立 Worktree。你是该任务唯一写入者；不要把原目录的修改带进任务，也不要让我在同一目录同时编辑。
>
> 预期范围是玩家脚本、独立测试场景和必要说明，实际路径以项目约定为准。先检查现有 Input Map；若需要修改 `project.godot` 或共享主场景，先核实负责人并协调文件写入权。复用现有检查，完成后展示最终范围与检查结果。我授权你提交本任务文件、普通推送该功能分支并创建 PR；检查条件不完整时创建 Draft PR，清楚说明缺口。不要合并或清理 Worktree。

**Agent 应执行并交付：**

1. 找到现有玩家移动、输入和冷却机制，说明复用位置与功能边界；给出分支、基准提交和新工作目录的绝对路径。
2. 在自己的 Worktree 实现功能。若输入配置由其他人负责，先交代需要新增的输入动作，并在可控范围内推进，不占用共享文件。
3. 分别报告代码检查、Godot 导入、场景运行和待人工检查项；只暂存本任务的明确文件，审阅暂存内容后按授权创建 Commit 和 PR。
4. PR 描述应让关卡或策划成员看懂：冲刺如何触发、参数在哪里调整、应打开哪个场景、已知限制是什么，并附实际 Commit SHA 和 PR 链接。

**人工验收与交付边界：** 成员在 Agent 给出的任务目录用团队固定的 Godot 版本打开指定场景，检查连续按键、冷却期间重复触发、撞墙和已有移动是否正常。验收通过后，指定评审人检查 PR。用户确认“将 PR #实际编号按仓库允许的方式合入 main”后才可执行合并；删除分支或移除 Worktree 是另一项具体确认，不能因 PR 已合并自动执行。

**常见失败：远端拒绝 Push。** Agent 应先查明是权限、分支保护、网络结果未知，还是同名分支已有他人提交。保留本地 Commit，不改推 main，不强推。若需要把远端新提交集成进任务分支，先给出涉及的提交与影响，由用户确认后操作并复验。

## 示例 2：美术成员交付 Blender 源文件和 GLB

**目标：** 更新一张桌子模型，同时交付可继续编辑的源资产和游戏可用的导出物。

**复制给 Codex：**

> 使用 `$godot-team-collab`，帮我交付已制作好的桌子模型。我会提供实际的 `.blend`、导出的 `.glb` 以及引用的外部贴图位置。请先读资产规范、检查现有桌子资产和使用它的场景，确认命名、单位、朝向、材质、碰撞和多边形预算；缺失要求请明确列出来。
>
> 从成功获取的最新 main 建立 `art/update-workbench` 和独立 Worktree，保留原目录的所有未提交修改。我负责这份 `.blend`、对应 `.glb` 和相关贴图；请检查是否已有其他负责人或有效资产锁。采用项目已有的 Git LFS 规则，不擅自迁移历史或更改规则。仓库要求锁时，先检查锁状态并按授权获取属于我的锁；如不支持锁，明确协调负责人。
>
> 请告诉我应把文件放入新 Worktree 的哪些实际位置。我在该目录完成文件放置后会明确交还写入权；之后由你检查交付完整性并执行仓库操作，我们不要同时写。不要把 `.blend` 和 `.glb` 分给不同的人并行修改。
>
> 检查源文件能否找到外部依赖、GLB 能否按团队 Godot 版本导入，以及现有引用有没有断。不能实际打开 Blender 或运行场景时，说明哪些验收需要我完成。我授权你在检查后提交这些资产及必要的导入配置、普通推送分支并创建 PR；缺少运行或视觉验收时使用 Draft PR。不要合并、删除文件或清理工作区。

**Agent 应执行并交付：**

1. 找到真实资产位置与引用关系，确认同一负责人管理源文件及衍生文件。示例路径可以是 `art/source/workbench.blend` 和 `game/assets/props/workbench.glb`，但不能据此强行重排现有工程。
2. 检查已有 `.gitattributes` 是否匹配资产，Git LFS 是否可用，工作区中的大文件是否已下载为真实内容。仓库要求 LFS 但规则缺失或工具不可用时先说明阻塞，不把大二进制直接提交来绕过要求；规则变更须单独取得授权。
3. 核对外部贴图和其他依赖、导出设置、游戏中资源引用，以及应纳入版本管理的 Godot 导入配置。排除 `.godot/` 导入缓存和项目约定不提交的备份；不要把生成缓存当成交付资产。
4. 提供简明交付记录：源文件、导出物、依赖、负责人、使用场景，以及实际完成的 LFS、Blender、Godot 导入和运行检查。PR 说明模型外观或规格变化，配上可用的预览与待人工验收项。

**人工验收与交付边界：** 美术负责人先确认 Blender 源文件可继续编辑，外部依赖齐全，GLB 来自这份源文件；在 Godot 的实际使用场景检查比例、朝向、贴图、材质、动画和项目要求的碰撞。导入成功不能替代外观或玩法验收。通过后交由指定评审人审阅 PR；合并与资产解锁/清理按各自具体对象确认，不能提前解除仍在编辑的资产锁。

**常见失败：同一 GLB 出现二进制冲突。** 暂停该资产的提交或集成，把两边的来源和负责人列清楚并保留两份工作成果。不能用“最新文件”或随意选择一边解决，也不能合并 LFS 指针文本。由资产负责人决定保留或重做哪份源内容，再从选定的 `.blend` 重新导出 GLB，补齐依赖并重新进行 Godot 导入和视觉验收。

## 示例 3：两个 AI Agent 使用 Worktree 并行开发

**目标：** Agent A 实现拾取逻辑，Agent B 实现背包界面，双方通过事先确定的接口连接。

**先复制给负责协调的 Codex：**

> 使用 `$godot-team-collab`，组织两个 Agent 并行完成拾取逻辑和背包界面。先检查现有系统并复用项目架构，确定它们的接口、各自可写路径和集成人，再启动实现。原目录是人类工作区，里面的所有修改都必须保留。
>
> 从本次成功获取的同一个最新 main 提交，分别创建 `feat/item-pickup` 和 `feat/inventory-panel`，各自使用独立 Worktree。每个目录只有对应 Agent 写入；两个 Godot 编辑器也必须分别打开各自目录。请提供分支、绝对路径、基准提交和负责人对照表。
>
> 先按真实工程确定拾取调用、物品 ID、数量规则、失败返回和界面刷新事件的契约。若需要新增共享接口文件，指定一个负责人先完成共享前置 PR；确认合并后，再从更新的 main 开这两个任务。不要让两个 Agent 分别发明同名接口。
>
> A 只改确认分配的拾取路径和独立验证场景；B 只改确认分配的界面路径和独立验证场景。`project.godot`、Autoload 配置和游戏总场景由指定集成人统一处理，两位 Agent 只报告接入需求，不同时编辑。实际路径和职责以 AGENTS 为准；出现重叠时先重新分工。
>
> 我授权每位 Agent 提交自己的任务文件、普通推送自己的分支、各开一个 PR。两位 Agent 不互相合并分支，不执行 main 合并、不清理工作区。协调者整理两个 PR 的依赖、建议顺序与联合验收步骤，等待我对具体集成操作的确认。

**交给各 Agent 的补充提示：**

> Agent A：你只在分配给 A 的绝对路径工作，按已确认契约实现拾取逻辑。检查目前是否已经有库存服务，复用它；用独立验证场景证明成功拾取、数量变化和失败处理。只提交 A 的约定文件，PR 中列明需要集成人完成的接入项。

> Agent B：你只在分配给 B 的绝对路径工作，按同一契约实现背包界面。可用隔离的示例数据验证界面，但不能把模拟数据验收写成真实拾取链路已通过。只提交 B 的约定文件，PR 中列明需要集成人完成的接入项。

**Agent 应执行并交付：**

- 先产出可检查的契约和互不重叠的文件职责表。例如 A 管理 `game/features/pickup/`，B 管理 `game/ui/inventory/`；这些只是示例，若实际库存服务位于共享目录，必须另行明确其唯一写入者。
- 两个 Worktree 各用自己的分支、暂存区和 Godot 缓存；不要切换或更改人类原目录的分支。每个 Agent 报告各自检查结果和 PR，协调者不代写双方工作区。
- 集成人收集 Input Map、Autoload、总场景接入需求，在指定集成分支/PR 中完成受管文件的改动。协调者说明“拾取 → 库存变化 → 界面刷新”还缺哪些联合验证，不用两个局部检查代替端到端结果。

**人工验收与交付边界：** 先审阅两个 PR 与共享文件的接入方案，再确认具体合并顺序。第一个 PR 合入 main 后，第二个分支会落后；必须先查差异和仓库规则，向用户提出把更新后的 main 集成到第二分支的具体方案，取得确认后由该分支唯一写入者操作，再普通推送并复验。实际集成结果仍可能冲突，即使 Git 没有报告冲突，也要重新验证拾取失败处理、库存数量、界面刷新和场景切换。主分支合并由获准的集成人执行，清理每个 Worktree 时另行确认其路径、提交去向和残留文件。

**常见失败：双方都需要改 `project.godot` 或总场景。** 两位 Agent 停止修改这些路径，报告各自需要的配置与节点连接；由集成人统一修改。已有改动不得直接覆盖或删除，应先展示差异、确定归属和保留方式。Worktree 隔离的是工作目录与暂存状态，不能自动消除共享配置、资源 UID、接口和玩法行为上的冲突。
