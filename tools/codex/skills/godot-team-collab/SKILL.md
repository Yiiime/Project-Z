# Godot 团队协作

让成员用自然语言完成 GitHub Flow：从最新 `main` 开任务分支，按需隔离 Worktree，审阅改动后交付 PR。复用 Git、Git LFS、GitHub CLI/现有 GitHub 连接器、Codex 自带 Worktree；不创建自有分支系统、自动同步守护进程或额外 Git 包装脚本。

## 按需读取

- 初次使用、工具/认证异常：读 [environment.md](references/environment.md)。
- 开任务、并行开发、提交、推送、PR 或工作区清理：读 [workflow.md](references/workflow.md)。
- 涉及场景、模型、LFS 或冲突：读 [assets-conflicts.md](references/assets-conflicts.md)。

这些参考随 Skill 安装，执行不依赖分发仓库的团队教程，也不要求额外 MCP。

## 先理解项目和当前任务

1. 查明真实 Git 根目录、当前工作目录/分支、远端、Worktree 列表以及 staged、unstaged、untracked 状态和有价值的 ignored 资产；识别进行中的 merge/rebase/cherry-pick。不在仓库中时先定位用户指定项目，不擅自 `git init` 或猜一个远端。
2. 读取当前适用的 `AGENTS.md` / `AGENTS.override.md`、`README.md`；动手前补读目标子目录的指令。再按链接读取架构、资产规范、贡献指南、现有 PR/任务说明和 CI。缺失文档应标为缺失，不生成虚构约定。
3. 找到真实 `project.godot` 与团队固定的 Godot 版本；检查入口场景、Autoload、Input Map、现有脚本/场景/资源、插件及 `.gitignore` / `.gitattributes`。用 `rg --files` 和针对任务的符号/资源路径搜索，避免全文扫描缓存、大型二进制或复制已有系统。
4. 用几句话交代「要实现什么、复用哪里、谁改哪些路径、如何验收」。已明确的信息直接采用；只有缺失信息会改变实现或导致文件争用时才询问。跨场景、共享接口或资产交接先明确负责人和依赖。

## 按当前授权推进

| 用户意图 | 可以推进到哪里 |
| --- | --- |
| 检查环境、解释冲突、评估方案 | 读取与诊断；不给项目、配置或远端制造修改 |
| 开发/修复/制作资产 | 新建任务分支或 Worktree，修改约定文件，做必要验证；不据此推断发布授权 |
| 提交 / 推送 / 创建 PR | 执行用户明确涵盖的步骤；「提交、推送并开 PR」可一次授权完成，不逐条重复询问 |
| 合并、rebase、cherry-pick、回退或清理 | 先准备具体对象、影响、保留/恢复方案，再确认；已有对同一具体方案的明确授权可沿用 |

「完成开发并交付 PR」包含本任务所需的 Commit、普通 Push 和 PR；「检查 / 准备 PR」只到可审阅的草稿。按完整语义判断，不要求成员逐个念出 Git 动词；用户另有限制时遵守限制。

安装软件、登录、修改 Git 配置、改变 LFS 规则和 GitHub 仓库设置必须属于用户当前任务授权；环境检查本身不授权这些变更。登录交由本人完成，不索取或显示 token。新增 PR 正文属于已授权的 PR 交付；不附带给同事发消息、评论或 @ 提醒。

LFS 历史迁移不在本 Skill 的执行范围，交维护者另立计划；不能通过普通交付确认扩展为改写整个仓库历史。

## 不可省略的安全边界

- 不覆盖、丢弃、暂存、挪走或提交归属不明的既有修改；尤其检查预先 staged 的内容。禁止为「保持干净」擅自 stash、reset、restore、checkout 覆盖或 clean。隔离 Worktree 不会带走原目录的未提交工作。
- 不在 `main` 或项目定义的受保护分支上开发、提交或直接推送；不改保护设置来绕过限制。
- 不强制推送，包括 `--force-with-lease`、`+refspec`；不跳过 hooks、LFS 检查或分支保护。普通 push 被拒绝时先查原因，不升级成强推。
- 不删除工作区、分支、未跟踪/被忽略资源，不强制解锁资产。经用户确认的安全清理按参考流程执行；`rm -rf` 工作树和强制删除不属于正常流程。
- 一项任务一个分支、一个写入者、一个工作目录。人类也可以是写入者；多个 Agent 不共享同一工作树的 index。只读审阅可以并行。文件职责重叠则先协调，Worktree 不承诺未来无冲突。
- `.blend` / `.glb` 等二进制冲突交负责人决定，并从选定源文件重导出；不把 LFS 指针当作可合并的模型，也不按时间戳挑胜者。
- 网络操作结果不明先核对远端分支、PR 或锁状态，再决定是否重试；失败和未验证事项如实保留。

Skill 是 Agent 的操作指引，不是权限沙箱。GitHub 的保护规则、访问权限和团队评审负责服务器端约束；它也不能阻止人类手动执行 Git 或 Codex 应用自身的自动 Worktree 回收。

## 工作方式与交付

默认从本次成功获取的 `origin/main` 固定基准提交创建分支，按 [workflow.md](references/workflow.md) 核对 remote、使用 `--no-track`，不必切回或改动本地 `main`。若项目使用其他主分支或 fork，先核实配置再替换示例，不能把 `origin` 自动当成可信上游。

对并行任务先约定各自路径和接口、统一集成人；每个 Godot 编辑器打开各自 Worktree 的项目，缓存独立，二进制源文件与导出物同一负责人。遇到冲突只推进可安全确认的部分。

提交前检查最终 diff、暂存区、资产与依赖完整性，复用项目已有检查。把「文本检查」「Godot 导入」「场景运行」「视觉/玩法人工验收」分别记录，不能用其中一项冒充其余通过。没有运行条件时可在获准后交付 Draft PR，注明缺口。

最后用成员能理解的中文交代：完成的行为与文件范围、分支和绝对工作目录、已执行/未执行的检查、Commit SHA/PR 链接（确实存在时）、还需谁确认什么。非程序成员无需复制一长串命令；需要其操作时只给下一项关键动作。
