## 已发现并修正的问题

| 问题 | 修正 |
|---|---|
| 四个短 Z 节点若写占全程10%—15%，会变成36—72分钟 | 改为合计约10—15分钟，避免悄悄形成完整第二主角制作量 |
| “被发现后可用备用窗口”可能绕过公司确证隔离 | 怀疑阶段可改已备路线；确证隔离后本次执行失败 |
| 迁移保留源状态可能被误当成恢复玩家权限 | 失败按阶段与原因处理；隔离优先，保留实例不恢复资格和时机 |
| 统一按公开许可过滤记忆会导致私下也忘记 | 知情范围控制检索，受众/渠道/许可控制表达 |
| 只以主观演讲质量决定胜负 | 真实事件标签先算规则结果，AI只组织合法素材，失败用同素材回退 |
| 评审绝对分与观众票份额混用，使观众实际权重随人数降低 | 两类票权先分别归一化，再按40/60合成；同分有明确处理 |
| 三人赛门槛直接套到更多参赛者 | 首个数值原型固定三个计分选手，扩充人数必须重新平衡 |
| 互动小游戏看到结果后可以取消未提交行动 | 确认后锁定成本并保存pending，退出恢复；结果后不可取消退款 |
| 两个视角重复扣时间，或利用并行倒改因果 | 只合并从同一起点独立可行的行动，依赖消息的动作串行 |
| Demo只验证模型改写邀请台词 | 增加D2主动小提议→D3完成→当晚回应，替代一次既有准备行动 |
| 迟邀约没有共同生活时间，或不邀约却自动播放亲密剧情 | 正常迟邀约保留三个活动窗口；持续拒绝进入弱关系支路 |
| 用户拒绝核验后Z永久不知道身份 | D12公司交接说明提供冷处理信息支路，不奖励共同觉察与信任 |
| 角色数、能力方向、文字预算与实时规则在分册不一致 | 统一8配角、4能力、4—6万字预算、动作推进时间 |
| 旧静态UI被当作新游戏制作基础 | 根入口与旧稿标注历史状态，当前仅设计基线，无游戏工程验收 |

## 2026-10-10 追加：源码研究落实到 v2 与首个切片

本轮用户授权完善 v2 设计和技术规格，没有要求实现引擎工程。以现有固定 commit 的社区源码研究为依据，修改五份 v2 主文档，新建 [D1—D3 Demo 开发与验收规格](D1-D3-Demo开发与验收规格-v2.md)，同步 README、根指引、导航与采用记录。三个并行专项审查分别覆盖核心规则、开发阶段、剧情一致性，新增切片又经独立复核；以下记录规格缺陷及修订，不冒称发现和修复了已运行游戏的 bug。

| 源码启发或规格缺口 | 本轮修正 |
|---|---|
| 时间观察通知可能被误当权威动作；窗口末端语义缺失 | 行动统一推进；半开窗口允许恰好完成；同刻先提交已开始行动再处理截止；补齐18:00/22:00边界 |
| 固定定义名被写成唯一action_id；预留与扣费混淆 | action_definition_id/action_id/收据分开；pending只预留，完整提交才实际增减；失败也是完整后果 |
| 任务定义/本局实例/目标与奖励没有明确契约 | 稳定objective_id、state/event谓词、auto/claim结算方式、奖励结果键；动作失败不自动终止整个任务 |
| 交付示例只查持有，就声明送达 | 校验拥有者、数量、目标与许可；真实转移＋收据＋任务推进同事务；AI/日志不能作事实来源 |
| 按event_id去重仍可用新请求/换措辞刷关系 | 增加带来源、对象、类型和周期的contribution_key；保留合法小礼物2＋回答1组合 |
| 总案写D2兑现，但小提议在D2才提出；核心邀约漏履约 | 统一D2形成约定、D3实际交付、夜间反馈、最早D3邀请；拒绝不构成失约 |
| 已知账号与岛内身份未可靠关联 | 报到核验关联，投递带来源，Z通过工作简报实际获知；身份关联成为邀约前置 |
| 补做先要求被接受，但接受又在后续反馈中 | 改为补交收据→夜间反馈接受→邀约资格，消除依赖环 |
| 迟交先入箱会失去复核物；17:00许可挡住补救 | 允许按原投递收据原位核对；Q05有独立至18:00的窗口；持有/已入箱最晚启动17:25/17:30 |
| D7补救落在Demo外；未来赴约与当下交付混淆 | D3现有窗口内制作有代价补救；D7仅完整版；D4邀请可接受但不伪造已见面 |
| 礼物起始成本虚算打工，差异账本却无法证明撞期 | 已有40岛券可以直接花12；D1共享场务不重计；加入08:40咖啡班与09:40关闭工作台的真实冲突 |
| NPC在岗、工作台权限只存在于叙述 | 切片补四人服务表、班次/数量上限、D1教学与D3复核许可；未扩成完整NPC模拟 |
| Z视角只有原则，没写首次发信流程 | 串行10＋5分钟；账号通知权限不等于任意私聊；发送/收到/接受及道具归属独立 |
| 未送达也要求15分钟，可能虚构接收 | 测试注入停22:10，保存恢复仍未收到；解除后复用消息再花5分钟接收 |
| 断网不扣费可能被解释为confirmed行动免费 | 等待本身不收费；pending恢复按原动作正常结算一次；已提交只补展示 |
| 同修订旧档可能接收旧AI，读更早档又可能被全局去重拦截 | 运行期load_epoch不随旧档恢复；丢弃旧回应；奖励去重按存档分支，不阻止合法回滚重玩 |
| 开发顺序/完整游戏验收混排 | G0—G6统一；公开Demo只D1—D3，后期终局独立内部测试；状态、AI有效性、玩家因果理解三组门槛分别验收 |

### 本轮实际完成的核对

- 12份当前入口/规格/索引文件的本地链接存在性、15段代码围栏、5份JSON示例语法；未重新宣称所有历史研究外链仍在线。精确计数与文件SHA-256见[静态核对输出](validation/v2-spec-static-check-2026-10-10.json)。

- 核对15:05/15:10正常投递、15:35/15:40失败后修复、17:25/17:30最晚复核、Z串行15分钟及D1班次/工作台冲突。D2工作台09:00开，基准已补08:30到09:00等待。
- 复读修订后的任务依赖、身份与消息知情来源、D3补救窗口和阶段边界；未发现仍需阻塞本轮规格交付的冲突。

### 当前仍不能声称通过的事项

全部G0—G6与D01—D16实机用例未执行。未建立规则引擎、运行故障注入、接真实模型、生成Windows构建或进行首次玩家试玩；静态JSON可解析与账本闭合不证明游戏可玩。D1新增撞期让机会取舍可测试，但礼物路线是否过强、日间等待是否过多、Z的提议是否自然、30—40分钟节奏是否成立，必须由后续构建和试玩决定。
