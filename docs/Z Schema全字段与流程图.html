先分清四层，以及两次回执

Unity请求用camelCase；模型上下文由后端按角色可见信息组装；模型输出是紧凑的dialogue/action/info；后台存档与执行记录包含展开动作和完整状态。命名、类型有差别本身不一定是冲突，关键是适配是否明确。

“Z答应去花店”：模型必须选择合法move候选，台词呈现后后台创建pending行程；结束对话占用，Unity继续走完整路线；到达回执后才认定已到。“给你菜单”：当前没有通用菜单交付执行器，wait成功只表示没有世界变化，不能证明玩家拿到了菜单。

Info影响下一轮判断与任务协作；好感/信任/怀疑度不会单独越过阈值就强制NPC帮助。周伯伯的逃离援助限制是明确角色边界。初始数值限制和回合变化范围是两回事。

按端点选Schema，不要验证顶层anyOf就算接通

下列均为当前/api/game的POST接口。Unity显式使用reference-v1，普通对话仅返回台词投影；省略syncMode时server仍默认legacy-full。直接/task接口与Unity的/sync任务事件是两种入口，同一次操作选一种，避免重复提交。

接口请求定义成功响应定义使用方式
/api/game/openOpenRequestGameResponse新局/读档；建议显式 syncMode=reference-v1，省略时当前 server 使用 legacy-full。
/api/game/focusFocusRequestGameResponse取得/释放玩家对话占用；actorId=null 释放。
/api/game/syncSyncRequestGameResponse先上传玩家原话，NPC实际呈现后也通过 utterance 事件提交提案；动作与任务结果也走此端点。
/api/game/intentIntentRequestIntentResponse尚未交谈，只决定是否走近目标；targetId 为空表示本次不靠近。
/api/game/utteranceUtteranceRequestUtteranceResponse基于已 sync 的历史生成提案；默认当前 Unity reference-v1 仅回台词。legacy-full 响应见 LegacyUtteranceResponse。
/api/game/commitCommitRequestGameResponse提交没有对外台词的判断；有台词时以 sync 的实际呈现回执提交。
/api/game/cancelCancelRequestOkResponse取消角色/会话中的提案与生成；不是取消物理行程。取消 move 需要专门 cancel_move 选项。
/api/game/checkpointCheckpointRequestGameResponseportable=true 导出完整 version=2 快照，否则按 syncMode。
/api/game/closeCloseRequestOkResponse结束当前 run；没有 checkpoint 字段。
/api/game/stateStateRequestStateResponse调试完整状态，不作为普通玩家界面数据。
/api/game/task/respondTaskRespondRequestGameResponse玩家接受/拒绝任务。
/api/game/task/inviteTaskInviteRequestGameResponse接受后邀请 NPC 协作；不会强制 NPC 接受。
/api/game/task/receiptTaskReceiptRequestGameResponse可信执行结果更新任务步骤；细节仍由 TaskEngine 验证。
/api/game/live/openLiveOpenRequestLiveOpenResponse结束私聊后进入；8位角色全员加入。
/api/game/live/closeLiveCloseRequestGameResponse同步中断片段并退出；恢复岛上调度。
/api/game/live/prepareLivePrepareRequestLivePrepareResponse取同一个角色的本局人设与私有记忆，附上公开直播感知。
/api/game/live/proposeLiveProposeRequestLiveProposeResponse保存角色直播提案；最终角色由 contextId 决定，静态 anyOf 不能替代角色匹配。
/api/game/live/observeLiveObserveRequestLiveObserveResponse只有实际发布/播出的内容才对全员可见；progress 仅缓存已播前缀。

HTTP错误形状是ErrorResponse。/cancel和/close只返回ok，不能假定每个成功响应都有checkpoint。校验顺序：端点结构 → runId/状态/来源/可见性 → 当轮动作与数值Policy → 提案提交 → 实际执行回执。静态Schema只能承担其中一部分。
