## 1. 核心分工

**规则决定实际发生了什么，AI 理解玩家在说什么，并让 Z 用自己的方式回应。**关键任务、物品、门禁、时间、记忆事实、比赛计分与结局由可重放的规则处理。

| 组件 | 输入 | 输出 | 不能做什么 |
|---|---|---|---|
| 世界规则 | 动作、资源、事件、日程 | 状态变化、可用操作、成本与后果 | 依赖自由文本是否“足够感人”决定通关 |
| 意图理解 | 玩家文本、所指材料、当前允许意图 | 意图候选、引用对象、待澄清项 | 把玩家说“我已经修好了”当作设备真的已修好 |
| 角色回应 | Z 已知事实、立场、经历、可回应动作 | 自然语言、情绪表达、受约束提议 | 创造物品、管理员权限、亲历事件或未建立的关系 |
| 记忆检索 | 当前话题、角色访问范围、已完成事件 | 有来源的事实与关系片段 | 从全文聊天中猜出发生过的游戏行为 |
| 演讲生成 | 已许可素材、Z 立场、比赛已结算标签 | 基于真实经历的表达与引用清单 | 修改赛果、补造苦难、公开未获许可的私密细节 |
| 演出层 | 已提交事件与表现指令 | 动画、音效、字幕、镜头 | 动画播放完才临时决定奖励是否发放 |

AI 可以建议“明天一起修灯”，但只有活动模板、时间窗口和角色许可都成立时，界面才出现可接受的提议。未经安排的自然闲聊可以存在，但不能诱使玩家相信任意承诺都会进入可玩世界。

## 3. 动作、任务与道具的统一执行协议

### 3.1 标识、状态与执行顺序

```text
选择目标 → 列出已知方法 → 免费澄清与预览条件/代价 → 玩家确认
→ 重新校验条件 → 分配唯一 action_id → 预留成本并持久化 pending
→ 收集必要的有限输入 → 在副本中推演结果/边界事件 → 校验完整变更
→ 原子保存成本/状态/事件/收据 → 发布状态变化通知
→ 演出与角色回应 → 显示新机会
```

条件包括操控角色、地点、时间、金币/物品、权限、任务阶段和已接受约定。存在未知风险时可隐藏具体后果，但必须给可理解的风险类别；不能假装显示“必定安全”。

首个Demo同时最多一个正在提交的正式行动；Z短视角也是有界流程，零分钟直播互动按顺序提交，AI表现等待不占用另一套玩家行动预算。无需先做任意并发任务框架。预留只减少“可用”金币/库存，不提前扣款或发放物品；提交时才把实际`gold_delta`、库存增减与时钟写入同一账本并释放占用。赠礼可以是从已有库存转出，也可以是确认一次金币交易取得并送出，具体由内容定义；已购买的同一礼物不能赠送时再扣购买款。失败也是一种完整规则结果，可以花掉时间、留下返工与失约；“原子”不表示失败免费，也不表示结果必须成功。

| 标识或状态 | 约定 |
|---|---|
| `action_definition_id` | 可重复使用的作者模板，如 `cafe_shift`，不能拿来当一次交易的唯一键 |
| `action_id` | 本次行动实例；确认时生成并随 pending 保存，恢复/重发使用同一个 ID |
| `event_id` / `receipt_id` | 已提交事实与完整变更收据；收据包含action_id、前后world_revision、起止时间、gold_delta、库存实际增减、任务与权限变化 |
| `run_id` / `world_revision` | 本局身份与快照修订；同一局回到旧档是合法回滚，不把未来收据带回旧状态 |
| `load_epoch` / `request_id` | 每次载入/重置递增的运行期隔离号、一次请求标识（另标request_kind区分动作请求与模型请求）；重发同一请求沿用ID，有意新发弹幕/赠礼用新ID；load_epoch不从旧档还原，避免修订号相同时接入旧回应 |
| 动作状态 | `pending → committed`；提交收据另记 `outcome=success / failure / partial`。partial 是作者定义的完整后果包，不是数据库只写了一半 |
| 确认前拒绝 | 返回 `rejected + reason + recovery_hint`，无 action_id 对应的新成本；排队/占用成功只回 pending，不能显示任务成功 |

存档失败时保留可恢复的 pending，不显示已到账；恢复后查收据决定继续结算还是只补展示。小游戏已选输入随 pending 保存，不能看过规则结果再用取消退款；退出回档遵循普通读档规则。内容若允许中止，必须定义有代价的中止结果，不能把通用取消键用作事后撤销。网络恢复和通知订阅者均无权再次执行奖励。

### 3.2 游戏时钟和同刻事件

- 使用绝对游戏分钟比较，日历只是显示；服务窗口为半开区间 `[开始,结束)`，行动可恰好在末端完成，不能在末端新开。预览显示预计结束时间，资源不足或跨未授权窗口时拒绝确认。
- 日间阶段边界为 12:00、14:00、18:00、20:00、22:00、23:00；普通行动不隐式跨界，午饭/节目/睡眠等明确声明自己的区间。D21 的归档是终局事件，不能用睡眠生成 D22。
- 在状态副本中按时间推进。跨过区间内的消息/离场事件时，只让其影响该时刻以后的可中断步骤。到同一时刻，先完成此前合法启动且此刻完成的动作，再处理许可过期/离场/截止，最后生成新菜单；特殊优先级必须在内容定义与预览中明确。
- 行动依赖的窗口须覆盖所需过程；当前状态满足不代表十分钟后仍可交付。对不能保证的中途风险，使用有检查点与失败包的活动，不能预览为必成。
- 阅读、正常移动、澄清、AI 等待不推进分钟；危险动作步将自己的分钟交给同一入口，禁止另扣一份活动时间。Z 并行区间遵循 §7，首个 Demo 的邀请节点按串行实现。
- 跳到下一时段是显式等待行动，仍处理经过的截止与失约；它不是修改时钟后再一轮补发奖励。

直播的20:00—22:00剧情时段遵守相同入口，但输入与节目推进分开：打字、普通弹幕发送、看评论、报名/等待抽选、AI生成与阅读均为0分钟；赠礼只结算声明的金币或库存，不把一条消息计作40分钟行动。玩家确认节目进展才执行一次`segment_advance`。Demo沿用三个各40分钟的窗口，三段合计120分钟；这是内容编排参数，不是三次说话额度。时段边界、消息投递和截止随推进事务处理，真实网络等待不能自动触发下一段。

### 3.3 交付必须发生在世界中

以下是协议示例，不是 Demo 的新增送货任务。只有包裹实际转移、交接凭据与目标事实写入同一次提交，任务才推进。UI 写一条“送到了”、背包刚获得包裹或玩家声称完成均无效。

```json
{
  "action_definition_id": "cafe_delivery",
  "actor_id": "player",
  "location": "prop_room_handover",
  "requires": [
    "quest_instance.delivery.active",
    "package.owner_is_player",
    "package.unreserved_count_at_least_1",
    "receiver.on_duty",
    "permission.deliver_to_this_target"
  ],
  "cost": {"minutes": 30, "gold": 0},
  "reserve": [{"item_ref": "quest_instance.package_id", "count": 1}],
  "effects_on_success": [
    {"transfer": "reserved_package", "from": "player", "to": "prop_room_receiver", "count": 1},
    {"fact": "package_received", "target": "prop_room_receiver", "quest_ref": "quest_instance.delivery"},
    {"permission": "prop_room.delivery_only", "expires": "today_18_00"}
  ],
  "failure_policy": "reject_before_confirm_if_full_interval_not_serviceable",
  "repeat_policy": "once_per_quest_instance"
}
```

示例中的 quest_instance、package 与 today 是实例化绑定位置，内容编译时必须解析到唯一对象和绝对时刻；不能把这些占位串直接当作已验证谓词。成本仅为接口示例，不覆盖核心数值表。内容校验器拒绝未定义引用、重复稳定 ID、反向时间窗口和没有完整失败包的可失败行动。

### 3.4 任务定义、本局实例、目标与奖励

| 对象 | 最少保存内容 | 执行规则 |
|---|---|---|
| QuestDefinition | 稳定 definition_id、version、入口/截止、目标定义、结果包、重复策略 | 目标用稳定 objective_id，不用数组下标；内容重排不能改变旧目标含义 |
| QuestInstance | instance_id、definition_id/version、accepted_at、绑定人物/物品/班次、status | 每日工作是不同班次实例；同一实例重试不重新发一份任务 |
| ObjectiveState | objective_id、判定类型、满足事实/收据引用、当前状态 | “拥有”与“已交付”用不同谓词，不能靠文本相似互认 |
| RewardReceipt | quest_instance_id、result_id、action_id、实际结果 | 每个结果包至多提交一次；奖励随结算事务保存，动画/对话不负责发奖 |

最小状态机：未实例化机会 `available` → 接受后 `active` → 所有条件满足 `ready` → 结算 `completed`；可按作者规则到 `failed` 或 `expired`。每个任务选一种结算方式：`auto` 在满足时同事务完成，`claim` 需要到指定交付点确认；不能一边自动发奖一边保留可领按钮。首个 Demo 工作、制作与投递采用 auto；送达的动作本身已经是交付，不再加一遍“领取完成奖励”。

目标分两类：`state_predicate` 检查当前状态，如“持有未占用材料”；`event_predicate` 检查真实事件，如“在接任务后交给陈叔”。作者必须写时间范围/任务实例/接收者。当前持有类在接受和载入时立即检查；事件类若允许此前完成必须显式 `allow_prior=true` 并绑定合格旧事实，否则不得把刚获得某道具当作已经送出。默认 ready 条件仍须在最终领取/动作提交时重验；不可逆的已交付事实则不会因后来没持有道具而回退。

事实提交后，按受影响条件重新检查目标，在同一副本中算出任务/承诺/奖励，稳定后一次保存。派生效果用稳定结果键去重，内容校验拒绝无界奖励循环。订阅通知与任务日志只展示这一结果，不承担权威判定；无需每 0.2 秒扫描一遍来决定有没有完成。载入时重建条件索引与观察基线，校验实例；不重播接受通知、不再次派发奖励。有矛盾的旧档走迁移或明确报错，不能用“重新评估”偷偷补一笔工资。

失败后的补救是关联的新行动/任务实例，引用原失败事实。它可产生 `resolved_by` 和新的履约记录，不能抹掉原失约，也不能复制过期许可。拒绝提议不建立承诺；停止跟踪任务仅改变 UI，不等于取消已经接受的承诺。

动作 outcome=failure 不自动等于任务 status=failed：窗口仍在的“待复核”可保持 active，目标状态为 needs_review，由复核行动完成；终止/过期后的恢复才创建关联的新任务实例。工资结果键始终绑定原班次，复核不能额外再生成一班报酬。发生过失败的行动事实始终保留，即使任务最终完成。

### 3.5 物品、目标和许可

物品定义规定可用动词；实际持有记录 owner、location、count 与 reserved_count。普通可堆叠材料用 holding_id，任务作品/借用工具用 instance_id；Demo 不做耐久、随机品质、容量或任意合成。每项行动校验 `actor + verb + item + target + permission + window`，许可的对象、区域、动作与期限不能只合并成“有门卡”。

购买、出售、制作与交付默认全有或全无：全部成本与目标空间满足才确认，实际收到/移出的数量写收据；禁止将接口布尔成功或“请求转移 1 件”当作真实变化 1 件。制作成功后才消耗材料并生成作品；作者定义的制作失败可以损耗材料，但损耗数量须预先说明。查看说明是知识操作，出示保留所有权，交付改变持有者，使用按定义消耗或保留；不能共用一个 `use()` 后默认扣除。

借来的工具只允许指定目标与动词，不能出售/送礼；外观像同种工具不意味着有同一使用许可。任务绑定材料只在 pending 中占用，完成后必须释放；长期保管/专属所有权另有明确持有规则，不能用永不释放的预留伪装剧情锁。相同交易 request 重发恢复原收据；有意新买一次应生成新 action_id，仍受库存、资金和窗口校验。

### 3.6 手机直播：互动、回应与节目推进分别记账

范围约束：以下赠礼接口可表达金币或库存成本，但 D1—D3 只启用已持有/预购礼物发送，只扣库存。手机即时购买并赠送尚未开放；未来启用时另核算内容前置与白天购买时间，不能仅放开接口便绕过 Q02。不存在收到一份库存礼物后再次扣其购买价格的情况。

夜间入口是游戏内手机直播界面，Z以近景Live2D式虚拟形象呈现；它只展示以下规则结果，不接管事实判定。观众条数、弹幕速度、送礼演出时长等属于表现与频率提案，不能变成未说明的每日行动预算。

| 操作 | 成本与提交 | 事实边界 |
|---|---|---|
| 发送普通弹幕/提交已有材料 | 0游戏分钟；新interaction_id/action_id记录本次真实输入或附件出示；真实材料仍须存在且允许公开 | sent不等于responded，不默认被Z念出；虚构描述只作为说话者的主张 |
| 送礼 | 确认具体金币或库存成本后保存pending；同一action_id原子提交一次实际变动，0额外节目分钟 | gift_delivered与Z是否回应分开；生成失败不退款已交付礼物，不额外发识别分 |
| 报名随机连麦 | 玩家明确opt_in；报名、抽选与等待均免费，抽选前可退出；中选后仍须确认接通 | 未报名不被自动接入；未抽中不算失约/关系失败，保留弹幕与投稿路径；重放同次抽选使用已保存结果 |
| Z回应与小提议 | 从合法材料、角色知识、当前节目主题生成候选；规则提交response_refs/贡献/承诺等合法结果后，AI负责表达 | 只有实际回应可登记双向交流；条件成立的核心反馈有作者可达路径，不以抽中连麦或模型随机选择为门槛 |
| 确认节目进展 | 对当前窗口创建segment_advance及其独立pending/收据，按窗口结算一次分钟 | 不代替赠礼收据，不重扣本段已提交金币/物品；回退、重试和读档只补尚未完成的步骤 |

幂等分三层：①相同`request_id`重发恢复同一互动/行动；有意发送第二条消息或第二份礼物生成新ID；②`segment_advance`用`run_id + episode_id + segment_id`作为推进唯一键，同段不再次加40分钟，但`episode_id + segment_id + actor_id`不能作为所有互动的唯一键；③关系贡献用§4的`contribution_key`限制重复收益，不阻止合法新消息或吞掉真实消费。抽选另绑定已编排的`draw_id`，退出后重新报名不能制造一次新抽选；下一次已开放轮次可重新自愿报名，具体频率仍是提案。未结算赠礼须先恢复/完成其pending再推进节目；未完成的AI表现可按超时规则采用作者回退并丢弃晚到回应。

每条消息保存可靠的说话者与来源：`player_input`、`audience_comment`、`authored_program_event`、`verified_submission`等由系统赋值，不能由自由文本自行冒认。匿名观众说“玩家已经交过作品”只产生该观众的发言记录，不产生交付、权限或玩家知识；即使Z读到了，也只能知道有人这样声称，不能把传闻提升为已核实事实。模型不得用其他观众的话满足玩家履约条件、编造共同经历或替玩家确认承诺。直播可引用材料另经身份、角色知识与公开许可过滤。

未被抽中连麦或未被挑中的普通弹幕，界面如实显示状态，不承诺下一条必读。Demo关键合格主题/投稿有可复现的作者回应节点，保证在实际条件成立时通过弹幕/投稿也能完成同等主线条件；即时聊天、购买礼物和反复称赞本身都不豁免真实准备、两次双向交流与D3履约。离线作者文本沿用相同互动/推进事务与抽选结果，不增加或减少结算。

## 4. 自由输入既有弹性又可预测

每个话题暴露一组合法意图，例如询问、解释、附证据、道歉、提出核验、邀请活动、请求帮助、确认计划、拒绝、结束。玩家不必记住这些词；界面用快捷句提供同等路径。

处理顺序：

1. 读取玩家选中的话题、附件和当前事件版本，只提供本轮需要的上下文。
2. 将自由文本映射为有限意图及所引用对象，记录原话供角色表达使用。
3. 对不确定、相互矛盾或超出世界支持范围的请求进行澄清；澄清不扣行动成本。
4. 需要耗时或重大后果的请求，先显示可执行行动卡，由玩家确认。
5. 规则根据事实与已接受承诺更新状态；再让 Z 表达结果、疑问与可行下一步。

“你的意思是让我在节目第二段检查提示器，而不是现在离开吗？”是有用澄清。“我完全理解了”但没有可检查的行动不构成计划确认。

同一句称赞、道歉或理由不能无限加关系。`action_id/event_id`只防止同一次结算重发，还需作者定义`contribution_key`：本局＋关系对象＋贡献类型＋来源主题/承诺＋限制周期。比如同一期的合格赠礼回应只有一项贡献，一个履约事实无论换多少种说法都只有一项可靠性贡献；这不是本段只能发一次消息。Demo合格主题节点中赠礼被回应的2与有效回答的1是两个预声明贡献，可由同一段内不同真实互动各算一次，不能由模型把一段话拆成多个事件无限生成。未被回应不自动给分，新的真实赠礼仍按自身ID消费；贡献记录随存档保存。新班次可有新工资，复述旧承诺不能有新信任。

无成本自由聊可以改变措辞和话题背景，实质认识、合作与承诺只在有对应条件的事件节点中变化。把聊天次数直接变成好感分会破坏日程经济。数量或关系快照未能读取时用 `unknown`，不得填 0 当作关系重置；角色拒绝、规则不满足、接口故障分别返回原因。

重要表态允许玩家回看 Z 的复述并纠正：什么时候、谁做什么、前置是什么、失败后怎么做。行动开始以后再说“我其实不是这个意思”不能倒改已发生事实；仍可按可用窗口取消或补救。

## 5. 事件与记忆示例

```json
{
  "event_id": "run_042_d09_lamp_01",
  "type": "shared_activity_resolved",
  "time": {"day": 9, "start": "15:00", "end": "16:00"},
  "participants": ["player", "z"],
  "location": "cafe",
  "facts": [
    "player_used_reserved_gift_parts",
    "z_held_lamp_while_player_repaired",
    "lamp_restored"
  ],
  "outcome": "success_with_sacrifice",
  "known_by": ["player", "z", "cafe_keeper"],
  "company_observation": "none_recorded",
  "commitment_refs": ["promise_fix_lamp"],
  "disclosure": {
    "public_use": "approved",
    "private_details": ["player_private_family_story"],
    "private_details_allowed": false
  }
}
```

事件事实只记发生的动作与结果。Z 可以把此事理解为认真、冲动或不善安排，但这些是解释，不是世界真相。双方可持有不同解释，后续对话可以修正理解，不能抹掉原动作。

记忆有三种层级：

- **硬事实：**已发生的活动、选择、交付、失约、公开/私人许可，结构化保存。
- **对话约定：**双方确认的下一步，带版本和履行状态。
- **表达摘要：**人物喜欢什么、最近在担心什么；只做回应背景，必须能指向原始片段，不能单独满足任务前置。

检索先按当前角色的知情范围选择，再按话题、未履约约定、最近活动和重要事件排序；进入表达素材包时，另按当前受众、渠道和披露许可过滤。Z 私下仍记得并能与当事人讨论一件被要求保密的事，只是不能拿到直播中讲；“禁止公开”不等于“从记忆中删除”。不能把全部聊天记录无限堆到提示词里，以免成本、延迟和矛盾不断增长。

## 6. 身份、信任与“她为什么愿意”

身份认知的事实链由作者安排的材料和核验组成，关系影响核验方式、情绪及下一步。模型可以解释证据，但不能把事实是否成立交给随机语气判断。

合作判断使用具体约束：她知道现状吗、了解方案风险吗、目标是否与她当前立场冲突、是否有可验证的去处、玩家是否履行过相关承诺。冲突要写成角色能够讲明白的理由。不得用“信任 80”覆盖“她明确不愿公开某段私人经历”。

Z 自主提议从当前合法活动中选择，例如补做一次失约活动、询问遗漏的事实、建议换一位联系人。提议先是候选；双方接受并在日程中预留才形成有效约定。模型不得自行离开场景、推进时间和消费物品。

承诺最小状态为 `proposed → accepted → fulfilled / missed / cancelled`；declined 单独记录拒绝候选，不进入失约。修改条款生成新版本并再次确认，旧版不能仍同时到期。条款至少含行动者、目标/交付对象、期限、可替代方法、接受者、结果判据；只有明确接受才占用实际需要的角色/时段，共同赴约占双方指定时间，截止前交件不锁住 Z 一整个下午。missed 保留事实，补做另记 `repair_ref` 与接受者确认；说“原谅你”不自动补齐未交付物品。Demo 的确认与拒绝可用快捷句或被复述确认的自由文本等价完成。

`known_facts` 引用角色实际获知的事实；`trust_claims` 保存在哪类行动上为何可靠；`consents` 绑定计划 ID/版本、范围和撤回条件。理解证据、愿意共同活动、许可公开、愿意迁移不可互推。邀约具体前置读取[核心系统 §4.1](核心系统与数值草案-v2.md)，其中已履约事实是必要条件，识别阈值只是条件之一。模型提议不等于同意，玩家在 Z 视角中也只能选择已合法开放的邀请方法。

## 7. Z 视角的状态契约

```text
节点前保存 → 固定区间起点与可用资源 → 切换操控者/知识过滤
→ 执行该角色专属动作 → 写入其事件 → 处理有效消息传递
→ 区间汇合 → 恢复玩家控制并保存
```

一个并行节点要预先声明：起点、允许的两侧动作、消息交接点、汇合上限。两个独立任务从同一起点开始，全球时刻推进到较晚的完成时刻；较早完成者有明确等待行为。若 Z 的动作依赖玩家刚发送的消息，则从消息收到以后串行开始，不能套“取最大值”让因果穿越。

Z不获得第二套可长期刷的金币和成长资源。节点只声明该角色的合法动作、时间和专属道具；不能利用切换重复打工、刷新商品和绕过时间窗口。她可携带的专属道具属于Z，需实际交付才进入玩家背包。

玩家看到 Z 的内心或查到的材料，只增加操作者认知；玩家角色行动菜单仍以其获得消息为准。关键事实要通过实际接收/交付进入对应角色知识。Z 视角也不开放任意读取玩家私密记录的权限。

## 8. 个性化决赛演讲

生成之前先制作一份**演讲素材包**：2—4 件可公开的本局真实经历、一个实际冲突或遗憾、Z 当前选择、允许提到的人和细节、已确认事实与仍有争议的说法。没有经历就诚实地生成简短版本，不能自动补齐所谓催泪素材。

```json
{
  "speech_context": "final_contest",
  "allowed_event_ids": ["run_042_d09_lamp_01", "run_042_d11_missed_meeting"],
  "z_position": "wants_independent_life_and_optional_broadcasting",
  "relationship": "friendship",
  "forbidden_details": ["player_private_family_story"],
  "allowed_claims": ["lamp_restored", "meeting_missed_then_repaired"],
  "max_length_hint": "90_to_150_seconds_reading",
  "gameplay_score_tags": ["concrete_shared_experience", "acknowledged_failure"]
}
```

生成返回 `text + cited_event_ids + claim_refs`。验证引用是否存在、角色是否知情、是否许可公开、是否与剧情状态相容；另做语言检查捕捉未获准的具体实体/时间/动作。机器校验无法证明任何自然语言都绝不幻觉，因此还需要固定用例、人工审稿样本和保守回退。

出现错误时只尝试一次受限修复，仍失败就使用作者模板拼接同一批事实。玩家可以通过“别讲那件事”的准备选项提前排除素材，Z 也可以拒绝公开自己的私密信息。

**计分与文本解耦：**系统先确定哪些实际经历、承诺与赛场结果可以产生共鸣标签，并确定本轮得分；模型只表达这些内容。同一事件集的不同文风不能导致一个档夺冠、另一个档归档。观众字幕与评论根据同一赛况产生，不允许评论声称发生了并不存在的重大事件。

## 9. 转移的状态机

| 阶段 | 条件与动作 | 可撤回/失败处理 |
|---|---|---|
| 未准备 | 只有想法或部分道具 | 不展示虚假的“立即迁移”按钮 |
| 已准备 | 接收端、资源、路径、设备、约定均可检查 | 条件过期则回到缺口状态，世界时间照常 |
| 窗口开启 | 玩家保持接口，Z 到达正确位置并确认 | 发现异常可取消；不能靠暂停菜单延长游戏分钟，但思考本身不扣时 |
| 注册与冻结 | 记录实例/快照标识，Z 确认进入冻结 | Z 停止新动作与生成对话；玩家继续执行 |
| 传输与校验 | 分阶段推进设备状态，接收端返回对应快照收据 | 校验失败不销毁源端，回到可恢复检查点或被隔离结果 |
| 控制权交接 | 接收端准备就绪、当前源端停止执行；一次性交接标识 | 不允许两端同时作为当前实例推进游戏事件 |
| 外部恢复 | Z 在外部运行并核对本局记忆与状态 | 匹配后才登记迁移完成；未匹配不以成功动画遮盖 |

迁移失败同时读取阶段和原因，**公司确证隔离优先于普通设备恢复**。冻结前可取消或被隔离；传输未验收时保留源状态；被确证隔离后，保留源状态只防止 Z 被错误销毁，不恢复玩家权限、已用凭证、失去的窗口或公司的已知信息，本次执行失败。普通校验/连接故障只有在窗口、权限与未隔离条件仍成立时才能恢复。交接后的网络确认延迟通过查询唯一交接 ID 恢复，不能重复提交造出两个 Z。游戏中这些是确定的叙事与状态规则，现实分布式系统或意识同一性不能由此推定。

所谓“逃走”必须包含玩家可操作的路径：进入合法维护点准备设备 → Z 从受限区到达接口 → 两侧按约定处理障碍 → 冻结/传输期间玩家保护窗口 → 外部恢复验证。不能只在结尾点击一个进度条。

## 10. 存档、失败与离线模式

存档包含版本、规则版本、世界快照、待处理行动、金币与库存占用、唯一事务ID、任务图状态、已结算结果、事件记录、角色知识、有效约定、关系、公开许可、直播消息/回应引用、连麦报名与抽选结果、节目推进收据、必要的生成文本缓存。模型供应商、模型名称与生成版本可作诊断元数据，但换模型不能改变已经发生的事实。

- 在日初、重大抉择前、视角切换前后、比赛阶段结束时自动存档。
- 异步 AI 请求绑定 run_id、load_epoch、world_revision、actor_id、目标、action_id/receipt_id 和 request_id。恢复 pending 后重新构造上下文，旧请求失效；相同修订号的旧档也不能重新接纳旧请求。确认意图前要求原快照仍有效；提交后生成的表现只可引用对应收据，不再修改世界。回应已采用作者回退后又迟到，只作为诊断结果丢弃，不覆盖当前台词和选择。
- 已提交的动作重放动画不重复扣费或发奖；读档恢复网络请求不重新执行动作。
- 保存采用临时文件、校验、替换与一份备份；坏档恢复时告知使用了哪个版本，不悄悄重置记忆。
- 老版本存档迁移采用显式版本转换；开发阶段可标记不兼容，面向玩家承诺后必须验证。
- 主线与核心动作离线可完成；自由聊天与个性化措辞降级为基于同一事实的作者文本。界面简短说明当前为离线回应，不冒充模型理解结果。

模型网络等待本身不推进时钟、不扣新成本。确认前的澄清可重试、改用快捷句或免费取消；已经确认但尚在 pending 的行动，应恢复有限输入并按同一规则正常提交一次成本，不能因为断网变成免费工作。已提交的行动只补展示，不重复收费。存档/替换失败与模型失败分开处理：前者须恢复可信快照或保留 pending 并报告，不能继续显示“已保存”；后者可用作者文本继续核心玩法。

本次资源规则若用于迁移旧测试档：版本化转换将`credits/credits_delta`映射到`gold/gold_delta`并保留原金额，移除`energy/stamina`及其上限、恢复、占用和门槛，不转成另一种隐藏预算。保留原时钟、实际金币/库存收据和履约事实；对尚未提交的旧pending仅删除被取消资源的预留，金币/库存占用及已确认动作继续按明确版本规则恢复。已提交结果不因删除资源字段而退款、重发工资或重演贡献。当前尚无真实存档迁移通过证据，不能把此规则描述为已支持玩家长期旧档。

检查点须覆盖 pending 保存后、规则结果已算出但未写盘、收据已落盘但未播放、AI 等待中和换视角中。调试导出包含版本、输入序列、初末状态、收据/事实/任务变化与回退原因，不包含密钥。所谓“一次结算”只针对同一个存档分支中同一个 action_id；玩家主动载入更早快照后重新选择是合法重玩，不能拿机器外的全局已领表阻止旧档发放正常奖励。

## 11. 性能、费用与数据边界

模型性能指标为原型验收目标，非现有实测：普通对话开始可读回应尽量在 2 秒内，完成回应 P95 目标 8 秒内；超过预设超时可使用作者回退，回退入口不应阻塞整局。先真实测量再选择供应商与上下文长度，不预设某款模型一定达标。

费用按每次有效调用记录输入、输出、缓存命中、重试与模型。估算公式：

```text
单局AI费用 = Σ(输入token × 输入单价 + 输出token × 输出单价
              + 对应缓存/服务费用) + 所有重试成本
```

仅作算量示例：每局 160 次调用、平均每次 4,000 输入与 250 输出 token，对应约 64 万输入、4 万输出 token；不含额外意图识别、校验调用与重试。实际调用数需要由一段完整体验测出来，不能把这个例子当成已知单局成本或服务报价。

正式联网版通过受控服务端代理管理凭据、预算与失败切换；分发客户端不内置开发者长期密钥。开发原型可用本地配置，密钥不进版本控制。无需在本轮购买服务或部署后端。

只上传当轮必要的游戏事实和玩家主动输入；不能为角色更懂玩家而扫描设备或个人文件。提供清楚的 AI 联网说明、清空/导出游戏记录入口，以及可选的诊断日志。日志默认脱敏，不保存密钥；外部模型的留存政策和用户条款在供应商确定后查官方资料并落实，当前不虚构“数据绝不留存”。

## 12. 内容作者模板

每个任务单元至少填写：

| 字段 | 必填内容 |
|---|---|
| 目的 | 玩家想达成什么，Z/其他人物各想什么 |
| 入口 | 触发时段、人物、前置、玩家如何知道可做 |
| 方法 | 至少对核心障碍提供两种成本不同的解法 |
| 成本 | 时间、金币、物品；另记录人物承诺和可预见风险，不能伪装成可刷减的隐藏资源 |
| 结算 | 哪些世界事实、权限、关系、记忆具体变化 |
| 失败 | 错过、拒绝、材料不足、被发现各怎样继续 |
| 知识 | 谁见过、谁收到消息、公司能记录什么 |
| 复用 | 哪个工作/活动/UI模板承载，不默认新增小游戏 |
| 表现 | 场景、角色动画、音效、对白长度、演出可跳过性 |
| 保存点 | 进入前、执行中、完成后哪些状态要恢复 |
| 验收 | 成功、替代解、失败、顺序变化、读档、AI降级 |

一个剧情节点写完并不意味着完成一条任务。至少需要在灰盒中执行成功和失败路径，再开始生产昂贵的正式演出。

## 13. 开发验收用例

这些是待执行的用例，不是“已通过”的测试结果。首个Demo执行A01—A09、A16、A18及下述A19—A29中适用的切片情境；A10—A15、A17的决赛/迁移/身份内容属于完整游戏或单独内部验证，不作为公开D1—D3的内容要求。切片精确步骤与通过门槛见[Demo验收表](D1-D3-Demo开发与验收规格-v2.md)。

| ID | 情境 | 必须满足 |
|---|---|---|
| A01 | 玩家说“昨天我们看过流星”，但事件中没有 | Z 不将其当作共同经历，最终演讲不引用 |
| A02 | 玩家称自己已得到灯塔管理员许可 | 对话可以讨论，门禁状态不变 |
| A03 | 对同一约定用五种近义表达 | 实质意图与成本一致；模糊版本先澄清 |
| A04 | 连续重复称赞/送同一类礼物 | 不出现无穷识别/信任收益；合法礼物仍按购买规则结算 |
| A05 | 玩家拒绝公开一段回忆 | 私下知情者仍能回忆和讨论；公开节目、演讲和评论均不能泄露具体私密内容 |
| A06 | Z 视角发现材料但没有送出 | 玩家角色无法引用此材料说服别人 |
| A07 | 一侧动作依赖另一侧完成 | 世界时钟按因果顺序推进，不把依赖任务并行省时 |
| A08 | 模型请求未返回时载入另一个档 | 旧回应不污染新存档，不发放旧事件奖励 |
| A09 | 在购买/工作/赠礼结算后重载多次 | 金币、物品、时间只结算一次；AI生成失败只回退表达，不撤销已完成劳动或已交付礼物 |
| A10 | 相同状态分别联网、断网完成决赛 | 比赛与路线结果相同，只有表现文本不同 |
| A11 | 玩家愿意逃离，但 Z 未同意 | 不能在 Z 视角强行提交迁移；可继续解释或换方案 |
| A12 | 转移到一半断线/保存恢复 | 源状态未被错误销毁，无重复当前实例与重复收据 |
| A13 | 身份已在第二章确认 | 后续模型不得再次扮演完全不知道自己是AI；情绪疑问可以延续 |
| A14 | 胜出比赛但未获运行安排 | 结尾明确仍受控制；不播放独立生活成功场景 |
| A15 | 比赛失利、迁移完成、友情成立 | 获得自由与友情相伴结尾，不强制升级恋爱 |
| A16 | 极长输入、乱码、游戏外命令 | 输入受限并可继续游戏，不暴露内部提示或执行系统命令 |
| A17 | 传输中被公司确证并隔离 | 源状态保留，但本次执行失败，不能伪装成网络故障继续重试 |
| A18 | D2 不同本局经历触发 Z 的小提议 | 提议来自合法候选，与经历有关；玩家接受/修改后 D3 实际行动和反馈不同 |
| A19 | 11:00 开始 60 分钟工作 / 11:01 开始同一工作 | 前者 12:00 完成后关闭窗口；后者确认前拒绝，无成本 |
| A20 | 接任务前已持有材料 / 只持有并称已交付 | state 目标立即可满足，event 交付目标仍未满足；不伪造交接事实 |
| A21 | 物品已被 pending 占用，尝试出售或二次制作 | 可用数量扣除占用；第二操作被拒绝，恢复后占用能正确释放 |
| A22 | 同一行为换 event_id 或五种措辞再结算 | 请求幂等与语义贡献上限都生效；新合法班次仍能正常领工资 |
| A23 | 完成后换场景/重发通知/载入相同修订旧档 | 通知不再发奖；旧 AI 请求因 load_epoch 不符而丢弃 |
| A24 | 未接受、已接受到期、失败后补做的三份存档 | 分别为无承诺、missed、原 missed＋repair；模型台词不篡改状态 |
| A25 | 同一直播段发送多条弹幕、长时间输入/等待模型；再确认本段进展并重复提交 | 输入与等待不加分钟；只由segment_advance结算该窗口一次40分钟；三段合计120分钟 |
| A26 | 同一赠礼request重发；随后有意送第二份礼物并发送新消息；推进节目后载入收据 | 重发只结算一次，新礼物/消息不被段级键吞掉；金币/库存按真实动作变化；同类关系贡献仍有上限 |
| A27 | 不报名；报名后退出；报名未抽中；中选后未确认接通 | 不自动连麦、不扣费、不写双向交流/失约；未抽中仍可通过免费弹幕/投稿满足相同主线条件，已抽结果不在恢复时重抽 |
| A28 | 匿名弹幕称玩家已完成任务、获许可或双方有共同往事 | 仅保存观众主张，不能获得玩家事实、权限或关系贡献；Z只能据实际来源回应；已发送与被回应状态分离 |
| A29 | 金币0且时间窗口合法直接工作；载入旧资源字段测试档或不兼容档 | 无恢复门槛或替代每日预算；工资、时间、库存保持一次结算；受支持版本按显式转换保留原金币与分钟，否则明确拒绝不静默重置 |

验证分层：状态规则单元/回放检查 → 任务集成流程 → 固定 AI 评估样本 → 人工试玩。模型变更先跑相同事实与错误注入样本，再决定是否投入公开构建。自动校验只能证明覆盖的条件，不替代对人物语气、节奏与情感可信度的人工判断。
