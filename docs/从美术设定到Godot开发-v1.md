# 从美术设定到 Godot 开发 v1

日期：2026-10-11。性质：美术生产与引擎落地说明；尺寸、地图规模与节点组织均为待验证提案。范围和验收仍以 [D1—D3 规格](D1-D3-Demo开发与验收规格-v2.md)、[AI 与状态规格](AI与状态规格-v2.md)及[技术方案 G0—G6](开发准备与技术方案-v2.md#93-开发阶段的进入与退出条件)为准。

**建议采用 Godot 4 + GDScript，白天制作固定视角的纯 2D 斜俯视世界，夜间切到玩家手机中的 Z 近景直播。**本轮检索未发现 `project.godot`、`.gd`、`.tscn` 等工程文件；现有 PNG 与 HTML 是静态设定。Godot 适合这条路线，但尚未建立或验证工程，也未冻结版本。

2026-10-11 用户已取消精力机制，货币统一为金币（`gold` / `gold_delta`）；时间、金币与实际库存由同一规则层结算，UI 不保留隐藏精力逻辑。普通走路、读字、打字与 AI 等待不耗游戏时间，夜间由明确的节目推进一次结算时段，单条弹幕不推进整段。旧 `ui/v1` 和 `ui/chapter1-pixel-v2` 的精力、岛券及现场俯视直播仅作历史稿；新手机方案见[交互与美术专项](手机直播交互与美术方案-v1.md)，已选 C 横屏 PC 方向继续细化，[v2 本地交互设计预览](../ui/live-phone-v2/index.html)尚未最终批准，旧三方案保留比较。

## 1. 三种分层分别负责什么

美术分层使地面、建筑、人物可以独立编辑；绘制排序决定人物走到桌前或桌后时谁遮住谁；碰撞、交互与导航数据决定哪里能走、能操作什么。这三者需要分别制作。整张概念 PNG 不包含被遮住的地面、动画、碰撞或权限，不能靠自动抠图变成完整游戏资源。

| 内容 | 建议节点 | 落地要点 |
|---|---|---|
| 海面、道路、地板 | `TileMapLayer` + `TileSet`；独特底图可用 `Sprite2D` | 重复纹理铺图块；大建筑无需强制切成小格 |
| 人物、树与可绕行家具 | 同一 `Node2D` 排序空间；人物用 `CharacterBody2D`，附 `CollisionShape2D`、`AnimatedSprite2D` | 父级启用 `y_sort_enabled`，脚底为原点；共同排序对象保持相同有效 `z_index` |
| 屋顶、树冠、前墙 | 独立 `Sprite2D` 或前景 `TileMapLayer` | 按遮挡需要拆段；遮住操作位置时可淡化 |
| 门与交互物 | `Node2D` 场景 + `Sprite2D`；`StaticBody2D` 与 `Area2D` 各附自己的 `CollisionShape2D` | 碰撞与交互范围分别配置；视觉读取已提交状态 |
| 明暗与灯光 | `CanvasModulate`、`PointLight2D`、`LightOccluder2D` | 日夜环境色与局部灯光分开；投影遮挡不等于行走碰撞 |
| 界面 | 主视口下 `CanvasLayer` + `Control` | 字、按钮、头像独立于场景图，支持输入与缩放 |

门的状态、许可与交互判定归规则层；`Area2D` 检出靠近，仅提供操作入口。换场景和读档后仍显示真实状态。与[机制卡 K03](../research/动物迷城/02-Demo借鉴与验证框架.md)相连的具体例子是：白天买到的礼物进入同一份库存，晚上直播只能使用实际持有数量，不能因为画出了礼物按钮就默认已经获得。

## 2. 独立资产怎样生产

先建立清单，再分别制作地形、建筑、人物、家具、道具、头像和 UI。每项记录稳定 ID、视角、像素密度、画布、锚点及必要状态。AI 可辅助独立资产起稿；透明底、连续轮廓、统一调色板、门后地面和逐帧一致性仍需清理、补绘与检查。保留可编辑源文件，导出 PNG、图集及帧标签/时长；背景和文字不烘焙进人物图集。

**岛内行走的白发长发 Z 先比较 32×48 与 48×64 两种源画布。**检查脸部辨识、发型轮廓、转身和步行是否足够清楚，并让门、家具与其他角色按同一世界尺度配套。不能给 Z 单独加密像素，也不能直接冻结旧提案的 32×48。世界视口与图块尺寸同样通过小样确定；该规格不用于手机近景角色。

四方向、每方向待机 2 帧与步行 6 帧，仅基础动作就是每人 32 个帧位；六人约 192 个帧位，交互动作另计。这是候选工作量，不等于已产出资源。长发摆动、不对称饰物使镜像复用受限，应实测完整一套动画的制作时间。用 `AnimatedSprite2D/SpriteFrames` 播放帧序，属性联动演出交给 `AnimationPlayer`。

**手机直播的近景 Z 单独生产。**保持同一白发角色身份，但不直接放大行走小人。先定构图、表情/动作参数表与事件映射，再画可编辑的分层角色资产，补全头发、眼、口与身体等遮挡区域。Live2D 式表现是目标，没有假定已选 SDK 或现有 PNG 可直接绑定；模型格式、绑定方式、许可和 Godot/Windows 集成要另行验证。输入、赠礼、自愿随机连麦与节目推进由规则事件驱动，动画不能反向发奖或扣时；动态不可用时允许近景静态表情加字幕回退，但不记为动态表现已验收。

## 3. 像素世界与高清中文

640×360 可作为世界视口候选。建议把世界放进独立 `SubViewport`，由 `SubViewportContainer` 或 `ViewportTexture` 显示，按整数倍率居中放大并处理余边；主视口上的 UI 按窗口分辨率排版。**单独加 CanvasLayer 不会提高渲染分辨率**：若根视口整体低清，中文也会一起变糊。

世界纹理与合成纹理采用 `Nearest`，避免插值抹平像素；中文字体独立设置。最近邻只管纹理采样，实时灯光按视口分辨率计算，因此灯光也在世界视口内检查。样板需验证相机移动、脚底对齐、不同窗口尺寸和鼠标坐标映射，不能仅凭静止截图确认效果。

## 4. 岛屿、M 地图与开发顺序

大岛先用约 **3×2 个镜头范围**做布局候选；以路线辨识与空间内容密度验证，不能据此把完整岛屿塞入首个切片。场景与 M 地图读取同一份地点、道路和入口拓扑；首版支持 M 打开、M/Esc 关闭，查看全岛缩略图、当前位置、当前任务与权限提示，不自动传送。缩放、平移和目的地标记可在辨识测试后决定是否需要。沿用 K01，普通行走、查看地图不推进游戏时间。已知地标、可达入口、获准进入和内部已探索分别表达；可见灯塔不意味着其内部已知或开放。地图中的人物不应成为未授权的实时追踪来源。

首先制作**一条街＋咖啡馆＋人物＋一扇门**的美术技术样板，验证比例、走动、遮挡、进出与中文。它可在 G0 锁定工具时并行探索，完成后作为 G2 的资产输入；美术样板通过不代表规则验收通过。

主流程仍是：G0 建立入口与数据身份；G1 验证确定性行动、时间/资源、任务和存档；G2 接入 D1 灰盒链；G3 跑通 D1—D3 两路及补救；G4 验证受限 Z 视角；G5 接真实 AI 与降级；G6 在目标 Windows 机器验收。模型表达读取事实，不能代替规则生成权限或物品。所有这些阶段目前仍需实际实施与验证。
