# 像素 CRPG：工具选择、资产生产与版本迭代

调研日期：2026-10-13。适用情境：单人开发、Codex 为主要执行工具、Godot 为运行引擎，目标是具有《动物迷城》式空间探索、关系、资源与任务联系的像素 CRPG。

本文是工具选型与流程建议，不是已经批准的美术规格或机制改版。本轮读取了当前工程、既有研究和官方工具文档；没有运行生成任务、安装插件、重新验收游戏、提交或推送 Git。下面区分当前事实、工程判断与待验证建议。

**结论：保留 Codex + Godot，把生产单位从“整套设定集”改为“有规格、可编辑、能导出、能验收的独立资产与场景”。优先补 Aseprite、资产清单和 Git 基线。**

美术设定集承担风格与气氛表达；生产资产承担图像、动画与空间结构；玩法规格承担条件、代价和结果。只给设定集让 Codex 复刻，会迫使它临场补完后两部分，这正是不一致和返工的主要来源。

**2. 适合你的最小工具组合**

| 工具/平台 | 在流程中的职责 | 建议优先级 |
|---|---|---|
| **Codex** | 维护规格与清单，组织批量任务，调用 CLI/API，编写规则和工具，执行导入、构建与检查 | 继续作为主控；把反复操作沉淀到脚本、模板与项目指引 |
| **Godot + GDScript** | 场景、移动、碰撞、交互、UI、音频、存档、导出和最终验收 | 保留当前引擎，固定当前可工作的版本及导出模板 |
| **Aseprite** | 像素源稿、图层、逐帧动画、Tag、调色板、确定性导出 | 优先补齐；至少学会开稿、图层、帧、锚点、导出与预览 |
| **PixelLab MCP / API** | 程序化生成角色方向、动画、地形、透明物件等候选资产 | 推荐用一个小批次验证质量和成本后接入 |
| **Aseprite Wizard** | 将 Aseprite 源稿和动画信息导入 Godot | 先验证一个角色，兼容后复用；不先写通用导入器 |
| **Git + 私有 GitHub 仓库 + GitHub Desktop** | 本地历史、远程副本、分支、版本标签及可视化查看变更 | 最先建立；Desktop 方便你直接看清 Codex 改了什么 |
| **项目内 Markdown + CSV/JSON** | 策划规则、资产清单、任务与参数的可读源数据 | 现在足够；避免文档、表格、脚本中各维护一份冲突数值 |

PixelLab 官方提供 MCP、REST v2 与 SDK，可提交异步角色、动画、tileset 和物件任务。[官方 MCP](https://www.pixellab.ai/mcp)、[API 文档入口](https://api.pixellab.ai/v2/llms.txt)

Aseprite 官方 CLI 支持批量导出 PNG 图集、JSON、帧标签与切片数据；这能把“每次手工重新导出”变为固定命令。[Aseprite CLI](https://www.aseprite.org/docs/cli/)

Aseprite Wizard 的 Godot 4 分支支持 SpriteFrames、Tag 动画、帧时长和重导入。它是第三方插件；“支持 Godot 4”不能替代在本项目具体版本上的兼容验证。[作者仓库](https://github.com/viniciusgerevini/godot-aseprite-wizard)

GitHub Desktop 提供提交、分支和推送的图形界面；这些操作也可以交给 Codex，Desktop 用作你独立查看工程状态的入口。[官方入门](https://docs.github.com/en/desktop/overview/getting-started-with-github-desktop)

以下按需要增加：

| 工具 | 什么时候有价值 | 当前取舍 |
|---|---|---|
| **Godot TileMapLayer + TileSet** | 地面、道路、墙面需要反复铺设、连接、编辑 | 新增地图内容的优先选择；独特建筑和交互物件继续做独立场景，不要求立即重写全部旧地图 |
| **Tiled** | 地图很多、需要专门关卡编辑和更复杂规则铺图 | 备选。官方已支持 Godot 4 `.tscn` 导出，但对象与资源路径有约束，导出文件可能被覆盖 |
| **LDtk** | 希望用 IntGrid、自动图层和实体字段快速编辑关卡 | 与 Tiled 二选一；Godot 导入器的维护和版本适配需先验证 |
| **Dialogue Manager** | 分支对白和条件文本多到手写管理困难 | 优先考虑脚本式文本，适合 Codex；已有对话和状态系统不用仅为换工具而迁移 |
| **Dialogic** | 更偏重可视化演出、时间线和立绘编排 | 对白工具的另一选择；起步不同时接两套 |
| **Audacity** | 修剪音效、处理音频、准备循环素材 | 音频生产需要时再加 |
| **GitHub Releases** | 保存每个里程碑可下载的游戏运行包及说明 | 开发里程碑即可使用；自动源码 ZIP 不是可执行游戏包 |
| **Steamworks** | 面向 Steam 发布和分发 | 后期发布环节；不会替代资产生产和版本管理 |

地图选型依据：[Godot TileMap](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)、[Tiled Godot 导出](https://doc.mapeditor.org/en/stable/manual/export-tscn/)、[LDtk 自动图层](https://ldtk.io/docs/general/auto-layers/)、[LDtk 集成索引](https://ldtk.io/api/)。

对白及辅助工具依据：[Dialogue Manager](https://github.com/nathanhoad/godot_dialogue_manager)、[Dialogic](https://docs.dialogic.pro/)、[Audacity](https://www.audacityteam.org/)、[GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。Dialogue Manager 的当前主版本声明适用 Godot 4.6+；选择插件时应固定发布版本，不能盲目跟随主分支。

暂时不建议为这四个问题换 Unity/Unreal，也不建议同时建立 Blender、Figma、Tiled、LDtk 多套生产路径。它们各有用途，但当前需要先贯通一条可重复使用的路径。这里推荐的是适合你的工具组合，不是在声称《动物迷城》开发团队实际采用了同样软件。

**3. 卡点一：怎样让资产生成流程化**

从“让 Codex 再画一张桌子”变为“让 Codex 处理清单里待制作的家具，并提交可验收候选”。

```text
冻结少量风格与规格样板
        ↓
资产清单 → 生成候选 → 自动检查 → 视觉审查/精修
                                    ↓
                       Aseprite 源稿 → 固定导出
                                    ↓
                       Godot 样板场景 → 验收
                                    ↓
                      启用该修订 → 版本提交
```

AI 生成阶段存在变化；整理完成后的源稿、导出和引擎装配应尽可能确定。保存最终文件，不能把“下次用同一个提示词/seed 再生成”作为备份办法。

建议资产清单至少包含：

| 字段 | 用途 |
|---|---|
| `asset_id`、`type` | 稳定身份与资产类别，避免依赖易变的中文文件名或图集第几格 |
| `spec_version` | 使用哪一套尺寸、视角、色板和动画规格 |
| `source_path`、`export_path` | 可编辑源文件与运行导出文件分别在哪里 |
| `canvas`、`content_height`、`anchor` | 画布、内容比例和原点，三者不要混为一个尺寸 |
| `directions`、`animations` | 需要哪些方向、状态和动作 |
| `reference_id`、`reference_hash` | 使用哪组已认可的视觉样板 |
| `status`、`active_revision`、`candidate_revision` | 正在用哪版，正在制作哪版；重做候选不立即覆盖已用版本 |
| `generator/model`、`parameters`、`job_id` | 追踪生成来源、参数和异步作业 |
| `file_hash`、`source/license` | 校验文件一致性，记录来源及许可 |

起步可以用一张 CSV 加每项 JSON 元数据，无需先做资产管理网站。

批处理规则应写进项目脚本/指引：

1. 默认只处理待制作或明确指定要修订的资产，跳过已验收版本。
2. 同一批共享已认可的色板、视角、光向、像素密度和参考图；先做一个合格样板再扩大数量。
3. 记录 job ID 与已下载文件；请求超时后先查原任务，避免直接重复提交导致重复扣费。
4. 设置批量上限、重试次数与成本上限；低质量资产进入修订队列，不无限重生成。
5. 输出接触表、动画预览和 Godot 样板截图，集中审查。
6. 只有通过检查的修订才切换为游戏正在引用的版本。

这些队列、缓存、重试和验收规则是建议由 Codex 建立的项目流程，不是宣称 PixelLab 已自动提供完整资产工厂。

PixelLab 不同模式的 `size`、方向和参考图参数含义不同；部分参数只是软约束。角色方向和动作连续性、Wang 地形拼接、透明物件可以借助其专门接口，但碰撞、交互点、Godot 地形规则仍需引擎数据。[官方 MCP 参数说明](https://api.pixellab.ai/mcp/docs)、[Tileset](https://www.pixellab.ai/docs/tools/create-tileset)

本会话能发现 PixelLab MCP 工具，但没有测试账号额度、授权和生成质量。工具选择最终应看一批样板的**每个合格资产总成本**：生成消耗 + 清理时间 + 引擎接入时间 + 返工；不能仅比较每张出图价格。

可以自动检查：文件是否解码、真实格式、尺寸、透明通道、帧数、命名、Tag、JSON 区域越界、源文件变更、引擎导入错误。是否同一个人、是否滑步、拼接是否突兀、光向是否一致、轮廓是否清晰和操作是否顺手，仍需看图、看动画和试玩。

**4. 卡点二：资产应交付什么格式**

统一的不是所有图片的宽高，而是同类资产的规格、世界比例、视角、光向和元数据。每类资产均考虑三层：**编辑源文件 → 运行图像/动画 → 引擎结构与行为数据**。

| 类型 | 编辑源文件 | 运行交付 | 必须附带的信息 |
|---|---|---|---|
| 主角/NPC 行走角色 | 每角色一份 `.aseprite` | RGBA PNG 图集/序列 + 帧 JSON；Godot `SpriteFrames` | 帧画布、内容高度、方向、idle/walk 等 Tag、帧时长、循环、脚底原点 |
| 地面、道路、水、墙模块 | `.aseprite` 图层/Tilemap | PNG tileset + Godot `TileSet .tres` | 图块大小、间距、边角过渡、地形连接、动画、碰撞/导航用途 |
| 树木、建筑、柜台、家具 | 分层 `.aseprite` | 透明 PNG，必要时拆底座/主体/屋顶；复用 `.tscn` | 脚底排序点、占地、遮挡、交互点、接近侧、开关/损坏等状态 |
| 世界中的物品 | `.aseprite` | 地面精灵 PNG/图集 | 物品 ID、世界比例、拾取/放置点、状态 |
| 背包和商店物品图标 | `.aseprite` | 独立图标 PNG/图集 | 与世界物品共用 ID；图标画布、留白、选中状态 |
| 头像、表情、立绘 | `.aseprite` 或分层绘画源文件 | PNG 表情集 | 画幅、脸部位置、表情 ID、显示尺度；无需与小人共用分辨率 |
| UI | Godot Theme/组件；像素装饰用 `.aseprite` | Theme `.tres`、面板/九宫格纹理、按钮组件 | 字体字号、间距、边距、普通/悬停/按下/禁用/焦点状态 |
| 地图关卡 | Godot `.tscn` + 资源；或选定的外部地图源格式 | 场景及其依赖 | 物件实例、层次、出生点、出口、触发、通行区、权限连接 |
| 特效 | `.aseprite` 或 Godot 粒子/动画资源 | 图集、动画、粒子场景 | 原点、时长、循环、叠加方式和关键事件点 |
| 对白、任务、物品定义 | 文本、CSV、JSON 或专用对白文件 | 校验后的数据/资源 | 稳定 ID、条件、成本、结果、失败、保存字段 |
| 音效/音乐 | 音频工程及高质量母带 | 按用途导出 WAV/OGG 等 | 循环点、音量、类别、来源；和画面规格分开维护 |

Aseprite Slices 可记录区域、pivot 与九宫格信息；但是否传到 Godot、哪些语义被插件使用，必须验证，不能默认从图片自动得到碰撞或完整对象逻辑。[Slices 文档](https://www.aseprite.org/docs/slices/)

地图通常组合为：地面 → 地面装饰/阴影 → 按脚底排序的人物及物件 → 屋顶/树冠等遮挡 → 独立 UI。光照遮挡、画面前后遮挡和人物行走碰撞是不同数据，不可互相替代。大树、房屋无需硬切成与地面一样大小的格子。

**可用于首轮小样的规格提案，不是已批准最终标准：**沿用 640×360 世界，地面先试 32×32；角色可试 64×64 透明帧画布、可见身体约 40 像素、统一脚底原点，先做四方向待机/走路；小物品 UI 图标先试 32×32。人物比例与门、桌、椅在同一个 Godot 场景里确认后，再决定是否放大密度。不要把这些数值当作《动物迷城》原始资产尺寸。

角色若导出裁切图集，必须保留原画布和偏移等信息；不能把每帧透明边自动剪掉以后全部强行底部居中，否则可能抖动。将 PNG 装进 `.aseprite` 只是得到可以继续编辑的文件，并不会自动恢复原来不存在的图层或动作。

以下仅演示确定性导出，假定 Aseprite 已加入 PATH，输入文件和输出目录已存在：

```sh
aseprite --batch art/source/characters/hero.aseprite \
  --sheet-type rows \
  --sheet art/staging/hero.png \
  --format json-array \
  --data art/staging/hero.json \
  --list-tags \
  --list-slices
```

`--batch` 不打开常规编辑界面；`--sheet` 写出图集，`--data` 写出帧元数据，Tags/Slices 随导出记录。相同目标文件会被覆盖，所以示例写入 staging。Godot 不会仅因旁边多了一个任意 JSON 就自动理解动画；应通过验证过的导入插件或小型转换脚本生成 SpriteFrames。插件导入和自制导出方案应明确哪个是主入口，避免两套流程同时写同一个资源。

**5. 卡点三：怎样接近认可设计，为什么仅靠设定集不能 1:1**

需要分别制定三种验收：

| 目标 | 设定图缺少的信息 | 合适的验收 |
|---|---|---|
| 画面与 UI | 原始素材、字体、字号、边距、像素密度、透明层、各种交互状态 | 固定分辨率、同状态、同资产的实机截图对照 |
| 空间与手感 | 相机视野/跟随、移动速度、脚底碰撞、遮挡、接近距离、动画时序 | 固定路线连续走图和录屏；截图只能验证部分外观 |
| CRPG 玩法 | 条件、行动成本、世界状态、NPC 日程、失败恢复、存档 | 从初始状态到结果的实际路径，含失败及读档 |

**把最终的画面认可点放到 Godot 里。**概念图用于挑方向；随后用真实生产资产搭建一个可以走动、交互的样板场景。确认这个样板后再批量生产同类内容，减少“大设定集全部画完以后才发现不能用”的损失。

当前 640×360 的世界在 1280×720、1920×1080 中可分别放大 2、3 倍；1600×900 铺满是 2.5 倍。若要求像素等宽，应选择整数缩放后留边，或设计可变可视范围/裁切规则。高清中文 UI 可继续独立铺满。当前是自定义 SubViewport + TextureRect，不能假定只改根窗口一个设置就能解决世界显示、鼠标坐标与 UI 锚点的全部问题。[Godot 多分辨率指南](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html)

像素纹理通常使用 Nearest 与无损导入；Godot 4 的 2D 过滤在 CanvasItem/项目默认设置中，不能照搬 Godot 3 的旧导入界面说明。避免把不同采样密度的高分辨率图任意缩成一套精灵。[Godot 图像导入](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_images.html)

UI 应由字体、Control、布局和 Theme 组成。概念图中烘焙的文字、按钮和装饰不能直接当作可交互 UI；应交付组件状态与布局参数。地图对象也应把图像、脚底、占地、遮挡和热点放到一个可复用定义，减少改外观时顺带改规则的机会。[Godot Theme 编辑](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_theme_editor.html)、[TileSet 数据](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html)

如果目标包含借鉴《动物迷城》的动态体验，还需要原作实机观察：角色跨过一个门宽需要多久、相机如何跟随、什么时候显示操作提示、不同角度怎样遮挡。项目现有 110 移速、42 交互半径等是调校值，不是原作实测。缺少测量时只能提出相似体验目标，不能宣称已复现原参数。

本轮参考已有研究的 **K01、K03、K05、K11**：保留行动才耗时、白天准备能在后续兑现、不同解法有不同成本、失败仍可补救。适配本项目时继续取消精力，不恢复旧资源预算；先在 D1 的现有范围验证。尤其区分“获得物品”“Z 理解”“愿意合作”“出口可用”这些状态。本文不改变机制，因此不新增已采用/已实现记录；后续实质改动再同步[机制采用记录](机制采用记录.md)。

**6. 卡点四：怎样留存完成部分并局部优化**

先建立一个真实的基线。建议首次留存顺序为：盘点唯一源文件和构建 → 配置忽略与大文件管理 → 提交代码、正式资产、规则与证据 → 打标签 → 保存运行包 → 推送到指定远程 → 用干净检出验证可恢复。

| 概念 | 对你意味着什么 |
|---|---|
| Commit | 一次有说明的文件快照；只包括提交进去的内容 |
| Branch | 从当前基线分出的修改路线；失败实验不必进入 main |
| Tag | 给某个确定的提交起一个稳定版本名，如 `v0.3.0-d1-pixel`（示例） |
| Release | 把标签、可运行包、变更说明、已知问题放到一起 |
| Push | 把本地提交传到远程；本地提交本身不等于异地副本 |
| Worktree | 同仓库另一个目录检出另一个分支，便于同时保留稳定版和实验版 |

单人阶段采用一个稳定 `main`，每轮一个短分支即可，不必设置复杂的 develop/release 多层结构。

```text
main：当前经过验收的版本
  └─ codex/cafe-ui：只调整咖啡馆界面
       ├─ 小提交
       ├─ 截图对照 + 相关玩法回归
       └─ 验收通过 → 合回 main → 达到里程碑时打标签并存运行包
```

不要按“角色做完了、地图做完了”分别长期留在互不合并的分支。稳定成果应汇合在 main；分支承载一次具体改动。Git 负责恢复旧版本，模块边界与测试负责降低破坏旧成果的概率，两者都需要。

| 文件类别 | 留存方式 |
|---|---|
| GDScript、`.tscn`、`.tres`、JSON/CSV、文档、工具脚本 | 普通 Git |
| `.uid` 和正式资产旁的 `.import` 配置 | 与原文件一起纳入 Git；不要一概当缓存排除 |
| 可编辑美术源文件、大型/频繁变化的 PNG 与音频 | 按体积和更新频率选择 Git LFS；小图标不必都用 LFS |
| `.godot/`、临时缓存、自动构建目录 | 忽略，可重建 |
| 发布 ZIP、WASM/PCK、录屏、大批候选图 | 发布附件或独立归档；不要每次构建都进入源码历史 |
| 验收基准图和关键证据 | 有选择地留存，与版本关联 |
| 玩家实际存档 | 独立备份；固定测试样本可作为测试夹具 |

Godot 的缓存与资源身份文件需要区别处理。[Godot 版本控制](https://docs.godotengine.org/en/stable/tutorials/best_practices/version_control_systems.html)、[UID 官方说明](https://godotengine.org/article/uid-changes-coming-to-godot-4-4/)

Git LFS 将大文件内容放在独立存储中，Git 中记录指针。应在首次提交前确定规则，并提交 `.gitattributes`；LFS 不会让二进制源文件变成可逐行合并的文本，备份也需要包含真实大文件。[LFS 配置](https://docs.github.com/en/repositories/working-with-files/managing-large-files/configuring-git-large-file-storage)、[仓库备份](https://docs.github.com/en/repositories/archiving-a-github-repository/backing-up-a-repository)

开始并行使用多个 Codex 会话时，再引入 worktree，并约定各自修改范围。当前所有文件未跟踪，必须先有基线；新 worktree 不会自动携带当前目录里的未提交研究与美术。[Git worktree](https://git-scm.com/docs/git-worktree)

还有一个本项目已有的实际边界：存档代码会检查 `SAVE_VERSION` 和 `RULES_VERSION`，不匹配会拒绝读取。发布时应写明兼容存档范围；规则变更选择做迁移或新开档。Git 回退代码不会自动回退 `user://` 的玩家数据。同名 Godot 项目的两个 worktree 还可能使用同一份默认用户目录，应复用现有测试的隔离方式。[当前读档实现](../game/core/day_state.gd)、[Godot 用户数据路径](https://docs.godotengine.org/en/stable/tutorials/io/data_paths.html)

**7. 从现在开始的开发流程**

| 阶段 | 具体工作 | 进入下一步的条件 |
|---|---|---|
| 0. 保存基线 | 整理 Git、源资产和已有运行包；标注已验证/待完善内容 | 干净检出能恢复当前工程与必需资产 |
| 1. 冻结最小体验 | 选一段地图和一条现有玩法链，列出动作、条件、资源与结果 | 可说明玩家每步做什么，以及怎样判断成功/失败 |
| 2. 建立视觉格尺 | 世界视口、缩放、角色/门桌比例、光向、色板、字体与交互参数 | 少量样板在实际目标窗口里看起来协调 |
| 3. 制作生产样板 | 一名角色、一扇门、一张桌、一个 NPC、一组地面、一件物品和一套对话/背包组件 | 源文件、导出、元数据和 Godot 使用都贯通 |
| 4. 验收引擎样板 | 固定截图 + 连续走图 + 一次行为结果和读档 | 你认可实际游戏表现，记录基准版本 |
| 5. 批量生产 | 按清单生产相同类型，失败项单独修订 | 资产检查通过，新增内容遵守同一接口 |
| 6. 按功能迭代 | 每轮一个分支，只做一个变化，复用组件 | 相关回归通过，没有混入无关改版 |
| 7. 留存里程碑 | 合并、标签、运行包、截图、已知问题、存档兼容说明 | 旧版随时能打开，新版差异可以解释 |

建议直接用已有“码头一段街 → 咖啡馆门 → 室内桌子 → 柜台 NPC”做样板，无需另造一套 Demo。

样板的验收应包含：正常走路不耗游戏时间；进入房间、绕桌、走到物件前后；仅在合法距离与接近侧显示交互；对话或购买产生正确结果；金币/库存/时间按当前活动规则结算一次；退出后读档恢复；两个目标窗口中文和像素显示正常。

再做一个对流程特别有效的检查：**只替换桌子外观，门、NPC、任务与存档继续正确；只改对话 UI，世界空间和资源结算保持原有行为。**这直接验证你最关心的局部优化能力。

保留现有 `game/tests/`；先补资产检查、固定状态截图与必要行为回归，不必先把所有测试迁到新框架。Godot 可通过命令行做导入和导出，适合交给 Codex 自动执行；无窗口检查不能代替真实渲染与手感验证。[Godot 命令行](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

**8. 以后交给 Codex 的任务可以这样写**

首次建立基线：

> 盘点当前工程、正式美术、唯一源文件、生成缓存、历史构建和运行证据。准备根目录忽略规则与 Git LFS 分类，保存现有可玩版本，确保 AGENTS 和研究资料在恢复范围内。建立首次基线提交，并用干净检出验证能打开与运行。报告纳入了什么、哪些大文件另行归档、哪些内容尚未验收；远程仓库使用我指定的目标。

建立资产生产入口：

> 以已认可的角色和咖啡馆样板为基准，建立机器可读资产清单与规格检查。先贯通一名角色、一扇门、一张桌和一组地面的生成候选、精修源稿、导出、Godot 导入与预览。优先复用 Aseprite CLI 和已验证的导入插件；只写本项目需要的调度和检查。候选与正在用的版本分开，保存 job ID、参数、文件和修订。完成样板验收后再扩展数量。

批量制作某类资产：

> 按资产清单制作所有待制作的咖啡馆家具，使用已认可的视角、色板和像素密度。先报告数量与生成预算，按预算执行。跳过已验收资产；失败项记录原因并单独修订。输出源稿、PNG、锚点/占地/遮挡/热点数据、预览接触表和 Godot 样板截图；没有通过检查的候选不要成为正式场景引用。

只优化一个模块：

> 从已验收的 main 创建 codex/cafe-ui 分支。本轮只优化咖啡馆对话界面，先列预计修改文件和验收标准。保持时间、金币、背包、赠礼与存档的既有行为。完成后按固定状态和分辨率截图对照并运行相关回归；提交本轮改动，报告 commit、改动和未验证项，交付验收后再合并。

恢复以前效果：

> 先保护当前未提交工作，再从指定标签建立用于查看的分支或 worktree，恢复当时代码、资产和依赖。使用独立存档目录启动，比较当前版与旧版差异。若只需恢复旧版某个模块，评估与当前规则的兼容后做一次新的恢复提交。

以上是未来任务模板，本轮没有执行这些工程操作。

**9. 投入顺序与调研边界**

第一优先：建立可恢复基线。第二优先：用现有咖啡馆打通一套真正可重复生产的资产和引擎样板。第三优先：将成功流程用于更多角色、地图与任务。工具越多不代表流程越完整；先验证这一小条链的质量、返工量和成本。

发布到 Steam 时，再按当时的 Content Survey 如实填报实际随游戏交付的 AI 生成美术、文本等；预生成内容和运行时生成内容的申报不同。这是发布流程中的一项，不替代美术质量检查。[Steamworks 内容问卷](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)

本报告没有对生成服务做质量横评，没有验证插件与当前 Godot 的实际兼容，没有测量《动物迷城》运行参数，也没有估计完整游戏工期。推荐来自官方能力资料与本工程的具体缺口；正式增加依赖前，用上述小样完成验证即可。
