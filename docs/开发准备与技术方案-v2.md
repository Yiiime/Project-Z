# 《来自月亮的 Z》开发准备与技术方案 v2

日期：2026-10-11 更新。性质：完整方案的生产准备与 D1—D3 开发阶段规格；不是已实现工程、已通过验收、已批准工期或采购承诺。外部工具资料保留前轮 2026-10-10 的查阅快照；本轮同步“取消精力、货币改为金币、夜间改为手机直播”的方向，没有新增引擎、插件或供应商选型。

## 1. 当前基线与本轮建议

**先做可独立测试的确定性基础，再做纯 2D 灰盒切片，最后把受约束的 AI 接到已能以作者文本跑通的 D1—D3 循环上。**单人开发的主要风险是地图状态、人物日程、任务分支和内容生产互相放大；引擎选择并不能消除这些成本。

本轮采用的最新项目条件：

- 完整游戏为 21 天、四章节；白天在定时日程下自由行动、积累资源与人脉，夜晚在手机中观看白发 Z 的近景直播，发送弹幕、赠礼及自愿报名随机连麦。
- 用户已取消精力机制，行动只按规则推进时间；金币（`gold` / `gold_delta`）和库存照常支出，不增加替代的疲劳预算。普通行走、读字、输入与 AI 等待不耗游戏时间；节目推进一次结算时段，单条弹幕不扣整段时间。
- 用户要求借鉴《动物迷城》的玩法、UI 和画风；本轮主方案建议人形角色像素化、纯 2D 俯视或斜俯视的上帝视角。**纯 2D 是待验证的默认技术提案，用户并未单独确认这一简化。**人物、地图、台词和资产原创；旧横向 2.5D 静态图不是新管线的可直接使用资产。
- 单人承担设计、程序、美术、内容与整合；PC 优先，先做约 30 分钟 Demo。iOS 是后续候选。
- 持有证据、Z 得知或理解、同意合作、出口可用与实际迁移完成仍分别记录；AI 不拥有改写事实和发放权限的权力。
- 本轮只研究与准备，没有安装引擎、插件、SDK，没有实现游戏、调用付费模型或发布构建。

本轮主方案提供的生产口径：完整游戏约 6—8 小时，玩家、Z 加 8 位配角（其中两位 AI 对手），8 个室内场景，24 个核心任务加 12 个支线单元，12 项技能、30 件功能物品，3 类活动模板、12 个共同记忆节点、4 段 Z 的短 POV（合计约 10—15 分钟）、3 条主要路线。Demo 为第 1—3 日、主路径约 30 分钟，自由探索可到约 40 分钟，4 位功能 NPC。这里用于一致地核算生产量，不把主方案中的建议自动升级为已逐项批准的需求。

**现状核查：**2026-10-10 在工作区检索未发现 project.godot、.gd、.tscn、Unity 场景、C# 游戏工程等入口；可见交付主要是文档、PNG、HTML 查看器和清单。不能将静态按钮、旧界面自检或图片生成记录视为可玩系统验证。

下文所有分辨率、素材数量、时长、性能和工期数值均为**工程提案或估算假设**，不是《动物迷城》内部规格，也不是用户已逐项确认的范围。主玩法文件最终确定范围后，按第 10 节公式重算。

| 证据 | 可用结论 | 对本项目的影响 |
|---|---|---|

### 2.1 社区源码发现转成哪些工程约束

依据为固定 commit 的[社区源码深读第 2—6 节](../research/动物迷城/05-社区源码深读与Z实现参考.md)及其四份证据笔记。这些是社区实现及静态风险，不是原作完整源码或已复现的游戏 bug。保留 K01/K03 的跨系统时间因果、K04 的关系依据、K05/K10 的不同准备路径和 K11/K12 的恢复与分离结算；Z 自己拥有规则层，无须复制 Mod 对外部游戏的观察手段。

| 研究发现 | Z 的工程边界 | 在哪一阶段证明 |
|---|---|---|
| 时间 Hook 观察原生方法结果，任务约 0.2 秒轮询可能漏过中间状态 | 行动提交直接产生可追溯结果；UI 可订阅通知，时间、任务与奖励不得依靠轮询 UI 差分触发 | G1 规则，G2 场景集成 |
| `Scheduled` 仅是排队，社区 `Succeeded` 同时覆盖排队与已应用 | 不使用通用成功 bool 宣告世界变化；请求、持久化 pending、最终结果与表现状态分开 | G1，G5 异步恢复 |
| 苹果示例的库存触发没有证明床边交付 | 持有、展示、交付、对方知情与任务结算分别使用实际事实条件；对白和勾选不创建事实 | G2，G3 |
| 关系事件可能采用请求参数，物品事件有请求量与真实变化的差异 | 行动结果记录本次实际变化及未生效原因；不能用预期增量生成已发生的关系、消费或奖励 | G1，G2 |
| 跨读档队列与观察基线存在条件性风险；目标位置索引有升级风险 | 存档作用域、加载代次、稳定任务/目标 ID、显式版本迁移；载入后从事实重建视图而不补发奖励 | G1，G4，G5 |

阶段编号见第 9.3 节。具体源码与读取范围仍保留在研究笔记，本文件不复制代码或把其 Hook 安装方式作为游戏架构。

## 3. 引擎选择：默认 Godot，已有 Unity 专长时保留 Unity

**无已知的成熟 Unity 工程或个人熟练度优势时，建议 Godot 4.x + GDScript；若开发者已经熟练掌握 Unity/C# 和相关资产管线，优先 Unity，不为理论轻量重新学习整套工具。**这是一项结合本项目的判断，不是通用排名。

| 维度 | Godot | Unity 2D | 本项目判断 |
|---|---|---|---|
| 2D 场景 | 原生 2D 节点、TileMapLayer、TileSet、碰撞与排序 | Sprite、Tilemap、2D 碰撞、动画与 Pixel Perfect Camera | 两者足够；本项目没有必须依赖 3D 管线的功能 |
| 数据与编辑 | 自定义 Resource 可在 Inspector 编辑并保存为文本 .tres | ScriptableObject 适合作为共享定义资产 | 静态定义与运行存档分开；不要让编辑资产直接承担玩家存档 |
| 开发复杂度 | GDScript 与场景系统直接配合，适合较小工程 | C# 类型体系与成熟生态适合已有经验者 | 首次开发优先减少插件和工具数量；个人熟练度可能逆转选择 |
| 像素清晰度 | 固定世界视口、整数缩放及独立 UI 层需要验证 | 官方 Pixel Perfect 包辅助参考分辨率、像素对齐 | 不因装了组件就认定所有缩放和相机运动无抖动 |
| 对话工具 | 可考察 Dialogue Manager | 可考察既有 Unity 对话工具；本轮未为其选定插件 | 只选一个对话运行时，任务事实由自己的规则层保管 |
| 后续 iOS | 官方导出经 macOS/Xcode；GDScript 路线更直接，官方当前仍将 C# iOS 标为实验性 | 有完整移动端流程，但触控、输入法与设备验证仍需单列 | PC Demo 不承担 iOS 验收；接口先避免绑死鼠标和键盘 |

官方依据：[Godot TileMapLayer 工作流](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)、[Godot Resource](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)、[Unity 6.3 2D 工作流](https://docs.unity3d.com/6000.3/Documentation/Manual/2d-game-creation-wokflow.html)、[Unity Pixel Perfect](https://docs.unity3d.com/Packages/com.unity.2d.pixel-perfect@5.0/manual/index.html)、[Unity ScriptableObject](https://docs.unity3d.com/6000.3/Documentation/Manual/class-ScriptableObject.html)、[Godot iOS 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html)。文档中的具体包示例不等于本项目已安装或已验证兼容。

## 4. 运行架构：只有规则层能改变世界

### 4.1 规则核心与外部适配分开

| 层 | 保存或执行什么 | 不应承担什么 |
|---|---|---|
| 内容定义 | 物品、动作、任务、日程、对白键、NPC 身份、地图入口 | 本次周目的可变结果 |
| 世界状态 | 时间、资产、人物位置、承诺、知识、门/设备、任务、合作与迁移阶段 | 把所有状态压成单一好感或剧情进度 |
| 规则执行 | 前置、成本、行动结算、事件顺序、失败补救、实际结果与去重 | 接受 AI 任意发奖、改权限或跳章节；读取系统现实时间自行推进世界 |
| 场景与 UI | 移动、碰撞、镜头、动画、交互入口、来源与结果反馈 | 自行认定任务完成或持有证据 |
| AI 表达适配 | 理解玩家表达、选择允许的意图、生成语气和有限反应 | 发明事实、决定最终权限、直接写存档 |

另设存档与网络适配边界。规则核心接收明确的状态、行动和必要输入，返回待提交的新状态与结果；不依赖场景树已经加载、NPC 动画结束、HTTP 返回或帧率。G1 可在无正式地图、无联网模型条件下验证。引擎场景负责输入与显示，存档适配器负责写入和恢复，网络适配器负责请求生命周期；它们不能各持一份可独立修改的货币、任务或时钟。

当前资源接口只保留所需的时间、金币和库存：金币余额 `gold`、金币变化 `gold_delta`，不保留隐藏精力状态、成本或恢复逻辑。若后续发现含旧字段的开发数据，应明确迁移或拒绝旧版本，不能继续扣旧成本。手机直播的互动提交与节目推进是不同命令：赠礼按定义只扣一次金币或库存，节目推进只结算一次对应时段，读字、发弹幕、AI 重试或表情动画不推进时钟。随机连麦必须先有玩家报名，选取结果由规则层保存；拒绝/未抽中不能堵塞弹幕与赠礼路径。

不用为小型 Demo 建立微服务、ECS 或通用脚本语言。世界规则用少量可测试对象即可；网络代理只为模型调用和密钥保护服务，不承担单人世界的实时模拟。测试可以直接调用同一套规则，不另写一个只供测试使用的简化玩法。

### 4.2 行动有明确生命周期，成功必须对应已提交事实

字段、枚举和恢复协议以[AI 与状态规格第 3、10 节](AI与状态规格-v2.md)为准。实现必须能区分动作定义、这一次执行请求、已确认且保存的 pending、已提交结果和展示进度；不要把同名 `action_id` 同时用作动作类型与每次执行身份。重复请求返回原结果，合法的新一班工作使用新的实例身份。

**免费澄清与预览 → 玩家确认、复核状态/窗口/资源 → 保存 pending 与资源预留 → 收集活动输入 → 在候选状态中推演时间与效果 → 一次保存成本、事实、任务和结果 → 发布已提交快照 → 表现与 AI 回应。**无额外活动输入的购买可在复核后直接提交，无须人为增加等待队列。

| 阶段或情况 | 可向玩家/调用者承诺什么 | 工程处理 |
|---|---|---|
| 未确认或前置不满足 | 方法、代价或具体缺口 | 不扣费、不新增任务完成事实；预览过期后重新计算 |
| 请求收到、排队或 pending 已保存 | 已接受处理，或可恢复的行动正在进行 | 不显示已购买、已交付或已发工资；预留不能被另一行动重复使用 |
| 结果已提交 | 本次实际完成/失败的事项、实际成本、实际效果与原因 | 世界状态、任务判定、收据与去重记录一起保存；失败也可以是规则定义的完整结果 |
| 保存失败或结果不确定 | 当前操作尚不能宣告完成 | 停止新世界写入，保留同一执行身份，重试写入或恢复最后验证档；不能用新请求重做一次，也不先展示会揭露结果的演出 |
| 结果展示中断 | 已提交事实保持；可补展示 | 不重扣费、不重发奖励；网络重试只恢复表达 |

收据至少能定位执行身份、所属存档分支、行动者/目标、提交前后版本、实际时间/资源变化、产生的事实/许可/任务结果，以及拒绝或失败原因。预期变化用于预览，实际变化用于结算和反馈，不能因为二者通常相同就省掉区分。任何通用 `success=true` 都不足以替代这些证据。

UI、对话和任务监听器只读取已提交结果；它们崩溃、晚订阅或重复收到通知时，恢复视图不能再次触发世界变化。项目不靠 Mod 式轮询差分还原自己已经知道的行动历史。长行动按已声明的阶段分别完整提交，每阶段有独立结果；“只扣了一半费用、其他字段没写成”属于存储故障，不能伪装成玩法允许的部分完成。

首次 Demo 沿用确定性条件，不实现随机检定。如果后续单独测试 2d6，须按核心系统规定保存首次样本与结果，并另列对照验收；不能因工程预留 RNG 字段而默默改变当前玩法。

### 4.3 时间、日程与空间

- 按本轮主方案，普通移动与 UI 操作冻结游戏时间；阅读、输入法选字、设置和模型等待也不消耗游戏时间。时间只由已定义的行动、等待或预编排事件推进，不设置例外的关键实时计时段。小游戏可以有输入挑战，但游戏内时间仍按该动作定义结算；这个规则与是否使用 3D 无关。
- 行动从一个日程窗口跨到另一个窗口时，先检查“允许跨窗”“中断并结算部分”“拒绝开始”三者中哪条适用，不能每个任务临时猜。
- NPC 日程按稳定时间点和任务覆盖规则编排：章节强制安排 > 当前承诺/任务安排 > 日常安排。不得同一时刻在两张地图出现。
- 未加载地图只更新逻辑位置和安排；无需让远处 NPC 逐帧走路。进入场景后从合法锚点呈现，临近关键人物的可见移动避免突然瞬移。
- 检测区域通行许可与具体设备操作权限，不能因进入房间就获得全部操作权。
- 所有活动使用同一游戏分钟推进入口；跨日跳转要处理经过的窗口，不只处理最终时间。同刻完成、许可过期/离场和生成新菜单的顺序，按 AI 运行协议第 3.2 节执行，不另用帧回调到达顺序决定后果。

这些是对 K01、K03、K04 的工程适配，不是关于《动物迷城》源码的陈述。

### 4.4 任务、物品、关系与视角如何使用同一事实

- **任务分三份。**定义保存稳定任务/目标 ID、条件与奖励规则；本局实例保存接取、目标结果、终态与奖励结算；世界事实保存真正发生的持有、交付、知情和承诺。接取时和载入后按定义判断已有事实是否有效：持有型目标可读取当前库存，要求“接取后送达”的目标须匹配实际送达记录，不能一概补造一次库存事件。目标顺序、文案和 UI 分组不承担长期身份。
- **任务完成不等于奖励已领取。**自动奖励与目标终态在同一事务写入；需主动领取时，领取是独立的受控行动，使用同一奖励身份防重复。重建日志只重建视图，不执行奖励规则。
- **物品有作用对象。**购买、持有、装备、交付、消费和留置分别按动作定义处理；数量上限、被预留资源或错误目标在确认前复核。场景中的物件、库存和任务读取同一来源，不各自加减一份副本。默认不引入通用库存“部分成功”；确需部分交付时必须先有明确玩法规则和预览。
- **关系有具体来源。**识别、兴趣、信任、本人知情、某项计划的同意和访问权限分别记录；没有查询到数据是缺失/错误，不自动解释为数值零或拒绝。更新读取规则实际结果，不照搬社区观察器的请求增量。Z 的台词不能自行授予下一步能力。
- **视角只换行动者与可见信息。**Z 节点使用同一行动执行器、存档与世界时钟，输入经过当前行动者的知识、物品和候选动作过滤。未传出的 Z 观察不进入玩家角色证据；切换前后均保存。D1—D3 邀请节点按串行实现，同时最多一个正式行动，不先做任意切人或完整双主角日程模拟。后期若引入独立并行区间，再按运行协议汇合；不能把有消息依赖的动作并行省时。

这些边界分别对应研究 K04/K05/K10/K11/K12 和[社区任务、关系、道具分析](../research/动物迷城/05-社区源码深读与Z实现参考.md)。它们用于 Z 的确定性实现，不意味着已验证原作采用相同内部结构。

## 5. 原创像素资产与地图规格

### 5.1 先做一张房间和一名角色，才冻结全套规格

建议第一版世界视口 **640×360**，基础格 **32×32**，角色源画布约 **32×48**，脚底中心作为枢轴。在 1280×720、1920×1080、2560×1440 和 3840×2160 下分别可用 2、3、4、6 倍整数放大。这是项目建议，不是原作尺寸。若一屏可读性或人物辨识不够，在小样阶段改，批量生产后不要轻易改基准。

世界层采用最近邻采样，不做混合像素密度；UI 和中文字体单独在输出分辨率绘制，不能把中文一起压进 640×360 再放大。非整数窗口优先保比例加边或采用事先验证的策略，不拉伸角色。Godot 的视口、拉伸与比例设置提供基础支持，实际相机移动和高 DPI 仍需测试。[官方多分辨率指南](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html)

资产交付契约：

| 类别 | 原型规格建议 | 必须同时交付 |
|---|---|---|
| 主角、Z | 四方向；站立 2 帧、步行 6 帧/方向；关键操作另画 | 原文件、PNG 图集、帧标签/时长、脚底枢轴、调色板 |
| 手机直播中的 Z | 独立近景资产，白发角色身份与世界形象一致；已选 C 方向继续细化，v2 尚未最终批准 | 可编辑分层源文件、补全被遮区域、参数/表情/动作表；动态模型与导出物在选型和集成验证后确定 |
| 功能 NPC | 四方向基本动作；暂不做八方向、整套换装 | 与主角统一格尺、足部遮挡规则、状态对应表 |
| 地形/建筑 | 一套海岛室外、一套室内共用基础；地面、墙、屋顶、装饰分层 | TileSet 源图、碰撞/遮挡说明、可交互物 ID |
| 道具/设备 | 拾取物、背包图标和场景模型有同一 ID | 开/关、已取/未取、通电/断电等实际需要的状态 |
| UI | 九宫格面板、按钮状态、焦点/禁用图标；中文矢量或清晰点阵字体 | 原始组件、状态清单、字体许可、颜色/间距标记 |
| 音频 | 海风/室内/直播环境循环，少量脚步与交互音 | 可循环 WAV 源、导出格式、响度/总线记录、许可 |

四方向基础动作为每人 32 个帧位；Demo 的玩家、Z 和 4 名功能 NPC 共 6 套角色约 192 个基础帧位，特殊动作还要追加。镜像和共用模板可以节省工作，但有胸牌、持物或发型不对称时不能无条件镜像。必须用实际小样记录“完整角色一套动画”耗时，而非根据单张 AI 图生成时间估算。

AI 生成图可辅助概念探索，**不能直接算作合格 sprite sheet**。连续帧的身体比例、轮廓、脚底、物件和像素网格仍需人工清理；不得使用原作拆包角色、地图和 UI 素材作为交付资产。

### 5.2 地图、碰撞和导航各自独立

地图层建议为：地面、低障碍、按脚底 Y 排序的人物/家具、前景墙或树冠、交互区域。人物碰撞体以足部占地为准，角色上半身可被高物体遮挡；过宽的整身矩形会让门口和桌边无法靠近。

- 小岛四区域通过明确入口连接；地图 UI 读取同一拓扑与已知地点数据，不能再维护一套手写导航关系。
- 每个门或设备至少有视觉状态、碰撞状态、访问条件、操作条件；开门要同步更新寻路，不能只有动画变了。
- 楼梯或“桥下/桥上”必须分逻辑楼层和导航层，避免同一二维点被误当相连。
- 小范围规则网格可以先验证 AStarGrid2D；自由路径更自然时再用 NavigationRegion2D。不要同时维护两套未经证明必要的导航。
- Godot 官方明确提示 TileMap 内置导航有性能和路径质量限制，且同一导航图上不能把二维导航网格按视觉层直接堆叠。采用何种方案先由一张代表性地图验证。[TileMap 官方说明](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)、[AStarGrid2D API](https://docs.godotengine.org/en/stable/classes/class_astargrid2d.html)

验收场景必须包括：两 NPC 对向过门、玩家挡路、门在行走中关闭、跨楼层、前景遮挡、任务临时调走 NPC。卡住后应有重算/让路策略，不以穿墙和可见瞬移作为通用修复。

### 5.3 UI 必须先服务阅读与操作

建议 1080p 下正文 24—28px，重要选项至少 28px，并提供字号和背景不透明度选项；具体观感以中文实机为准。像素场景不要求中文也做成难读的低分辨率像素字。

只在当前上下文显示需要的信息：时间、当前操作、金币/相关库存和可知阻碍；完整背包、任务与人物记录按需展开。夜间切为手机直播界面，白发 Z 的近景回应与弹幕输入、礼物、连麦报名/拒绝分层显示；不沿用现场俯视图，也不把后台权限操作混成观看按钮。重要证据和系统操作不能被弹幕遮挡。鼠标焦点、键盘焦点、输入状态、确认与取消路径必须一致。

中文输入法、长名字、两倍文本长度、连续滚动记录、按键重绑及暂停后恢复属于功能验收。已有 PNG 不包含这些实现证据。

### 5.4 手机近景与 Live2D 式表现单独验证

近景 Z 与像素行走图是两套用途不同的资产。当前只确定她在手机画面中用表情、视线与动作回应互动的目标，没有选定 Live2D SDK、插件、模型格式或绑定方案；现有概念 PNG 不能直接视为可运行模型。先依据[手机直播专项方案](手机直播交互与美术方案-v1.md)确定构图候选，再交付参数表、分层角色源文件与受约束的表情/动作映射，随后核查所选方案的授权、Godot 集成、Windows 导出与性能。

规则层已提交的回应事件驱动演出，演出完毕不发放金币、物品或推进日程；模型只可从允许的表现标签中选择。动态模块不可用时保留近景静态表情和字幕、输入及节目推进，不能阻塞 D1—D3 规则验证。静态回退通过也不等于动态目标已完成。`ui/v1` 与 `ui/chapter1-pixel-v2` 仍为历史图，其精力/岛券和现场直播不能作为当前接口规格；已选 C 方向继续细化，v2 尚未最终批准，旧三方案保留比较。

## 6. 内容与数据管线

### 6.1 定义和运行数据分开

| 数据 | 作者编辑来源建议 | 运行时存储原则 |
|---|---|---|
| 道具/动作/角色定义 | Godot Resource 或 Unity ScriptableObject；批量数值可从 CSV 导入 | 稳定 ID 引用；定义通常只读 |
| 任务 | 小型结构化资源：阶段、前置、动作、结果、失败、补救、截止 | 单独的 QuestState；不靠对白播放次数推断 |
| 日程 | day/phase/地点/锚点/覆盖优先级表 | 当前安排和已触发事件独立 |
| 对话 | 选定的对话编辑工具和文本源 | 查询规则层，指令仅调用白名单动作 |
| 本地化 | 语言表、稳定字符串 ID、说话人/语境/变量注释 | 文本键与逻辑 ID 分开 |
| 存档 | 自有版本化 DTO/JSON 等 | 只存运行状态、引用 ID 与必要日志 |

Godot Resource 能在 Inspector 中编辑并保存为可版本控制的 .tres；Unity ScriptableObject 适合作为预制数据，官方明确 standalone Player 不能像编辑器那样直接持久化其资产修改。[Godot Resource](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)、[Unity ScriptableObject](https://docs.unity3d.com/6000.3/Documentation/Manual/class-ScriptableObject.html)

避免一开始自研图形化任务编辑器。先用现成 Inspector、表格与对话工具，补一个数据校验器和调试查看器；当作者实际反复卡在相同操作时，再开发定向工具。

### 6.2 每个任务单元必须具备的字段

一个“任务单元”不是一个按钮或一句台词，而是一段可独立测试的因果链：进入条件、玩家目标、至少一个动作、成本、世界变化、失败或替代、结束条件。

每单元记录：ID、章节/日期窗口、涉及 NPC/地点、已知与隐藏前置、持有/提交物、必然或随机结果、互斥事实、承诺、截止后处理、复用资产、对白键、存档检查点、自动化断言。重要线索必须记来源和核实状态。

内容检查器至少报告：重复 ID、断引用、不可达阶段、无终点环、没有补救的关键物品消耗、截止先于出现、NPC 位置冲突、条件分支全假、缺语言键和重复奖励。不能把 AI 生成对白数量当任务完成量。

### 6.3 本地化与版本控制

先交付完整简体中文；同时采用稳定字符串键，避免硬编码拼接长句。用伪本地化验证扩展长度，再决定英文制作范围。AI 台词使用当前语言和相同的规范术语；不把生成内容写回作者语言表。

Godot 有国际化与 CSV/gettext 工作流，Unity 有 Localization 包；实际选用工具需验证占位符、字体、换行与导出完整性。[Godot 国际化](https://docs.godotengine.org/en/stable/tutorials/i18n/internationalizing_games.html)、[Unity Localization](https://docs.unity3d.com/Packages/com.unity.localization@1.5/manual/index.html)

工程建议纳入 Git；像素源、音频等大二进制按需使用 LFS。引擎导入缓存、构建产物、密钥不进入源码。保留工具/插件锁定表与素材许可台账；迁移工作区时把 AGENTS.md、研究及采用记录一并纳入，而不是假设它们已被跟踪。

## 7. 存档、AI 与离线体验

### 7.1 存档应早于扩写任务

存档字段以[AI 与状态规格第 2、10 节](AI与状态规格-v2.md)维护。工程上必须完整保存本局/分支身份、内容与规则版本、时间、角色知识与承诺、资产、场景、任务实例和目标 ID、pending/预留、已提交收据及去重范围、必要的展示进度。后期出口与迁移状态按实际引入的模块加入，D1—D3 不为未实现终局制造假数据。表达摘要和最后一条回复只属于可重建的表达层，不能替代世界事实。

保存采用“写临时文件—校验—替换正式文件—保留上一份”策略，并验证目标平台行为；不要声称所有文件系统上天然绝对原子。损坏时读取已验证备份，不静默生成空进度。区分设置、存档槽和周目已解锁的便捷功能。

加载必须经过明确屏障：停止接受新行动 → 作废旧会话在途请求并更新加载代次 → 读取与验证候选存档 → 迁移版本或明确拒绝不兼容内容 → 恢复世界、pending/预留及已提交结果 → 核对任务、角色知识与场景引用 → 重建视图 → 开放输入。加载代次用于区分运行中的先后会话，不能被旧存档里的计数覆盖后与旧请求重新相等；具体字段遵循 AI 规格。

未确认的 UI 输入和在途模型请求在切档时作废；目标存档中合法的 pending 仍按其原执行身份恢复，两者不能一起粗暴清空。已提交动作只恢复结果和展示进度。去重记录与其世界快照一致恢复，不能用跨档全局“已处理 ID”阻止玩家合法回滚后的重试，也不能让新周目继承上一局的知识和奖励。

加载时校验版本、稳定 ID、数据范围和引用；任务目标重排不改变其身份。缺少定义或迁移失败时保留原档并给出明确原因，不偷偷跳过目标。G1 即需保存/载入往返比较、提交边界故障注入和重复请求检查；之后新增状态必须同时补恢复规则。没有提出面向玩家的兼容承诺前，可明确标识开发档不兼容，不能声称已有通用迁移能力。

Godot 官方保存教程提供持久化对象与文件示例，但不替本项目解决版本迁移、事务一致性和内容软锁。[官方保存教程](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html)

### 7.2 AI 的入口和输出必须受限

AI 运行协议以[AI 与状态规格](AI与状态规格-v2.md)为权威，本文件不另列请求/响应 schema。工程接入分为三项可以单独替换的责任：

1. **构造上下文。**从已提交状态生成当前角色可见、当前受众可披露的事实和合法候选；上下文附会话/存档与状态版本。玩家原话属于待理解的表达，不是已经发生的事实。
2. **理解与提议。**意图、引用材料和作者定义的行动候选经过协议校验和当前规则复核。涉及耗时或重大承诺时进入正式确认，不因模型返回合法 JSON 就直接执行。
3. **表达已提交结果。**向模型提供本次实际结果与可引用经历；不得重新计算分数、物品、权限、承诺或任务。受约束主动提议须被接受/修改并实际兑现，不能只验收一段“她主动说了话”的台词。

G1 可先提供作者文本适配器和可注入响应的测试接口，G3 用它跑通合法提议与行动后果。接口占位不表示已完成 AI；G5 必须接入实际模型，分别验证意图处理、提议依据、引用约束和表达质量，记录所用模型/协议/内容版本。假响应可用于异常注入，但不得混入实际模型通过样本。

“理解”“相信”“愿意合作”应由主方案定义可检验的语义条件，例如核实了哪些事实、表达了哪些顾虑、是否给出明确同意；不能只凭模型一段情绪强烈的文字就把全部开关置为真。词义判定不确定时允许澄清或转为明确选项，不暗中猜重大承诺。

公开构建的模型密钥应在受控代理端；客户端不能内置付费服务密钥。代理只接收必要的游戏状态与输入，增加请求上限和并发限制；本地世界仍能离线运行。不在首次 Demo 搭建账号、云存档、复杂管理后台。

### 7.3 网络与模型失败的确定行为

| 情况 | 体验与规则建议 |
|---|---|
| 超时、断网、限流 | 给出简短状态并切换作者对白/明确意图选项；模型故障不追加时间或关系代价，已提交的劳动结果及其成本保持 |
| 输入无法理解 | 澄清一次或展示当前可表达的主要意图；保留已输入文字 |
| 回复格式错、越权或矛盾 | 不应用状态变化，使用该状态对应的已审 fallback |
| 返回时玩家已离开/状态改变 | 重新校验请求身份、加载代次、角色/上下文与状态版本；只按运行协议展示仍有效的表达，过期行动候选必须重新判定，不能把旧许可应用到新场景 |
| 玩家取消/读档 | 未确认表达可取消；读档作废旧运行会话请求，再恢复目标档的 pending/结果；已提交结果不退款、不重结算，晚到文本不能执行旧动作 |
| 离线模式 | 当前切片关键路径与收束仍可达，表达自由度明确降低；完整游戏以后单列全路线验收，不伪称正在使用在线 AI |

Godot HTTPRequest 提供超时、完成信号与取消接口，但上述事务和 fallback 必须由项目实现；没有“换个 SDK 就自动解决”的依据。[官方 HTTPRequest](https://docs.godotengine.org/en/stable/classes/class_httprequest.html)

延迟指标统一采用[AI 与状态规格 v2 第 11 节](AI与状态规格-v2.md)：开始可读回应尽量在 2 秒内，完成回应 P95 目标 8 秒内；均是原型目标，非现有实测，不在本文件另立一套标准。超时与回退按同一规格执行。单机移动与 UI 不等待同步网络调用。

模型成本用实测 token 计量：每轮成本 = 输入 token / 100 万 × 输入单价 + 输出 token / 100 万 × 输出单价，再加重试/摘要。例：一次 Demo 16 次调用，每次平均 2,500 输入、130 输出，为 40,000 输入、2,080 输出 token；这只是算量假设，没有指定供应商、实时价格或月费。应测正常一轮、重玩和异常重试的上限，避免每回合发送全部聊天历史。

### 7.4 验证 AI 是否值得保留

用相同世界状态对比“作者选项版”和“AI 自由表达版”。检查玩家是否更能表达顾虑、是否感到 Z 记住了真实经历、是否减少选项理解偏差；同时测延迟、矛盾、越权、成本与卡关。AI 关闭后若游戏完全失去规则循环，说明系统边界未做好；关闭后若体验几乎不变，也不能凭“接了模型”宣称 AI Native 已被验证。

## 8. 风险原型：验证依赖与失败后的收缩

原型可以使用占位资产。各项产出进入第 9.3 节阶段证据；这里不另开一套按天承诺的排期，也不把多个原型分别做成独立系统再重写整合。

| 风险与所属阶段 | 必须拿到的证据 | 未通过时的处理 |
|---|---|---|
| 工具链与输入，G0/G2 | 一个候选引擎能形成测试包；场景中中文输入法、焦点和基本交互可用 | 先修构建/输入，只有明确阻碍才换引擎；不批量生产 |
| 确定性规则与持久化，G1 | 不加载正式场景即可执行动作；相同输入可核对结果；保存失败、重复请求与重载不产生半套状态 | 缩小动作种类，先修提交和稳定身份，不扩写任务 |
| 时间/交易/任务联动，G2 | D1 的工资、成本、真实持有、机会与任务日志来自同一提交；跨窗拒绝有原因 | 修条件和结果来源，不用动画补丁或轮询日志凑状态 |
| 两条认识路径与补救，G3 | 不同投入可达同一认识目标；遗漏后仍有已设计且有成本的补救；提议有实际兑现 | 调整内容依赖/窗口，不能临时送礼保底或 AI 赐予资格 |
| 像素与地图小样，G2—G4 | 单房间角色、遮挡、交互距离、门与日程一致；新增任务可由数据接入 | 先降低空间/演出复杂度，补有证据的定向工具 |
| 受限 Z 视角，G4 | 只出现她合法可做的邀请动作；知识/背包不串角色，时间与存档可恢复 | 缩小节点操作，不删去真实邀请动作而仅播放镜头 |
| AI 表达与异常，G5 | 实际模型样本、固定事实引用、晚到响应隔离、断网继续、延迟与费用记录 | 收缩生成场合和候选，不把作者替代文本记成 AI 通过 |

不要分别把两款引擎都做成完整原型。先根据熟练度选一个；只有出现明确阻碍才用另一款重做同一个极小测试。

## 9. 构建、测试与验收门槛

### 9.1 平台与构建准备

首发验收目标建议为 **Windows 10/11 x64、键鼠**；开发机是 macOS 并不意味着 Windows 体验已验证。需要一台真实 Windows 机器或明确的测试协作者；导出成功、虚拟机能启动、Windows 真机跑完是不同证据。macOS 测试包可以作为开发便捷交付，但不要自动扩大成双平台正式承诺。

Godot 需要匹配引擎版本的导出模板。Windows 和 macOS 均有官方导出流程；macOS 外部分发还涉及签名/公证，不能以本机绕过提示等同于可分发包。[Windows 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)、[macOS 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_macos.html)

每份构建保留：build_id、引擎/模板/插件版本、源码 commit、内容版本、导出设置、构建日志、已知问题和对应测试记录。可利用官方命令行导出形成复现脚本；本轮没有运行它。[Godot 命令行](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)

iOS 放在 PC 闭环之后单列预算：触摸移动/点选、虚拟键盘遮挡、横屏安全区、暂停后台恢复、网络状态、真机性能与签名。Godot 官方流程要求 macOS 和 Xcode；“有导出选项”不代表这些适配已完成。[iOS 官方导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html)

### 9.2 测试层次

- **规则自动化：**前置真假、费用边界、跨日、事件顺序、任务谓词、幂等结算、保存/载入往返与提交故障。调用实际规则核心，确认无场景和网络依赖；只在另行开启随机实验时补概率输入测试。Godot 可验证 GUT 候选版本；它是第三方测试工具，需锁定与引擎兼容的版本。[GUT 作者仓库](https://github.com/bitwes/Gut)
- **数据自动化：**第 6 节静态校验、关键路径可达、引用与语言键完整；不以“有测试脚本”替代可达性证据。
- **场景集成：**门/设备/人物与任务事实同步；换场景后保留准备；输入焦点、暂停恢复、保存/加载和平台导出。
- **人工体验：**约 5—8 位外部测试者逐人记录误解、卡点和决策理由；小样本只作为问题发现，不宣称统计显著的留存/喜爱率。
- **AI 回归：**使用 AI 运行规格与切片验收文的用例集合，按真实故障增加；实际模型样本和注入响应分别报告。同一规则结果下对比作者文本、联网表达和断网回退，采样通过不是永不出错的证明。

### 9.3 开发阶段的进入与退出条件

具体动作、场景、初始档与断言以[D1—D3 Demo 开发与验收规格](D1-D3-Demo开发与验收规格-v2.md)为准；运行与错误语义以[AI 与状态规格](AI与状态规格-v2.md)为准。下表定义依赖和交付，**所有阶段当前均未执行/未通过**。完成下层工具小样，不自动满足上层玩法或 AI 验收。

| 阶段 | 进入条件/依赖 | 必需产物 | 退出条件与证据 | 未通过时停止的扩展 |
|---|---|---|---|---|
| **G0 开工基线** | 当前 v2、切片规格和运行协议可读；实际工程现状已核查 | 选定的引擎小样入口、版本/许可清单、切片任务依赖索引、最小数据字典、测试环境记录 | 数据/动作/任务身份可明确引用；引擎能启动最小测试入口；场景与联网依赖可被隔离。美术规格先保持候选 | 不批量制作场景、21 天文本或新增插件体系 |
| **G1 确定性基础** | G0；核心规则有明确预期值，使用内存/临时文件测试存档与作者文本适配器 | 状态与行动执行器、稳定 ID、结果收据、任务谓词、存档适配与调试检查入口 | 在无正式地图、无模型下完成前置检查、时间/资源/结果一致提交、重复请求、pending 恢复、切档/坏档和读回比较；保留输入档、行动序列、前后状态及断言结果 | 不把交易/任务逻辑散入场景脚本，不扩写剧情 |
| **G2 D1 灰盒联动** | G1；D1 数据及占位场景可用 | 报到、工作、交易、准备、任务记录与首次节目所需场景适配；免费查看与成本预览 UI | 从新档在灰盒中执行 D1 链；工资/费用/物品/任务和可用机会一致；拒绝、重复确认、切图、读档结果符合切片用例。可观察差异必须来自真实准备 | 不以移动画面、完整 HUD 或模型聊天代替日夜因果，不精修大量资产 |
| **G3 D1—D3 双路径与补救** | G2；两路内容、补救和日程数据齐备；作者文本覆盖关键输出 | 两条成本不同的认识路径、可恢复失败、D2 提议与 D3 兑现、日切及结果记录 | 两条路径各从新档跑通；缺准备和准备充分产生不同操作；遗漏后的补救有来源和成本；提议可接受/修改/拒绝并产生正确后果。邀约资格先通过规则验证，尚不冒称 Z 视角已完成 | 不扩大到第二章身份、软禁、灯塔迁移或四章内容；作者文本通过只记离线规则通过 |
| **G4 受限 Z 视角邀请** | G3；邀请资格和可用理由来自本局事实；运行协议明确控制/知识边界 | 邀请节点、角色专属动作、邀请送达/接收记录、切换前后存档 | 能亲自完成 Z 这一侧的合法邀请动作；不强制同意、不泄漏未知身份、不借用玩家物品；共享时间不重复结算；重载后控制者/知识/邀请进度一致 | 不开放任意切人、双份成长经济或第二套主角战役 |
| **G5 联网 AI 与降级** | G4；运行协议与作者回退齐全；模型/代理与测试预算可用 | 实际联网适配、受控上下文与候选、校验/回退、请求隔离、生成与费用诊断 | 实际模型能理解切片允许的输入、引用本局事实并提出合法候选；候选经确认兑现。超时、格式错、越权、晚到、切档和断网不改变已提交结果；记录实际模型、调用样本、延迟/费用和人工判断 | 未达成则明确标“离线规则切片可用、联网 AI 未通过”，不能以假响应或作者文本替代 AI 验收 |
| **G6 完整 Demo 验收** | G1—G5 证据齐备；必要像素资产/输入/音效/回退已集成；目标机器可用 | 可复现构建、切片验收逐项记录、已知问题、来源与许可、首次玩家观察 | 目标 Windows 真机分别验证两路、补救、Z 节点、关键重载和网络降级；无存档损坏/重复结算/不可解释阻断；表现能说明条件和代价。节奏、可读性、联网体验与版本证据均满足切片完成标准 | 未通过不标完成、不进入填满四章的内容生产 |

G6 后再用实测任务、美术、集成与回归吞吐量重估完整游戏；不能把 Demo 天数或人日简单乘七。完整游戏仍需独立验证三路线、比赛和迁移，内部终局测试档不得混作玩家已走过的公开 Demo 路径。

### 9.4 证据格式与剩余风险

每次阶段验收至少记录：构建/源码与内容版本、用例 ID、初始档与操作序列、预期和实际状态差分、收据或错误原因、平台、通过/失败/未执行及剩余问题。场景验收再附短录像或截图；AI 验收再附模型/协议版本、真实调用与注入响应的区分、降级原因、延迟/费用和人工审查。没有这些记录时只能标“尚未验证”，不能因任务单已勾选写“通过”。

优先处理三类风险：状态/存档错误阻止扩大内容；两条路径在玩家感知上相同则调整机会成本与反馈；规则正确而 AI 仍不可信则收缩生成范围并复核，不能继续加自由聊天掩盖问题。美术与导航小样可交错进行，但不得绕过规则和内容依赖。

性能先在指定测试机与固定场景测量，1080p 稳定 60fps、交互不被模型调用阻塞仍只是原型目标。30—40 分钟是游玩节奏预算，不是计时到了就算通过；不能靠删去必须做出的选择或加速文本强行命中。未锁定硬件和实测前，不发布最低配置或性能承诺。

## 10. 内容规模与人力预算

### 10.1 用于估算的 Demo 口径

以下保留前轮初始预算模型；实际切片范围以 [D1—D3 规格](D1-D3-Demo开发与验收规格-v2.md)为准。数量有差异时更新预算，不反过来为满足预算数量新增任务：

- 第 1—3 个完整演示日，主路径约 30 分钟，自由探索约 40 分钟；不是把完整 21 天均匀加速播放。
- 4 个功能区域，约 4—6 张小场景；玩家、Z 和 4 名功能 NPC，合计约 6 套角色。
- 第 1—3 日的完整主线链；用于估算约 6—8 个任务单元、1 个共同障碍的 2 种准备路径和 1 次可恢复失败。用早期沟通与次日后果验证协作，不要求 Demo 提前演完整个游戏的逃离终局。
- 8—12 件有用途的道具，管理时间、金币与库存；不含精力或替代状态预算，也不含完整回合战斗、八方向角色、全语音、多人、移动首发、全岛自主生活模拟。
- 约 80—120 个对白/事件节点，全部分支约 6,000—10,000 汉字；单周目显示约 2,000—3,500 字。数量需通过可玩节奏验证，不能为满足字数塞对白。
- 世界文本、日程反应与 AI fallback 都进入作者内容预算；模型不能承担未经审核的关键事实和结局。

### 10.2 Demo 的分项人日

这里的 1 人日指约 6 小时有效制作/整合时间；不是 24 小时，也不把 AI 生成等待当主要制作成本。假设开发者已有基础编程能力，能完成中等复杂度原创像素资产，采用有限动画与现成引擎工具。若这些条件不成立，增加学习/外包或减少范围。

| 工作包 | 估算人日 | 主要计量依据 |
|---|---:|---|
| 风险原型与规格冻结 | 8—12 | 前轮初估占位；按第 8—9 节实际验证投入校准 |
| 规则/时间/资源/任务/存档底座 | 10—16 | 一套行动结算与持久化，不重复建系统 |
| 4—6 场景、碰撞、日程与路线整合 | 10—16 | 单地图搭建与集成吞吐量 |
| 像素角色、环境、道具、UI、基础音效 | 17—28 | 6 套有限动作、2 类主要 TileSet、组件复用 |
| 剧情、分支、作者对白和 fallback | 8—14 | 6—8 任务单元及 80—120 节点 |
| AI 适配、代理与异常降级 | 5—8 | 单角色、有限场合、结构校验与缓存 |
| 集成 QA、外测修正、构建与交付 | 7—12 | 关键路径、平台、存档和文本回归 |
| **小计** | **65—106** | 各包按单人顺序/交错投入相加 |
| **加 20% 返工余量** | **约 78—128 人日** | 首次估算占位，原型后重新校准 |

这些人日是前轮的未校准生产假设，当前不换算成阶段交付日期。单人兼任各工种并不会使它们真正并行；兼职按可投入的有效小时换算。完成 G2 后首次重估基础与场景成本，G4 后校准分支内容与视角成本，G5 后补模型适配和回归实测；阶段是否完成始终按证据，不能按估算时间已耗尽来判定。

2026-10-11 新增的手机近景动态资产、绑定与引擎集成尚未实测，**未包含在上表的像素动画估算中**。取消精力会缩减规则工作，但不能据此声称足以抵消新增美术成本；完成一套 Z 的分层与基础回应小样后再重估 Demo 和完整版总量。

### 10.3 完整游戏：按本轮主方案内容量估算

完整游戏按约 6—8 小时、21 天四章、玩家和 Z 加 8 位配角核算。普通 NPC 包括两位剧情中的 AI 对手均由作者编排，不运行另一套开放 AI 代理；对手的动机、日程、策略变化与任务反馈仍要制作和回归。

| 本轮主方案内容量 | 生产核算方式 |
|---|---|
| 玩家、Z、8 位配角，共 10 套主要角色 | 基础动作约 320 个帧位；专属行为、表情与剧情动作另计 |
| 8 个室内场景，已有四区域室外结构复用 | 室内需要独立布局和交互；室外的具体场景拆分数量尚待地图小样，不能把室外美术当零成本 |
| 24 个核心任务 + 12 个支线单元 | 共 36 个单元，每个包含条件、成本、结果、失败/替代和回归路径 |
| 12 项技能、30 件功能物品、3 条主要路线 | 数据、图标、效果、禁用原因、来源、组合与可达性都要整合测试 |
| 3 类活动模板、12 个共同记忆节点 | 模板可以复用交互，但事件文本、知识来源和角色反馈仍分别作者化 |
| 4 段 Z 的短 POV，合计约 10—15 分钟 | 计入总游戏时长；复用 Z 资产，追加视角权限、知识隔离、转场和读档测试，不另建一套长期角色养成 |
| 文本总量尚未定稿 | 按主方案先以全部分支 4—6 万汉字作预算变量，须通过前 3 个任务的实际字数与阅读节奏校准，不当成强制字数 |

**从零完成上述内容量的初始估算为约 320—540 个有效人日，含可复用的 Demo 工作。**按每年约 220 个有效人日，约为 1.5—2.5 人年；这是一名单人开发者所有工种相加的劳动量，不是多人团队招聘规模，也不是承诺日历期限。

| 工作包 | 完整游戏总人日提案 | 估算依据 |
|---|---:|---|
| 规则、工具、存档、AI 适配与构建 | 70—110 | 复用 Demo 底座，加入两位作者编排对手的状态回归、章节与 POV 状态支持 |
| 地图、美术、动画、UI 与音频 | 90—150 | 10 套主要角色、8 室内、室外复用及专属事件状态 |
| 任务、对白、日程和内容整合 | 80—140 | 36 单元、21 天四章、记忆节点、活动模板与 4 段短 POV |
| 跨系统 QA、返工、外测和发行准备 | 80—140 | 3 路线、不同任务顺序、读取旧档、AI/离线、章节与结果组合 |
| **总计** | **320—540** | 已包含整合与返工预算，不再另加一次 Demo 或 20% |

这些数字不是行业统计，也不是从原作团队人数反算。它们是假设开发者已有基础程序能力、采用有限四方向原创像素动画、不含全语音和 iOS 首发的预算。八位配角的剧情深度、每个任务的解法数量和必须独立绘制的动作仍会明显改变结果。

增加 NPC 并不只是增加一张立绘；扩展现有任务的分支会同时影响对白、日程、存档和 QA。若可投入周期显著更短，应优先缩减演出与状态复杂度或任务密度，不能仅把 21 天填入日历就承诺同样的内容体验。

校准办法：记录前三个任务从设计到通过回归的实际小时、第一张地图的整合时间、第一名角色全套动作时间；据此重算剩余数量。预算式为“固定系统成本 + 各类合格内容单元数量 × 实测单价 + 整合/回归 + 余量”。重用资产按真实改动计价，不能按零成本，也不能把同一成本同时算进多个工作包。

### 11.2 需要主方案定案，但不阻止本轮研究完成的事项

1. **引擎与个人经验：**是否已有明显的 Unity/C# 熟练度；没有则采用 Godot 小样起点。
2. **Demo 细化范围：**执行 D1—D3 规格中的具体场景、任务和用例；美术切图数量以灰盒布局决定，不能为沿用初估中的 4—6 张场景主动扩大范围。
3. **输入与规则：**默认键鼠和快捷选项可完成切片；实际输入法/焦点适配在 G2 检查。当前确定性规则和无实时计时已有 v2 依据，不重新挂成开工前必须选择的问题；随机只在以后明确开启对照试验时进入范围。
4. **美术可投入程度：**角色四方向和格尺是否足够，哪些关键动作必须独立画；缺乏经验时允许占位验证多久。
5. **平台条件：**G6 所需 Windows 真机测试条件是否可获得；macOS 是否只是内部包；iOS 在 PC Demo 验收后另定范围，不能拿 macOS 导出替代 Windows 运行证据。
6. **AI 服务条件：**供应商/模型、联网目标环境、可接受延迟、每次游玩预算与代理部署归属。未指定前保持可替换接口和离线规则闭环。
7. **完整游戏生产承受能力：**以本轮 36 任务、10 主要角色、8 室内、3 路线的主方案量级测算；需要确认可投入时间、角色专属动画与文本深度，而不是另建一个更大任务范围。

这些未定事项按依赖处理：模型供应商未定不阻止 G1—G4；最终像素规格未定不阻止占位灰盒；Windows 测试条件缺失不能标记 G6 通过。本文只完成准备与阶段规格，没有任何 Gate 已通过；后续以工程、构建、运行与玩家观察证据逐项更新。

## 12. 实机参照、发行与持续服务准备

### 12.1 还需要做一次可复用的实机拆解

现有研究来自公开证据，不等同于亲自运行原作。使用自己合法可用的游戏构建与存档，记录平台、版本、主角、模式、是否开启辅助工具，再完成以下观察；用 [实机观察模板](../research/动物迷城/03-补充来源与实机观察模板.md) 归档。

| 观察片段 | 要记录的可复用结果 |
|---|---|
| 一个完整日程，含迟到/跨窗口 | 走路、待机、对话阅读、动作和菜单各怎样影响时间；窗口结束是否打断 |
| 一种工作从首次到熟练重复 | 接取、操作、结算、工资、访问机会及重复减负；区分劳动收益与任务一次性奖励 |
| 同一目标的两种办法 | 条件、物品、能力、人情、时间与失败代价；实际操作是否有不同 |
| 一次失败并继续 | 丢失什么、保留什么、如何找到补救；读档前后状态是否一致 |
| 一段真正的逃离执行 | 准备如何兑现为空间操作，何时不可返回，哪些资源或合作不可替代 |
| 五个代表界面 | 探索HUD、行动成本菜单、对话/检定、背包、任务记录；记录信息层级、焦点、关闭路径、字号和状态反馈 |

产出的是“动作→代价→变化→下一步”记录与组件行为表，参考图仅作内部比较；不给截图自动贴上已经实现或完成美术的标签。观察未完成前，本作普通移动冻结、确定性检定和像素规格仍明确属于自己的选择。

### 12.2 PC 发行准备

若采用 Steam 发行，需要分别准备商店页与产品构建：真实玩法说明、截图与视频、语言/联网信息、输入与系统要求、测试构建、版本和已知问题。Steam 官方将商店与构建审核分开，并要求正式发布前 Coming Soon 展示至少两周；正式排期还要核对账号开通等适用要求，不能把导出安装包之日直接当作上架日期。[Steamworks 发布流程](https://partner.steamgames.com/doc/store/releasing)

目前不创建商店页、不支付费用、不发布任何内容；这些属于 Demo 通过之后的制作计划。发行截图应来自实际游戏，静态 UI 图只能明确作为概念展示。首个预告应能看清日间选择、夜间回收与 Z 的回应，不只剪角色立绘。

### 12.3 AI 内容说明与服务预算

Steam 内容调查区分预生成 AI 内容和游戏运行时生成内容；运行时生成需要说明用于约束输出的措施。项目需要保存哪些内容使用生成工具、哪些回应在运行时生成、如何限制无依据事实/越界内容及如何回退的实际说明，并以提交时的官方要求为准。[Steamworks Content Survey](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)

建议先按买断叙事游戏测算，把典型首通、多周目、长对话和异常重试的云端成本纳入预算；游戏内礼物只使用金币或实际库存，不绑定真实充值。定价前需要实测模型、服务期限、并发、缓存与维护成本，不能在没有费用依据时承诺无限永久免费云端聊天。Steam 官方列出了把服务费用计入游戏价格、平台支持的微交易、订阅或 DLC 等处理方式；这里只选择买断作为研究起点，不决定额外收费方案。[Steamworks 关于实时 AI 服务成本的说明](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)

离线关键路径、可恢复存档和作者回退能减少服务中断对已购游戏的影响。它们仍需要实际构建验证，不能仅靠“单机游戏”名称保证长期可玩。
